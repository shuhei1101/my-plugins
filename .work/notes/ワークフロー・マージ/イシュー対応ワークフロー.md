# イシュー対応ワークフロー — review → resolve → close

`.work/issues/` に溜まったイシューを「レビュー（捌く）→ 対応（消化）→ クローズ」で流すワークフロー。
スマホからの運用を含めて、ユーザーは判断だけを行い、ブランチ作成〜マージ待ちコミットは自動で進む。

---

## 全体像

```
issue-create / issue-scan        issue-review                 issue-resolve (/loop)              merge / reject
  （decision: pending で作成）  →  （ユーザーが decision     →  （1 起動 1 イシュー）          →  （closed/ へ）
                                    accept/reject を記入）         accept → issue-resolver agent
                                                                   reject → chore/rejected-issues
```

- **作成**: `issue-create`（手動）/ `issue-scan`（スキャン）が `.work/issues/ISSUE-{N}.md` を作る。
  フロントマターは `decision: pending` / `status: not_started` / `branches: []` / `instruction: ""`。未解決事項は `## QA` に提起。
- **レビュー**: `work:issue-review`（スマホ主用途）。未レビュー（`decision: pending`）を上から 1 件ずつ
  `AskUserQuestion` で提示し、`decision`（accept/reject）を記入。イシューの `## QA` もその場で回答させ、
  自由記述の対応指示は `instruction` フロントマターキーに書く。結果は master にコミット（resolve が新ワークツリーで読めるように）。
- **対応**: `work:issue-resolve`（`/loop` 駆動、1 起動 1 イシュー）。
  - `accept` + `not_started` → `work:issue-resolver` サブエージェントを 1 つ委譲。`work:start` で
    ブランチを切り、修正を実装し、**マージ待ち最終コミット**で停止（マージはユーザーが別途）。
  - `reject` → 共有ブランチ `chore/rejected-issues` で `wontfix` クローズ（`closed/` へ移動）。蓄積して
    まとめてマージ。
  - `pending`（未レビュー）/ `accept`+`in_progress`（対応中・別セッションの可能性）→ スキップ。
- **クローズ**: `merge` がブランチの `## 関連イシュー` を `resolved` でクローズ、reject ブランチは
  `wontfix`。どちらも `closed/` へ移動し `_index.archive.yaml` に記録。

---

## フロントマター（イシューの状態の source of truth）

| フィールド | 値 | 設定者 |
|---|---|---|
| `decision` | `pending` / `accept` / `reject` | 作成時 `pending`。`issue-review` でユーザーが accept/reject |
| `status` | `not_started` / `in_progress` | 作成時 `not_started`。`work:start` が対応ブランチ作成時に `in_progress` |
| `branches` | ブランチ名の配列 | `work:start` が対応ブランチ作成時に追記 |
| `instruction` | 自由テキスト（既定 `""`） | ユーザーの自由記述の対応指示。`issue-review` で記入 |

- `status` は `_index.yaml` にもミラーする（`issue-tool.py set-status`）。フロントマターが永続記録、
  `_index.yaml` がセッション横断のライブ信号。
- QA は**イシュー側**に持つ（`## QA`）。作成・スキャン時に提起し、レビュー時に回答。これにより
  resolve のサブエージェントはブランチ作成中に QA で止まらず最終コミットまで到達できる。
  タスクドキュメントの `## QA` は従来どおり残す（イシュー由来でないブランチ用）。

---

## reject 集約ブランチ `chore/rejected-issues`

- reject のクローズは master 直コミットできない（`master-commit-guard`）ため、専用の集約ブランチを 1 本
  だけ用意し、その専用ワークツリーで close コミットを積む。
- セッションが変わると経緯を忘れるため、ブランチ文書に各 reject（ID・タイトル・理由）を追記する。
- ユーザーがそのブランチで OK を出したらマージ＝リジェクト確定。

## 関連コンポーネント

| 種別 | 名前 | 役割 |
|---|---|---|
| スキル | `work:issue-create` | イシュー作成（既定フロントマター・QA 提起） |
| スキル | `work:issue-scan` | スキャンでイシュー作成（既定フロントマター付与） |
| スキル | `work:issue-review` | 未レビューを捌く（decision/QA/instruction 記入・スマホ主用途） |
| スキル | `work:issue-resolve` | レビュー済みを消化（/loop・1 起動 1 イシュー） |
| スキル | `work:start` | ブランチ作成 + イシュー連携（status/branches/関連イシュー） |
| エージェント | `work:issue-resolver` | 1 イシュー→ブランチ→マージ待ち最終コミット |
| スクリプト | `issue-tool.py` | `set-status`（status ミラー）/ `close`（closed/ 移動 + archive 追記） |
| リファレンス | `work-dir/イシュー.md` | イシューファイル構成・フロントマター・索引スキーマの単一情報源 |
