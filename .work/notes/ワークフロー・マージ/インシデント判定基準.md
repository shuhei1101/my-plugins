# インシデント判定基準ノート

## インシデントとして記録すべきもの

- コマンドを実行したらエラーが発生し、正しい方法が判明した
- ファイルを誤って削除・上書きしてしまった
- 当初の計画（TODO）に含まれていたはずの作業を AI が漏らして、ユーザーが再依頼した
  - 例: JP ミラーを作り忘れて英語版しか作らなかった → ユーザーが「JP ミラーも作って」と指示
- AI が誤った仮定で動いて、ユーザーが訂正した
- **意図齟齬インシデント**（Claude Code 側の判断ミス）— 記録すべき典型例:
  - 「X をリファクタして」と言ったのに Claude が X を丸ごと削除した
  - 「小さな変更」と言ったのに Claude が機能全体を作り直した
  - Claude がスコープを誤解し、ユーザーが「そういう意図じゃなかった、Y だけにしてほしかった」と訂正した
  - Claude がファイルを「不要」と判断して削除 → ユーザーが「なんで削除したの?」と指摘（削除が誤りだった）
  - Claude が古い挙動をデフォルト保持したが、ユーザーはすでに「不要」と伝えていた

## インシデントとして記録すべきでないもの

- PR で対応した作業内容そのもの（ソースコードの修正内容）
- ユーザーが新たに追加で依頼したタスク（スコープ拡張）
- 一般的なベストプラクティスや既存ドキュメントに書かれた内容
- **ユーザー自身の依頼が不明確・誤りだったケース** — ユーザーの表現が曖昧・不完全で Claude がその文字通りに従った場合は、責任はユーザー側にある。Claude Code のインシデントに記録しない。

## 判断の境界線

「そもそも最初からやるべきだったのに漏れた」→ インシデント
「ユーザーが新たに気づいてお願いした追加作業」→ インシデントでない
「ユーザーの意図はコンテキストから読み取れたのに Claude が読み誤った」→ インシデント
「ユーザーの依頼自体が不明確・誤りで Claude が文字通り従った」→ インシデントでない（ユーザー側の責任）
