# イシュー対応スキルとライフサイクル整備

> ブランチ: `feat/issue-resolve`

## 概要

`.work/issues/` に溜まったイシューを `/loop` で上から自動処理する新スキル `work:issue-resolve` を作る。
ユーザーは ISSUE のフロントマターで「対応する/しない（decision）」を選び、任意で `## ユーザー指示` を書く。
AI はループで上から走査し、対応するものはブランチを切って最終コミットまで進め（マージはユーザーが別途）、
対応しないものは closed/ へ退避する。

その前提として、まず work プラグインの**現行ライフサイクル**（フック駆動の一連の流れ）を
`CLAUDE.md` / `CLAUDE.jp.md` に文書化する。issue-resolve はこの既存ライフサイクルの上に乗る。

## QA

### QA-001: 「対応しない（reject）」イシューのクローズをどこでコミットするか

**背景**: `issue-resolve` は reject されたイシューを closed/ へ移動し `_index.archive.yaml`（git 追跡対象）へ
追記する必要がある。しかしループ起動時はブランチが無く master 上で動くため、`master-commit-guard` フックが
master へのコミットをブロックする。`_index.yaml` は gitignore なので削除はコミット不要だが、ファイル移動と
archive 追記はコミットが必要。

| # | 案 | 内容 |
|---|---|---|
| 1 | A | reject も `work:start`（type=chore）でブランチを切り、そのブランチ上で close→コミット→マージ待ち。全アクションが「ブランチ→マージ待ち」モデルに統一される |
| 2 | B | reject は master 上で close + コミット（guard を 1 回通過させる）。ブランチを作らず軽量だが master 直コミットの原則に反する |
| 3 | C | reject の close をブランチ文書に積まず、未コミットのまま放置してユーザーに委ねる |

**推奨方式**: A。ユーザーの「イシューの数だけブランチができてマージ待ちになる」というモデルと一致し、
master を汚さない。1 起動 = 1 イシュー = 1 ブランチで統一できる。

**状態**: 未解決

**決定したら反映先**: `work:issue-resolve` SKILL.md の reject 処理ステップ、`CLAUDE.md` ライフサイクル節
