# リファレンス関数型スタイル監査

> ブランチ: `docs/reference-functional-style-audit`

## 概要

dev-kit の全リファレンス（Next.js + Python）が、quest-pay の実コード同様の
**関数型・`type` 優先スタイル**に準拠しているかを精読監査し、非準拠箇所を修正する。

### 背景（前ブランチ `docs/local-yaml-repository-pattern` での経緯）

- ローカル YAML データストアのリファレンスを作成した際、初版は `Repository` / `interface` /
  クラス／ファクトリオブジェクトを使った OOP 寄りのスタイルになっており、ユーザーから却下された。
- ユーザーの方針：**クラス・`interface`・`Repository` 等のクラスチックな命名は禁止**。
  関数ごとに `type` で型を定義（例: `type FetchResource = (args: {...}) => Promise<...>`）。
  データアクセスは `fetch{Feature}` / `insert{Feature}` などの素の関数。引数はオブジェクト。
  参照すべき実コード: `~/repo/quest-pay/packages/web/app/api/*/{query,db,service}.ts`。
- この経緯から「他のリファレンスも同様に関数型で書けているか確認したい」という依頼で本ブランチを予約。

### 予備調査の結果（grep + 高シグナルファイル確認）

- **Next.js**: `next/frontend/conventions/型規約.md` がデフォルト `type`・`interface` はライブラリ拡張のみと明記。
  `class` 使用はエラークラス（`extends AppError`）と Playwright Page Object のみ → 正当。クラスベースの
  Service/Repository は不在。**概ね準拠**。
- **Python**: `python/architecture/TypeScriptスタイル適用.md` が「Function-First」を明文化し、
  Service/Repository/Provider/Validator は関数で書くと規定。`class` ヒットは DTO（`@dataclass`）・
  Pydantic・Enum・例外・Protocol の**アンチパターン例**（「やってはいけないこと」節）のみ → 正当。**概ね準拠**。

→ 予備調査では大きな違反は未検出。本ブランチでは全ファイル精読で取りこぼしを確認する。
