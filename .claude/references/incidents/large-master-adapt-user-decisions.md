# Large master-adapt: defer naming and scope decisions to the user

## Context

- PR: PR169 (`integrate-guard-kit-into-workspace`)
- Date: 2026-05-30

## What happened

PR169 was branched from master at PR164, then sat for some time while PR165 / PR166 / PR167 / PR170 / PR172 all merged into master. By the time the user asked to run `/work-kit:merge`, `git log HEAD..master --oneline` returned ~40 commits including:

- PR172: `plugins/work-kit/` → `plugins/workspace/` rename, env vars `WORK_KIT_*` → `WORKSPACE_*`
- PR167: bumped `work-kit` (now `workspace`) 2.38.0 → 2.39.0 — exactly the version PR169 had also taken
- PR165: removed all `<!-- Generated by ... -->` provenance stamps and the `mark-generated` skill
- PR166: merged py-kit/html-kit/next-kit into dev-kit

`git merge master` produced conflicts in 8 files plus location-relocation prompts for every PR169-added file.

The merge skill's Step 3 says to **adapt autonomously** using a tiebreaker (recency / blast radius / PR purpose / safe-default). But several decisions weren't actually mechanical:

1. **env-var name**: keep `WORK_KIT_GUARD` (matches my PR), or rename to `WORKSPACE_GUARD` (matches the PR172 rename other vars went through)?
2. **scope of the follow-up task** the user mentioned mid-session (configurable protected-branch names): fold into this PR, or hand off to the next one?
3. **whether to proceed at all** given the size of the conflict — abort and reschedule, or push through?

I paused and asked the user explicitly (Q1/Q2/Q3) instead of choosing autonomously. The user picked `WORKSPACE_GUARD`, hand-off-to-next-PR, and "proceed". Adaptation then went cleanly.

## Lesson

The merge skill's "autonomous adapt" assumes the tiebreaker can decide. When master has moved enough that adaptation forces **a new identifier name**, **a scope-of-PR call**, or **an abort/proceed call**, the tiebreaker doesn't apply — those are user preferences, not commit-order facts. Stop and ask 2–4 short questions before running `git merge master`, especially when:

- The master change includes a **rename** that your PR's new identifiers should plausibly follow (env vars, file paths, namespaces)
- Your PR and a master PR landed on the **same version number** and one must re-bump
- The conflict diff is large enough that "safe default = take master" would still leave a non-trivial re-write afterward

It is faster overall — and produces a correct branch the user actually wants — than producing a clean diff that uses a name the user would have renamed anyway.
