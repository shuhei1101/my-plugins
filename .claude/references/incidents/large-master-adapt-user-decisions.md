# 大規模 master 適合: 命名・スコープ判断はユーザーに渡す

## コンテキスト

- PR: PR169（`integrate-guard-kit-into-workspace`）
- 日付: 2026-05-30

## 何が起きたか

PR169 は master の PR164 時点から分岐し、そのまま放置されている間に master へ PR165 / PR166 / PR167 / PR170 / PR172 がマージされていった。ユーザーが `/work-kit:merge` を実行した時点で `git log HEAD..master --oneline` は約 40 コミットを返した。重要なもの:

- PR172: `plugins/work-kit/` → `plugins/workspace/` リネーム、env 変数 `WORK_KIT_*` → `WORKSPACE_*`
- PR167: `work-kit`（現 `workspace`）を 2.38.0 → 2.39.0 にバンプ。PR169 もまさにこの番号にバンプ済みで衝突
- PR165: 全 `<!-- Generated by ... -->` provenance スタンプと `mark-generated` スキル削除
- PR166: py-kit/html-kit/next-kit を dev-kit に統合

`git merge master` の結果、8 ファイルの内容衝突 + PR169 が追加したファイルすべての場所変更プロンプトが発生した。

merge スキルの Step 3 は「タイブレーク順位（新しさ → 影響範囲 → PR目的 → 安全側）に従って自律判断する」となっているが、今回は機械的に決められない判断が複数あった:

1. **env 変数名**: `WORK_KIT_GUARD` のまま（私の PR の命名）か、`WORKSPACE_GUARD` にリネーム（PR172 で他の変数が辿った道）か？
2. **セッション中にユーザーが言及した次タスク**（保護ブランチ名を env で設定可能に）の**スコープ**: この PR に取り込むか、次 PR に handoff するか？
3. **そもそも進めるか**: 衝突規模を考えると中断してリスケすべきか、押し切るか？

私は自律判断せず、ユーザーに 3 つ短い質問（Q1/Q2/Q3）を投げた。ユーザーの回答は `WORKSPACE_GUARD` / 次 PR に handoff / 進めて OK。その後の適合作業はクリーンに完了した。

## 教訓

merge スキルの「autonomous adapt」はタイブレークが決められることを前提にしている。master の変更が以下を**強制する**場合、タイブレークは機能しない — これらはコミット順の事実ではなくユーザーの好みだから:

- master の変更に**リネーム**が含まれ、自分の PR が追加した識別子（env 変数・ファイルパス・ネームスペース）もそれに従うのが自然なケース
- 自分の PR と master の PR が**同じバージョン番号**にバンプし、どちらかが再 bump する必要があるケース
- 衝突 diff が大きすぎて「安全側 = master を取り込み」を選んでも結局大幅な書き換えが必要なケース

`git merge master` を実行する前に 2〜4 個の短い質問を投げる方が、結果的に速い — ユーザーが本当に欲しいブランチに到達できる。「クリーンな diff だが採用したくない命名」を作ってしまうより遥かにマシ。
