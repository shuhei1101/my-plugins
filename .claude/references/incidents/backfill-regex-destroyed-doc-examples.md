# Backfill Regex Stripped Example Snippets Inside Documentation Code Blocks

**Date**: 2026-05-24
**PR**: PR94

## What happened

A one-shot Python script was used to back-fill provenance metadata comments
(`<!-- Generated by ... -->`) into every existing generated file in the repository.
Before inserting the new metadata line, the script removed any pre-existing metadata
line using a regex like:

```python
META_RE = re.compile(r'^(<!-- Generated by [^>]+-->|# Generated by [^\n]+)$', re.M)
new_content = META_RE.sub('', content, count=1)
```

This worked for almost every file, but it broke `mark-generated/SKILL.md` and `SKILL.jp.md`:
both documents contained **example output blocks** demonstrating the metadata format inside
fenced code blocks, like:

````markdown
```
<!-- Generated by claude-kit/skill-creator v3.17.0 -->
<!-- This file is a Japanese mirror... -->
```
````

The regex matched the example line first (because the file had no real metadata at the top yet),
and `count=1` deleted that example line. The result was an empty code block in the documentation.

## Root cause

The regex did not distinguish between
(a) a real metadata comment at the file top, and
(b) an illustrative example shown inside a code block.

Both are syntactically identical lines starting with `<!-- Generated by `.

## Fix

For the two affected files (`mark-generated/SKILL.md` and `.jp.md`), the example output blocks
were rewritten so they do **not** contain the literal `<!-- Generated by ` pattern. Instead the
examples are described in prose (e.g., "Example output: an HTML comment containing
`claude-kit/skill-creator v3.17.0`"). This sidesteps the regex problem permanently.

## Takeaway

When writing a script that mutates files in bulk based on a pattern, be aware that the same
pattern may legitimately appear in documentation, code blocks, or test fixtures. Either:

1. Anchor the pattern to a position that documentation cannot occupy (e.g., "only match if the
   line is among the first N non-blank lines AND not preceded by a fenced code block opener"), or
2. Rewrite docs to describe the pattern in prose rather than reproducing it literally.

The "anchor by position" approach is fragile; the "prose-only docs" approach is robust and the
one applied here.
