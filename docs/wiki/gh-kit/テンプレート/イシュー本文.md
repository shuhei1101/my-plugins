# gh-kit 規約: イシュー本文

Issue 本文の構造ルール・担当セクション一覧・記入テンプレート。

issue-triage が起票直後に **全セクションの骨組み** を作成し、後続モニター（issue-spec）が自分の担当セクションだけ上書き更新する。

**Issue で扱う範囲は「要件レベル」まで**（何を作るか）。設計詳細（UI 設計 / システム方式 / PoC / 実装計画）は **Draft PR + `docs/wiki/`** で扱う。

## 担当セクション一覧

| セクション                  | サブセクション           | 必須or条件                               | 担当モニター               |
| --------------------------- | ------------------------ | ---------------------------------------- | -------------------------- |
| `## 概要`                   | -                        | 必須                                     | issue-triage               |
| `## 背景`                   | -                        | 〃                                       | 〃                         |
| `## 現状`                   | `### 関連実装コード`     | 〃                                       | 〃                         |
| 〃                          | `### 関連テスト`         | 〃                                       | 〃                         |
| 〃                          | `### 関連 Issue/PR`      | 〃                                       | 〃                         |
| 〃                          | `### 関連ドキュメント`   | 〃                                       | 〃                         |
| 〃                          | `### 既存テスト実行結果` | テストが実行可能な場合                   | 〃                         |
| 〃                          | `### 再現手順`           | バグ報告の場合のみ                       | 〃                         |
| `## システム要件（SA）`     | `### 機能要件`           | 〃                                       | issue-spec                 |
| 〃                          | `### 非機能要件`         | 性能/セキュリティ/運用要件がある場合     | 〃                         |
| 〃                          | `### スコープ外`         | 誤解防止のため可能なら書く               | 〃                         |

> **UI 設計 / システム方式設計 / PoC 結果 / 実装計画** 等の設計詳細セクションは Issue 本文では扱わない。


## `## 概要`

**担当:** issue-triage

### 記述例

```markdown
## 概要

ログイン中ユーザーが自身のプロフィール（氏名・自己紹介・アバター画像）を編集できる画面を追加する。
```

### 補足

- ユーザーが起票時に書いた目的文を 1〜3 行に整形する（誤字脱字・改行整理のみ）
- **ユーザー入力の範囲内に留める**: 仕様や実装方針を推測で書き加えない
- 「{誰} が {何} をできるようになる」というユーザーストーリー形の表現が望ましい
- 結論（解決したい問題・実現したい状態）から書き出す。背景や経緯は次の `## 背景` に書く

## `## 背景`

**担当:** issue-triage

### 記述例

```markdown
## 背景

現在プロフィールは管理者画面からしか更新できず、ユーザーから「自分で更新したい」という要望が複数件寄せられている（Issue#102, Issue#145）。
```

### 補足

- ユーザーが起票時に書いた経緯文を整形する（誤字脱字・改行整理のみ）
- **ユーザー入力の範囲内に留める**: 観測されていない原因推定や、仕様への意見は書かない
- 起票に至った経緯・きっかけ・問題の発生状況など「なぜこの Issue が必要になったか」を書く
- 関連する既存 Issue/PR / 顧客要望 / 障害発生日時 などがあれば明示する
- `## 概要` と重複しない（概要が「何を実現したいか」、背景は「なぜ必要か」）


## `## 現状`

**担当:** issue-triage（コードベース調査結果）

### `### 関連実装コード`

**概要:**

Issue が言及する領域のコードベースを調査し、現状の実装がどこにあるかを整理する。
既存実装の所在・役割を把握することで、後続フェーズが「何を変えるか」「どこに追加するか」の判断材料を持てるようにする。

**記述例:**

```markdown
### 関連実装コード

| No | ファイル                   | メソッド   | 概要                 | 補足                 |
| -- | -------------------------- | ---------- | -------------------- | -------------------- |
| 1  | `pages/profile/view.html`  | -          | プロフィール表示画面 | 編集機能はここに追加 |
| 2  | `api/users/{id}.py`        | `get_user` | GET エンドポイント   | PUT は未実装         |
| 3  | `services/user_service.py` | `get_user` | ユーザー取得処理     | `update_user` なし   |
```

**ファイル列:**
- リポジトリルートからの相対パスで書く

**メソッド列:**
- ファイル全体への参照ならメソッド列は `-`
- 特定メソッドなら関数名・メソッド名をそのまま記載

**概要列:**
- そのファイル / メソッドの役割を 1 行で要約

**補足:**
- 領域別コードベース調査の結果を表で整理

### `### 関連テスト`

**概要:**

`### 関連実装コード` で洗い出した実装に紐づくテストを調査して整理する。
既存テストが何をカバーしているか・していないかを可視化し、後続フェーズが「どのテストを変更すべきか」「どこに新規テストが必要か」を判断する素材にする。

**記述例:**

```markdown
### 関連テスト

| No | 分類 | ファイル                              | メソッド        | 概要                  | 補足           |
| -- | ---- | ------------------------------------- | --------------- | --------------------- | -------------- |
| 1  | E2E  | `tests/e2e/profile_view.spec.ts`      | -               | 表示のみカバー        | 編集テストなし |
| 2  | 単体 | `tests/services/test_user_service.py` | `test_get_user` | get_user の単体テスト | -              |
```

**分類列:**
- `単体`: 単一の関数・クラス・メソッドを外部依存なしで検証するテスト
- `結合`: 複数のモジュールが連携するユースケースを通しで検証するテスト（外部依存は Mock 注入）
- `E2E`: ユーザー操作を起点に画面 → API → DB → 画面復帰までの一連動作を検証するテスト
- `外部疎通`: 外部サービス（LLM / 決済 / メール送信 等）への実通信が成立するかを検証するテスト（料金発生のためユーザー手動実行のみ）

**メソッド列:**
- ファイル全体実行ならメソッド列は `-`

**補足:**
- 「カバーしていない領域」は補足列で明示する（ギャップを後続フェーズに引き継ぐ）

### `### 関連 Issue/PR`

**概要:**

同じキーワード・同じ機能・同じファイルに関わる既存 Issue / PR を検索して整理する。
重複起票の発見、過去判断の参照、影響を受ける可能性のある直近 merged PR の警告を後続フェーズに引き継ぐ。

**記述例:**

```markdown
### 関連 Issue/PR

| No | 番号    | 状況   | 概要                           | 補足                 |
| -- | ------- | ------ | ------------------------------ | -------------------- |
| 1  | Issue#102    | open   | 同じ要望、本 Issue に集約      | 集約後 close 予定    |
| 2  | Issue#145    | closed | 過去の同様要望（実装見送り）   | 当時の判断理由を参考 |
| 3  | PR#220 | merged | `user_service.py` を直近で改修 | 影響注意             |
```

**番号列:**
- Issue は `Issue#xx`、PR は `PR#xx` で区別

**状況列:**
- `open` / `closed` / `merged` のいずれか

**補足:**
- `related-issue-finder` / `related-pr-finder` の戻り値を整形
- 過去にバグを埋め込んだ可能性のある merged PR は補足列に「影響注意」と明記

### `### 関連ドキュメント`

**概要:**

Issue の領域に関係する既存ドキュメント（Wiki / CLAUDE.md / Rules / agents）を洗い出して整理する。
後続の `pr-doc-plan` フェーズが「どのドキュメントを更新すべきか」を判断する素材になる。

**記述例:**

```markdown
### 関連ドキュメント

| No | 分類 | ページ                     | 概要                          | 補足                 |
| -- | ---- | -------------------------- | ----------------------------- | -------------------- |
| 1  | Wiki | `設計図/モジュール構成/ユーザー.md`   | User 周辺のクラス構造         | 更新対象             |
| 2  | 〃   | `設計図/バックエンド結合/README.md`   | 既存エンドポイント一覧（PUT 追加対象） | PUT 追加で更新が必要 |
| 3  | 〃   | `設計図/ER図/ユーザー.md`             | users テーブル定義            | bio カラム追記が必要 |
```

**分類列:**
- `Wiki` / `CLAUDE.md` / `Rules` / `agents` など

**補足:**
- 本 Issue で更新が必要そうなら補足列に明記（後続 `pr-doc-plan` の素材になる）

### `### 既存テスト実行結果`

**概要:**

`### 関連テスト` で洗い出したテストを実際に走らせた結果を記録する。
バグ報告 Issue では再現確認の証拠に、新機能追加 Issue では「現状動作する範囲」を把握して回帰検知の基準にする。

**記述例:**

```markdown
### 既存テスト実行結果

| No | 分類 | ファイル                              | メソッド        | 概要                 | 結果 | 補足               |
| -- | ---- | ------------------------------------- | --------------- | -------------------- | ---- | ------------------ |
| 1  | E2E  | `tests/e2e/profile_view.spec.ts`      | -               | プロフィール表示 E2E | ✅   | 編集テストは未作成 |
| 2  | 単体 | `tests/services/test_user_service.py` | `test_get_user` | get_user 単体テスト  | ✅   | -                  |
```

**分類列:**
- `単体` / `結合` / `E2E` / `外部疎通` のいずれか

**メソッド列:**
- ファイル全体実行ならメソッド列は `-`

**結果列:**
- `✅`（pass）/ `❌`（fail）。落ちた場合は補足列にエラー要約

**補足:**
- テストが実行可能な場合のみ記入
- 外部疎通テストは料金発生のため自動実行禁止。手動実行が必要な旨を補足列に書くに留める

### `### 再現手順`

**概要:**

バグ報告 Issue で「どう操作すれば問題が再現するか」「期待動作と実際の動作のギャップ」を記録する。
後続の修正フェーズで再現確認・回帰テスト作成の基準になる。

**記述例:**

```markdown
### 再現手順

1. ログイン後、`/profile/edit` に遷移
2. 自己紹介欄に 600 文字を入力
3. 保存ボタンをクリック

期待: バリデーションエラー表示
実際: 500 Internal Server Error
```

**補足:**
- **バグ報告の場合のみ記入**。新機能追加 Issue では省略
- 番号付き箇条書きで再現手順、末尾に「期待 / 実際」を明示
- 再現しなかった場合もその旨を記録する（環境差・キャッシュなどユーザー環境の問題かもしれない）

## `## システム要件（SA）`

**担当:** issue-spec

### `### 機能要件`

**概要:**

システムが「何ができるか」を機能単位で列挙する。
エラーハンドリング・バリデーション・レスポンシブ対応の有無もここに含める。
後続の実装・テスト計画の基本要件になる。

**記述例:**

```markdown
### 機能要件

| No | カテゴリ         | 要件                                                         | 補足                            |
| -- | ---------------- | ------------------------------------------------------------ | ------------------------------- |
| 1  | 編集機能         | ログイン中ユーザーが氏名・自己紹介・アバター画像を編集できる | -                               |
| 2  | バリデーション   | アバター画像は 5MB 以下に制限                                | クライアント側で事前チェック    |
| 3  | エラー表示       | 5MB 超のアバター画像はエラーメッセージを表示                 | 保存ボタン押下前にブロック      |
| 4  | 状態表示         | 保存処理中はボタンが無効化されインジケーターを表示           | 二重送信防止も兼ねる            |
| 5  | レスポンシブ対応 | デスクトップ・タブレット・スマホで利用可能                   | ブレークポイント 768px / 1024px |
```

**カテゴリ列:**
- 例: `編集機能` / `閲覧機能` / `バリデーション` / `エラー表示` / `状態表示` / `レスポンシブ対応` など
- 同カテゴリが連続する行は `〃` で省略

**補足:**
- **エラーハンドリング・バリデーションも機能要件に含める**
- 1 要件 1 行。条件分岐や複雑なフローは補足列または別 No に分割

### `### 非機能要件`

**概要:**

機能要件以外の品質要件（性能・セキュリティ・運用 など）のうち、本 Issue で守るべきものを列挙する。
数値基準を明示することで、後続フェーズが計測可能なテスト・設計判断に使える素材にする。

**記述例:**

```markdown
### 非機能要件

| No | カテゴリ     | 要件                                       | 補足                  |
| -- | ------------ | ------------------------------------------ | --------------------- |
| 1  | 性能         | 保存処理は 3 秒以内にレスポンス            | 95 パーセンタイル基準 |
| 2  | セキュリティ | 自分以外のユーザーのプロフィールは編集不可 | 認可チェック必須      |
```

**カテゴリ列:**
- 例: `性能` / `セキュリティ` / `運用` など

**補足:**
- 性能 / セキュリティ / 運用 などの品質要件のうち **当てはまるものがある時のみ** 記入
- 数値で測れる基準を補足列に明記（「速い」「重い」など主観表現は避ける）

### `### スコープ外`

**概要:**

本 Issue では実装しない項目を明示する。誤解で実装スコープが膨らむのを防ぎ、関係者の期待値を揃える。
将来やる予定があれば後続 Issue 起票候補としても活用する。

**記述例:**

```markdown
### スコープ外

| No | 項目                 | 理由                             | 補足              |
| -- | -------------------- | -------------------------------- | ----------------- |
| 1  | パスワード変更       | 別フロー（メール認証込み）が必要 | 別 Issue 起票予定 |
| 2  | メールアドレス変更   | メール認証フローが必要           | 別 Issue 起票予定 |
| 3  | プロフィール公開設定 | 将来要件、本リリース対象外       | -                 |
```

**理由列:**
- なぜ今回スコープ外なのかを 1 行で説明

**補足:**
- 「今回はやらない」項目を明示することで実装スコープの膨張を防ぐ
- 将来やる予定なら補足列に別 Issue 起票候補を書く
