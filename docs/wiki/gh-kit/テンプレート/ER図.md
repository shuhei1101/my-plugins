# gh-kit 規約: ER 図

DB スキーマを一望できるドキュメント。
Mermaid `erDiagram` で物理スキーマを図示し、各テーブルの論理名・カラム・型・制約を表で記述する。

「テーブル名や論理名で他ドキュメントから参照したい」「カラム制約を実装時に確認したい」のどちらにも答えられる単一の SoT を目指す。

ファイル名は `ER図.md`（固定）。新規 DB ・新規テーブルを追加するたびに更新する。

## 担当セクション一覧

| No | セクション         | サブセクション                                | 必須or条件                                    | 担当       | 補足                                          |
| -- | ------------------ | --------------------------------------------- | --------------------------------------------- | ---------- | --------------------------------------------- |
| 1  | `## 概要`          | -                                             | 必須                                          | issue-arch | -                                             |
| 2  | `## ER 図`         | -                                             | 必須                                          | 〃         | Mermaid `erDiagram` 1 枚                      |
| 3  | `## テーブル一覧`  | -                                             | 必須                                          | 〃         | 論理名 / 物理名 / 概要 / 主キー / レコード規模 |

## `冒頭リード`

### 記述例

```markdown
# ER 図

このプロジェクトの DB スキーマ全体図と、各テーブル詳細。

論理名はドキュメント・UI・口頭で使い、物理名（snake_case）はマイグレーション / SQL で使う。
両者の対応はこのページでのみ正規化して管理する。
```

### 補足

- DB が複数ある場合は `ER図_{DB名}.md` でファイルを分けて、本ページは全 DB の索引にしてもよい
- 論理名 / 物理名の対応はこのページに必ず集約（コード内 / 他 Wiki でブレないように）

## `## 概要`

### 記述例

```markdown
## 概要

PostgreSQL 16 で運用。論理名は日本語、物理名は `snake_case` で統一。

主な集約: ユーザ / 投稿 / コメント / 通知 の 4 ドメイン。
全テーブルに `id` (UUID v7) / `created_at` / `updated_at` の共通カラムを持つ。
```

### 補足

- DBMS の種類とバージョン（PostgreSQL 16 / MySQL 8 / SQLite 等）
- 物理名の命名規則（snake_case / lowerCamelCase など）
- 全テーブル共通カラム（id / created_at / updated_at / deleted_at など）
- ドメイン分割が複数ある場合はその概略

## `## ER 図`

### 記述例

````markdown
## ER 図

```mermaid
erDiagram
  ユーザ ||--o{ 投稿 : "投稿する"
  ユーザ ||--o{ コメント : "コメントする"
  投稿 ||--o{ コメント : "コメントされる"
  ユーザ ||--o{ 通知 : "通知される"

  ユーザ {
    uuid ID PK
    string メール UK
    string 表示名
    timestamptz 作成日時
    timestamptz 更新日時
  }

  投稿 {
    uuid ID PK
    uuid ユーザ.ID FK
    string タイトル
    text 本文
    timestamptz 作成日時
    timestamptz 更新日時
  }

  コメント {
    uuid ID PK
    uuid 投稿.ID FK
    uuid ユーザ.ID FK
    text 本文
    timestamptz 作成日時
  }
```
````

### 補足

- Mermaid `erDiagram` 1 枚に全テーブルを載せる（一望性を優先）
- テーブル数が 20 を超えるとレンダリングが崩れやすい → ドメインごとに `ER図_{ドメイン}.md` に切り出してよい
- リレーション記号: `||--o{` = 1:N / `||--||` = 1:1 / `}o--o{` = N:M
- **論理名（日本語）で記述する** — テーブル名・カラム名ともに（読み手が業務語彙で理解しやすいため）
- **外部キーは `{参照先テーブル名}.ID` 形式** で書く（例: `ユーザ.ID` / `投稿.ID`）— 参照先が一目で分かるようにする

## `## テーブル一覧`

### 記述例

```markdown
## テーブル一覧

| No | 論理名     | 物理名          | 概要                       | 主キー | レコード規模 | 補足 |
| -- | ---------- | --------------- | -------------------------- | ------ | ------------ | ---- |
| 1  | ユーザ     | `users`         | 認証単位のアカウント       | `id`   | ～10 万      | -    |
| 2  | 投稿       | `posts`         | ユーザの投稿               | `id`   | ～100 万     | -    |
| 3  | コメント   | `comments`      | 投稿へのコメント           | `id`   | ～500 万     | -    |
| 4  | 通知       | `notifications` | ユーザ向け通知             | `id`   | ～1000 万    | -    |
```

### 補足

**論理名列:**
- 日本語名。UI・ドキュメント・口頭で参照する公式名

**物理名列:**
- DB の実テーブル名（snake_case）。マイグレーション / SQL でそのまま使う

**概要列:**
- そのテーブルが何を表すかを 1 行で

**主キー列:**
- カラム名。複合キーなら `(col_a, col_b)`

**レコード規模列:**
- 想定行数のオーダー（`～10 万` / `～100 万` / `～10 億`）
- インデックス戦略・パーティショニング判断の材料になる

**補足:**
- 順序は ER 図の依存順 or ドメイン順に揃える
- 廃止テーブルは削除し、履歴は git log に任せる

## `## {テーブル名}`

実テーブル 1 つにつき 1 つの H2。論理名 + 物理名を見出しに併記する。

### 記述例

````markdown
## ユーザ (`users`)

認証単位となるアカウント情報を保持する。

### カラム

| No | 論理名       | 物理名         | 型              | NOT NULL | 既定                   | 説明                       | 例                      | 補足                          |
| -- | ------------ | -------------- | --------------- | -------- | ---------------------- | -------------------------- | ----------------------- | ----------------------------- |
| 1  | ID           | `id`           | `uuid`          | ◯        | `gen_random_uuid()`    | 主キー（UUID v7）          | `018f8a...`             | PK                            |
| 2  | メール       | `email`        | `varchar(255)`  | ◯        | -                      | ログイン用メールアドレス   | `taro@example.com`      | UK / RFC 5322                 |
| 3  | 表示名       | `display_name` | `varchar(50)`   | ◯        | -                      | UI で表示される名前        | `太郎`                  | 1〜50 文字                    |
| 4  | ステータス   | `status`       | `text`          | ◯        | `'active'`             | アカウント状態             | `"active"`              | `active` / `suspended` / `deleted` |
| 5  | 作成日時     | `created_at`   | `timestamptz`   | ◯        | `now()`                | レコード作成日時 (UTC)     | `2026-06-27T05:00:00Z`  | -                             |
| 6  | 更新日時     | `updated_at`   | `timestamptz`   | ◯        | `now()`                | レコード更新日時 (UTC)     | `2026-06-27T05:00:00Z`  | trigger で自動更新            |

### インデックス

| No | 名前                  | カラム      | 種別     | 補足                  |
| -- | --------------------- | ----------- | -------- | --------------------- |
| 1  | `users_email_key`     | `email`     | UNIQUE   | ログイン引き当て用    |
| 2  | `users_created_at_ix` | `created_at`| BTREE    | 新規ユーザ一覧の並び替え |

### 補足

- パスワードハッシュは別テーブル `user_credentials` に切り出して保存（このテーブルは持たない）
- 物理削除は禁止。`status='deleted'` で論理削除し、90 日後に別バッチで物理削除
````

### 補足

**カラム表の論理名 / 物理名列:**
- 論理名は日本語、物理名は snake_case
- ドキュメント・口頭は論理名、SQL・マイグレーションは物理名

**カラム表の型列:**
- DBMS のネイティブ型（PostgreSQL なら `uuid` / `varchar(N)` / `timestamptz` / `jsonb` 等）

**カラム表の NOT NULL 列:**
- 必須なら `◯`、NULL 許容なら `-`

**カラム表の既定列:**
- `gen_random_uuid()` / `now()` / リテラル値。なしは `-`

**カラム表の説明列:**
- そのカラムの業務的な意味を 1 行で

**カラム表の補足列:**
- 制約（PK / FK / UK / CHECK）、enum 値の選択肢、計算ロジック、関連 trigger など

**enum 値の書き方:**
- 型列は `text` のままで、補足列に `'a' / 'b' / 'c'` 形式で列挙し各値の意味も併記

**インデックス表:**
- PK / UK の重複は書かない（カラム表の補足で済む）
- 検索クエリで使う追加インデックスのみ列挙
- 名前は実 DB と一致させる（`{table}_{column}_{kind}` 形式）

**サブセクションの省略:**
- インデックスがカラム表の制約だけで十分なら `### インデックス` は省略可
- 業務的な特殊運用がないテーブルは `### 補足` も省略可

**補足:**
- 論理名 / 物理名はこのページが唯一の SoT。他 Wiki / コードコメントから「定義はここ」と参照する
- 物理名のリネームは破壊的変更扱い → マイグレーション計画とセットで本ページも同時更新
- 全テーブルに `id` / `created_at` / `updated_at` の 3 共通カラムを必ず含める
