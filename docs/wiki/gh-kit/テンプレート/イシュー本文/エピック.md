# gh-kit テンプレート: エピック

`layer:epic` が付いた Issue の本文書式。
機能全体（複数ユースケース横断）の親 Issue で使う。

epic では **機能全体の設計成果物（シナリオ設計書）** を作り、複合ユースケースの E2E テストの元にする。

## 担当セクション一覧

| No | セクション              | サブセクション | 必須or条件               | 担当                                                    |
| -- | ----------------------- | -------------- | ------------------------ | ------------------------------------------------------- |
| 1  | `## 前提条件`           | -              | 依存 Issue/PR がある場合 | issue-triage                                            |
| 2  | `## 概要`               | -              | 必須                     | issue-triage                                            |
| 3  | `## 背景`               | -              | 〃                       | 〃                                                      |
| 4  | `## ユーザー視点要件`   | -              | 〃                       | issue-triage が下案、ユーザー承認後に確定               |

## `## 前提条件`

### 記述例

```markdown
## 前提条件

| No | 種類    | 対象                                | 状態   | 補足                                     |
| -- | ------- | ----------------------------------- | ------ | ---------------------------------------- |
| 1  | Issue   | #52（認証基盤刷新エピック）         | 未完了 | 完了後に本 Issue を進行可能              |
| 2  | PR      | #180（Better Auth 導入）            | merged | -                                        |
```

### 補足

- **依存する Issue / PR がない場合は「なし」と記載**
- 種類列: `Issue` / `PR` / `外部（会議・調査結果 等）` のいずれか
- 状態列: `未完了` / `完了` / `merged` / `open` などを実状に応じて
- 未完了の前提がある間は本 epic は着手不可（`issue-triage` が assignee をユーザーに戻して待機）

## `## 概要`

### 記述例

```markdown
## 概要

ログイン中ユーザーが自身のプロフィール（氏名・自己紹介・アバター画像）を編集・閲覧・削除できる機能を追加する。
```

### 補足

- 機能全体（複数ユースケース横断）を 1〜3 行でまとめる
- **ユーザー入力の範囲内に留める**（推測・実装方針は書かない）
- 「{誰} が {何} をできるようになる」というユーザーストーリー形が望ましい

## `## 背景`

### 記述例

```markdown
## 背景

現在プロフィールは管理者画面からしか更新できず、ユーザーから「自分で更新したい」という要望が Issue#102 / Issue#145 として複数件寄せられている。
```

### 補足

- 起票に至った経緯・きっかけを整形（ユーザー入力の範囲内）
- 関連する既存 Issue / 顧客要望 / 障害発生日時があれば明示
- 概要と重複しない（概要は「何を実現したいか」、背景は「なぜ必要か」）

## `## ユーザー視点要件`

### 記述例

```markdown
## ユーザー視点要件

| No | カテゴリ         | 要件                                                        | 補足                       |
| -- | ---------------- | ----------------------------------------------------------- | -------------------------- |
| 1  | 編集             | 自身のプロフィール項目を編集できる                          | 氏名 / 自己紹介 / 画像     |
| 2  | 閲覧             | 自身のプロフィールを閲覧できる                              | -                          |
| 3  | 削除             | アバター画像を削除できる                                    | -                          |
| 4  | 通知             | 保存失敗時にエラーが表示される                              | -                          |
| 5  | セキュリティ     | 他ユーザーのプロフィールは編集できない                      | -                          |
| 6  | 性能             | 保存操作は 3 秒以内にフィードバックが返る                   | -                          |
| 7  | 対応環境         | デスクトップ・タブレット・スマホで利用可能                  | -                          |
```

### 補足

**カテゴリ列:**
- 機能側（編集 / 閲覧 / 削除 / 通知 等）と非機能側（セキュリティ / 性能 / 対応環境 等）の両方を扱う
- 実装側の詳細（バリデーション数値・ライブラリ選定 等）は subsystem 側で扱うのでここでは書かない

**要件列:**
- **ユーザー視点の 1 文** で書く（「{ユーザー} が {アクション} できる / される」）
- 実装用語（API / DB カラム / コンポーネント名）を避ける

**補足:**
- 1 行 = 1 要件。条件分岐は補足列 or 別 No に分割
- ここが epic 直下の docs task「シナリオ設計書」と story 起票の元になる
