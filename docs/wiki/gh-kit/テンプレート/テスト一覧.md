# gh-kit テンプレート: テスト一覧

プロジェクトの **既存テストの網羅状況** をテスト種別ごとにまとめる書式。
設計ドキュメント（結合 / シナリオ）に対して **実装テストコードが存在するか** を対応表で示す。

トリアージ時に「このエンドポイント / 画面 / シナリオを再現できるテストがあるか」を高速に判断するために使う。

ファイル名は `テスト一覧.md`（固定）。新規テスト追加 / 削除のたびに更新する。

## ファイル構成

`docs/wiki/テスト/テスト一覧.md`（`テスト` 分類フォルダ配下、1 ファイル）。

| -- | -------------------------- | ------------------ | -------- | ---------------------------------------------- |

| 7  | `## 外部疎通テスト`         | 外部 API 利用時   | 〃       | 外部API × 実装外部疎通テストコード                |

## `冒頭リード`

### 記述例

```markdown
# テスト一覧

プロジェクトの既存テストの網羅状況。
設計ドキュメント（結合 / シナリオ / モジュール構成）ごとに、実装テストコードの有無と場所を対応表で管理する。

- **設計** 列: `docs/wiki/設計図/` 配下の該当ドキュメントへのリンク
- **実装** 列: リポジトリ内のテストコードのパス（未実装なら `-`）
```

### 補足

- 「設計と実装の対応」を確認する用途と明記
- 実装未着手のドキュメントも表に含める（未実装は `-` で可視化）

```markdown
| No | 主要画面           | シナリオ                            | 設計                                                                           | 実装                                                            | 補足                     |

| 1  | ダッシュボード画面 | 新規ユーザー登録から初回ログイン    | [新規ユーザー登録から初回ログイン](../設計図/シナリオ/新規ユーザー登録から初回ログイン.md) | `tests/e2e/onboarding/signup-to-first-login.spec.ts`            | -                        |

| 3  | 通知一覧画面       | タスク完了から通知配信              | [タスク完了から通知配信](../設計図/シナリオ/タスク完了から通知配信.md)         | `tests/e2e/notification/task-complete.spec.ts`                  | -                        |
```

### 補足

**カラム構成:**
`No / 主要画面 / シナリオ / 設計 / 実装 / 補足`（6 列）

**主要画面 / シナリオ 列:**
- `設計図/シナリオ/README.md` の一覧と揃える

**設計列:**
- `設計図/シナリオ/{論理名}.md` への相対リンク

**実装列:**
- リポジトリ内のテストコードのパス（例: `tests/e2e/*.spec.ts`）
- 未実装なら `-`

**運用:**
- シナリオドキュメントを追加したら本表にも 1 行追加（未実装で OK）
- テストコード実装 / 削除時は本表を必ず同期

## `## 単体テスト（フロント）`

### 記述例

```markdown
## 単体テスト（フロント）

| No | 分類     | 対象           | 設計                                                                        | 実装                                                    | 補足                        |
| -- | -------- | -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------- | --------------------------- |
| 1  | 共通     | `formatDate`   | [共通](../設計図/モジュール構成/共通.md)                                    | `tests/unit/front/shared/format-date.spec.ts`           | -                           |
| 2  | フォーム | `useSigninForm` | [認証](../設計図/モジュール構成/認証.md)                                   | -                                                       | 結合でカバー、単体不要判断  |
```

### 補足

**カラム構成:**
`No / 分類 / 対象 / 設計 / 実装 / 補足`（6 列）

**分類列:**
- モジュール構成の分類と揃える（`共通` / `認証` / `フォーム` 等）
- 同じ分類が連続する場合は `〃` で省略

**対象列:**
- 単体テスト対象のクラス名 / 関数名 / フック名（モジュール構成と一致）

**設計列:**
- `設計図/モジュール構成/{分類}.md` への相対リンク

**実装列:**
- リポジトリ内のテストコードのパス（例: `tests/unit/front/**/*.spec.ts`）
- 未実装なら `-`

**運用:**
- 全関数 / メソッドを網羅する必要はない（結合テストで十分カバーされるものは補足で「結合でカバー、単体不要判断」等と明記）
- ロジックが複雑・単体で検証したい対象のみ表に載せる

## `## 外部疎通テスト`

### 記述例

```markdown
## 外部疎通テスト

| No | 関数名          | 対象 API | 設計                                                                      | 実装                                              | 補足                            |
| -- | --------------- | -------- | ------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------- |
| 1  | `openaiChat`    | OpenAI   | [integrations](../設計図/モジュール構成/integrations.md)                  | `tests/external/openai/chat.spec.ts`              | 料金: $0.01/回                  |
| 2  | `slackNotify`   | Slack    | 〃                                                                        | `tests/external/slack/notify.spec.ts`             | 副作用: `#test-notify` に投稿   |
| 3  | `sendgridSend`  | SendGrid | 〃                                                                        | -                                                 | 未実装 / 副作用: 実メール送信   |
```

### 補足

**カラム構成:**
`No / 関数名 / 対象 API / 設計 / 実装 / 補足`（6 列）

**関数名列:**
- 対象ラッパー関数名（モジュール構成側の `### 疎通テスト` と揃える）

**対象 API 列:**
- 外部 API 名（`OpenAI` / `Slack` / `SendGrid` 等）
- 同じ API が連続する場合は `〃` で省略（ここでは関数単位で並ぶため、`設計` 列の方に `〃` が出やすい）

**設計列:**
- **モジュール構成のラッパーファイル**（例: `設計図/モジュール構成/integrations.md`）への相対リンク
- そのファイル内の `### 疎通テスト` 表で確認内容の詳細を管理する
- （外部 API 自体のリファレンスは `外部API/{API名}.md` を参照、設計列とは別軸）

**実装列:**
- リポジトリ内の外部疎通テストコードのパス（例: `tests/external/**/*.spec.ts`）
- 未実装なら `-`

**補足列:**
- **料金 / 副作用の目安を必ず書く**（`料金: $0.01/回` / `副作用: 実メール送信` 等）
- モジュール構成側の `### 疎通テスト` 表の補足列と揃える
- 実行時に何が起こるかが分かる状態を保つ

**運用:**
- 通常の CI では実行しない（誤実行防止フラグ `--run-external` 必須）
- 詳細な実行方法は `テスト実行方法.md` の `## 外部疎通テスト` を参照
