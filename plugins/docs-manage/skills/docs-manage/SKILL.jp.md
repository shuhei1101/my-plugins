# docs-manage — プロジェクトドキュメント & QA 駆動の意思決定管理

プロジェクトのドキュメントを管理する：構造の初期化・未決定の設計質問の追跡・決定の記録・仕様書全体で情報の単一ソースを維持する。

---

## 概要

ドキュメントは `docs/` 配下の4つのエリアに整理する：

```
docs/
├── specs/           ← 設計・仕様ドキュメント（フラット配置・サブフォルダなし）
│   └── Home.md      ← ナビゲーションハブ（全仕様書へのリンク集）
├── qa.md            ← 未決定の設計質問（QA-XXX 連番）
├── qa_history.md    ← 決定済み QA の履歴ログ（追記型）
└── incident.md      ← インシデントログ（INC-XXX 連番、任意）
```

**不変ルール：** 1 つの事実は 1 つのドキュメントで管理する。書き込み前は必ず重複チェックを行う。

---

## 作業内容

### ステップ1: 操作を特定する

#### 条件

- 常に — 他の何より先に実行する

#### 処理内容

1. ユーザーが何を求めているかを判断する：

   | ユーザーの要求 | 移動先 |
   |---|---|
   | 新規プロジェクトまたは `docs/` が存在しない | ステップ2（初期化） |
   | 未決定事項・設計上の疑問点を挙げたとき | ステップ3（QA 追加） |
   | 既存 QA エントリの決定を確認したとき | ステップ4（QA クローズ） |
   | 仕様書の追加・削除・リネームが発生したとき | ステップ5（Home.md 更新） |
   | 仕様書に情報を書き込む必要があるとき | ステップ6（重複チェック + 書き込み） |

→ 適切なステップへ進む

#### 出力

- 操作タイプを確認済み

---

### ステップ2: ドキュメント構造の初期化

#### 条件

- `docs/` が存在しない、またはユーザーが新規プロジェクトのドキュメントを整備したいとき

#### 入力

- プロジェクトルートディレクトリ

#### 処理内容

1. `docs/` が既に存在するか Glob でスキャンして確認する。
2. `docs/specs/Home.md` を作成または更新する — 全仕様書へのリンク集となるナビゲーションハブ。
3. `docs/qa.md` を作成する — 未決定の設計質問（まだなければ空でよい。テンプレートは参考資料参照）。
4. `docs/qa_history.md` を作成する — 決定済み QA の履歴（まだなければ空でよい）。
5. 必要に応じて `docs/incident.md` を作成する — インシデントログ（プロジェクトが必要とする場合のみ）。
6. プロジェクトルートの `README.md` に docs へのリンクを追加する（既存内容は保持）。

`docs/` が既に存在する場合：既存ファイルを差分検出して上書きせずにマージを提案する。

→ ファイルの書き込みはステップ6へ進む

#### 出力

- `docs/specs/Home.md`・`docs/qa.md`・`docs/qa_history.md` が作成または確認済み

---

### ステップ3: 新しい QA エントリを追加する

#### 条件

- ユーザーが未決定事項・設計上の疑問点を挙げたとき

#### 入力

- ユーザーの未決定事項の説明

#### 処理内容

1. 次の QA 番号を決める：
   - `docs/qa.md` と `docs/qa_history.md` の両方を Grep で `QA-(\d+)` 検索する
   - 次の番号 = 見つかった最大値 + 1。一度発行した番号は再利用しない
2. 参考資料の QA エントリテンプレートを使って下書きを作成する。
3. QA エントリの必須ルール：
   - `推奨方式` フィールドは**必須** — 必ず 1 つの案を選び 1〜2 行の理由を書く。「ユーザーが判断」などの回避は禁止
   - 見出しはリテラル `未決定` で終わること：`## QA-XXX: {タイトル} 未決定`
   - 後回し（後で決める）のエントリには `（後で）` を付ける：`未決定（後で）`
   - 複数のサブ質問がある場合 → `### QA-XXX-1`、`### QA-XXX-2` のサブセクションに分割する
4. **新規追加は必ず `docs/qa.md` の一番下に追記する**（時系列順を保つため）。

→ ファイルの書き込みはステップ6へ進む

#### 出力

- 新しい QA エントリが `docs/qa.md` の末尾に追記済み

---

### ステップ4: QA エントリをクローズする

#### 条件

- ユーザーが既存の QA エントリの決定を確認したとき

#### 入力

- QA 番号またはタイトル
- 採用した選択肢と理由

#### 処理内容

1. 番号またはタイトルで `docs/qa.md` の対象 QA エントリを特定する。
2. 決定内容を書き込む先のマスター仕様書を決定する（参考資料のマスタードキュメント原則参照）。
3. 書き込み前に重複チェック（ステップ6）を実行する。
4. 3 つの書き込みをバックグラウンドのサブエージェントに委譲する（並列実行）：
   - **A** — 対象の仕様書（`docs/specs/` 内）に決定内容を反映する。
   - **B** — `docs/qa.md` から対象 QA ブロックを丸ごと削除する。残余・「決定済み」マーカーは一切残さない。
   - **C** — 参考資料の QA 履歴エントリテンプレートを使って `docs/qa_history.md` の末尾に追記する。
5. 新しい仕様書が作成された場合は `docs/specs/Home.md` のリンクを更新する。

→ ファイルの書き込みはステップ6へ進む

#### 出力

- 仕様書に決定内容が反映済み、qa.md から QA エントリが削除済み、qa_history.md に履歴エントリが追記済み

#### 補足

##### 禁止事項

- `qa_history.md` にだけ書いて対象の仕様書を更新しない — 両方を必ずセットで更新する

---

### ステップ5: Home.md を更新する

#### 条件

- `docs/specs/` 内で仕様書が追加・削除・リネームされたとき

#### 入力

- `docs/specs/` ディレクトリの現在の状態

#### 処理内容

1. `docs/specs/` を Glob スキャンして現在のファイル一覧を取得する。
2. `Home.md` の現在のリンクと差分を検出する。
3. セクション分類の更新を提案する（機能 / アーキテクチャ / API / 参考資料 — プロジェクトに合わせて）。

→ ファイルの書き込みはステップ6へ進む

#### 出力

- 更新済み `Home.md` のリンク一覧が準備済み

---

### ステップ6: 重複チェックして書き込む

#### 条件

- `docs/` への書き込みを行うすべてのステップ

#### 入力

- 書き込み先のファイルと内容

#### 処理内容

1. 対象キーワードで `docs/specs/` 配下を全文 Grep 検索する。
2. 重複が見つかった場合：
   - マスタードキュメント原則（参考資料を参照）を適用して正しい置き場所を決める。
   - マスター以外のドキュメントでは、重複する内容を参照リンクに置き換える：
     ```markdown
     詳細は [マスタードキュメント — セクション名](docs/specs/master.md#section) を参照
     ```
   - マスタードキュメントを更新した後は、古いアンカー名を Grep で検索し、他ドキュメントの参照リンクが古くなっていないか確認する。
3. ファイル書き込みはすべてバックグラウンドのサブエージェントに委譲する（`run_in_background=true`）：
   - メインセッションは判断・分析・ユーザーとのやり取りに集中する。
   - サブエージェントは完了を待たずに並列でファイルを書き込む。
4. 仕様書を更新した後（初回作成時を除く）、ドキュメント末尾の最終更新行を追記または更新する：
   ```markdown
   **最終更新**: YYYY-MM-DD — {変更内容の概要（1行）}
   ```

→ 完了

#### 出力

- ファイル書き込み済み、最終更新行更新済み、重複チェック通過済み

#### 補足

##### 禁止事項

- `docs/specs/` 内にサブフォルダを作らない — すべての仕様書はフラットに同階層に置く
- 同じ事実を複数のドキュメントに書かない — 1 つの仕様は 1 つのドキュメントで管理
- `docs/specs/Home.md` を更新せずに新しい仕様書を追加しない
- 古い情報を残さない — ドキュメントを削除したら `Home.md` のリンクも削除
- 仕様書の本文に TBD / 要検討 / 後で決める マーカーを残さない — QA エントリを起票して、仕様書本文にはリンクのみ置く：`[QA-XXX](docs/qa.md#qa-xxx) で検討中`

## 参考資料

### QA エントリテンプレート（`docs/qa.md` に追記）

```markdown
## QA-XXX: {タイトル} 未決定

**背景**: {なぜこの決定が必要か、関連ドキュメントへのリンク付き}

### QA-XXX-1: {サブ質問のタイトル}

| 案 | 内容 |
|---|---|
| A | {選択肢 A の説明} |
| B | {選択肢 B の説明} |

**推奨方式**: {A / B / C} — {1〜2 行の理由}

**決定したら**: {更新すべき仕様書 / セクション}

---
```

### QA 履歴エントリテンプレート（`docs/qa_history.md` の末尾に追記）

```markdown
## QA-XXX: {タイトル}

- **質問内容**: {元の質問の概要、1〜2 行}
- **決定した内容**: {採用した選択肢と理由の要約、1〜3 行}
- **決定日**: YYYY-MM-DD
- **転記先**: [{ドキュメント名}](docs/specs/{ファイル名}.md#{セクション名})

---
```

### マスタードキュメント原則

| 情報の種類 | マスタードキュメント |
|-----------|---------------------|
| 機能仕様 | `docs/specs/` 内の機能別仕様書 |
| 全機能共通仕様 | `共通仕様.md` または相当するドキュメント |
| 未決定の設計質問 | `docs/qa.md` |
| 決定済みの設計（経緯含む） | 機能別仕様書（qa.md には残さない） |
| API 仕様 | 専用 API 仕様書 |

マスター以外のドキュメントは参照リンクのみ記載 — 内容を重複して書かない。

## プロジェクトへのルール展開

**プロジェクトで初めて使用するとき**、`.claude/rules/specs-work.md` が存在しない場合に作成します：

1. プロジェクトルートで `Glob(".claude/rules/specs-work.md")` を実行して確認。
2. 存在しなければ、`.claude/rules/specs-work.md` を以下の内容で作成：

```markdown
---
paths:
  - "docs/specs/**/*.md"
  - "docs/qa.md"
  - "docs/qa_history.md"
---

# 仕様書 / ドキュメント作業

## マスタードキュメント原則

1つの事実は1つのドキュメントで管理する。仕様書を編集する前に、同じ内容が他にないかを確認する。あれば複製せずリンクする。

## フォルダ構成

- すべての仕様書は `docs/specs/` 直下に配置。**サブフォルダは作らない。**
- `docs/specs/Home.md` はナビゲーションハブ。すべてのドキュメントはここからリンクされている必要がある。

## ドキュメントの追加・削除

- 新しい仕様書を作成 → `docs/specs/Home.md` にリンクを追加する。
- 仕様書を削除 → `docs/specs/Home.md` および相互参照からそのリンクを削除する。

## 未決定事項 → docs/qa.md

仕様書を編集中に未決定の事項が出てきたら、すぐに `docs/qa.md` に QA エントリを起票する。仕様書本文に TBD / 要検討 マーカーを残さない。本文にはリンクのみ置く：`[QA-XXX](docs/qa.md#qa-xxx) で検討中`

## QA エントリのクローズ

1. 対象の仕様書に決定内容を反映する。
2. `docs/qa.md` から対象 QA ブロックを丸ごと削除する。
3. `docs/qa_history.md` の末尾に要約を追記する。
```

3. `.claude/rules-jp/specs-work.md` をスタブとして作成：

```markdown
> **このファイルは日本語ミラーです。本体は `.claude/rules/specs-work.md`。**
```

4. コミット：`git add .claude/rules/ && git commit -m "chore: add specs-work rule"`
