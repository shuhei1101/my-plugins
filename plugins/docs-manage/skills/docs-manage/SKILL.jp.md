# Wiki — プロジェクトドキュメント & Issue 駆動の意思決定管理

## フォルダ構成

```
wiki/
├── home.md            ← ナビゲーションハブ（全ドキュメントへのリンク集）
├── Issues.md          ← 未決定・未解決の Issue 一覧
├── イシュー履歴.md    ← 決定済み Issue の履歴ログ（追記型）
└── {機能名}.md        ← 機能別ドキュメント（フラット配置・サブフォルダなし）
```

**不変ルール：**
- すべてのドキュメントは `wiki/` 直下に配置 — サブフォルダを作らない
- ドキュメントを追加・削除するたびに `home.md` を更新する
- `Issues.md` には未解決の Issue のみ置く。決定したものは `イシュー履歴.md` に移す

---

## Wiki の初期化

新規・既存プロジェクトに wiki を作成する場合：

1. `wiki/` が既に存在するか Glob でスキャンして確認
2. `wiki/home.md` を作成（または更新）— 全ドキュメントへのリンク集
3. `wiki/Issues.md` を作成 — 未解決の Issue（まだなければ空でよい）
4. `wiki/イシュー履歴.md` を作成 — 決定履歴（まだなければ空でよい）
5. プロジェクトルートの `README.md` に wiki へのリンクを追加（既存内容は保持）
6. 必要に応じて `CLAUDE.md` に wiki 運用ルールを追記（ユーザーに確認する）

`wiki/` が既に存在する場合は、既存ファイルを差分検出して上書きせずにマージを提案する。

---

## 新しい Issue の追加

ユーザーが未決定事項・検討事項を挙げたとき：

1. 次の Issue 番号を決める：
   - `wiki/Issues.md` と `wiki/イシュー履歴.md` の両方を Grep で `ISSUE-(\d+)` 検索
   - 次の番号 = 見つかった最大値 + 1。一度発行した番号は再利用しない
2. `wiki/Issues.md` に追記：

```markdown
## ISSUE-XXX: {タイトル}  {未決定 | 検討中 | 保留}

**背景**: {なぜこの Issue が必要か}

**選択肢**:
- **A**: ...
- **B**: ...

**推奨**: {A/B} — {理由}

**関連ドキュメント**: [{ドキュメント名}](wiki/{ファイル名}.md)
```

複数のサブ質問がある大きな Issue は `### ISSUE-XXX-1`、`### ISSUE-XXX-2` で展開する。

---

## Issue の決定

ユーザーが決定を確認したとき：

1. 番号またはタイトルで `Issues.md` の対象 Issue を特定
2. マスタードキュメントを決定する（後述のマスタードキュメント原則を参照）
3. 書き込み前に重複チェックを実行（後述の重複チェックルールを参照）
4. ファイル書き込みはすべてサブエージェントにバックグラウンドで委譲（並列実行可）：

   - **A** — 機能別ドキュメント（マスター）に決定内容（理由含む）を追記
   - **B** — `wiki/Issues.md` から対象 Issue を削除
   - **C** — `wiki/イシュー履歴.md` の末尾に追記：

     ```markdown
     ## ISSUE-XXX: {タイトル}

     - **質問内容**: {元の Issue の概要}
     - **決定した内容**: {採用した選択肢と理由、1〜3 行}
     - **決定日**: YYYY-MM-DD
     - **転記先**: [{ドキュメント名}](wiki/{ファイル名}.md#{セクション})

     ---
     ```

   - **D** — 新しいドキュメントが作成された場合は `wiki/home.md` のリンクを更新

---

## 重複チェック

ドキュメントに情報を書く前に必ず実行：

1. `wiki/` 配下を対象キーワードで全文 Grep 検索
2. 重複が見つかった場合 → マスタードキュメント原則を適用して正しい置き場所を決める
3. マスター以外のドキュメントでは、重複する内容を参照リンクに置き換える：

```markdown
詳細は [マスタードキュメント — セクション名](wiki/master.md#section) を参照
```

マスタードキュメントを更新した後は、古いアンカー名を Grep で検索し、他ドキュメントの参照リンクが古くなっていないか確認する。

**悪い例**（同じ仕様が 2 箇所に重複）：
```markdown
# 共通仕様.md
## 失敗閾値: STT: 3, TTS: 2

# feature-x.md
## 失敗閾値: STT: 3, TTS: 2   ← 重複！
```

**良い例**（情報の単一ソース）：
```markdown
# 共通仕様.md  ← マスター
## 失敗閾値: STT: 3, TTS: 2

# feature-x.md
閾値の詳細は [共通仕様.md — 失敗閾値](共通仕様.md#失敗閾値) を参照
```

## home.md の更新

ドキュメントが追加・削除・リネームされたとき：

1. `wiki/` を Glob スキャンして現在のファイル一覧を取得
2. `home.md` の現在のリンクと差分を検出
3. セクション分類の更新を提案（機能 / 仕様 / API / 参考資料 — プロジェクトに合わせて）
4. 書き直しはバックグラウンドのサブエージェントに委譲

---

## マスタードキュメント原則

| 情報の種類 | マスタードキュメント |
|-----------|---------------------|
| 機能仕様 | 機能別ドキュメント（例: `feature-x.md`） |
| 全機能共通仕様 | `共通仕様.md` または相当するドキュメント |
| 未決定事項 | `wiki/Issues.md` |
| 決定済みの設計（経緯含む） | 機能別ドキュメント（Issues.md には残さない） |
| API 仕様 | 専用 API ドキュメント |
| AI 構成 / LLM 役割分担 | 専用 AI 構成ドキュメント（存在する場合） |

マスター以外のドキュメントは参照リンクのみ記載 — 内容を重複して書かない。

---

## 最終更新の記録

ドキュメントを更新するたびに（初回作成時を除く）、末尾のこの行を追記または更新する：

```markdown
**最終更新**: YYYY-MM-DD — {変更内容の概要（1行）}
```

記載例：
```
**最終更新**: 2026-04-27 — ISSUE-029 に基づきホットリロード/再起動の分類セクション追加
**最終更新**: 2026-04-27 — T2 を並列呼び出しから単一呼び出しに変更（セクション 3・4 更新）
```

別セッションの AI がファイルを読んだときに「いつ・なぜ更新されたか」を即座に把握できるようにするため。

---

## ファイル書き込みのサブエージェント委譲

ドキュメントの作成・更新・追記はすべてバックグラウンドのサブエージェントに委譲する：

- メインセッション：判断・分析・ユーザーとのやり取りに集中
- サブエージェント：実際のファイル書き込みをバックグラウンドで実行（`run_in_background=true`）
- サブエージェントの完了を待たずに次のタスクに進む

サブエージェントへの指示テンプレート：
```
タスク: {どのファイルに何を書き込むか}

内容:
{ヒアドキュメント形式で具体的な内容}

ルール:
1. 書き込み前に wiki/ 配下を Grep で重複チェック
2. 重複があればマスタードキュメント原則を適用
3. 新しいドキュメントを作成した場合は wiki/home.md を更新
4. ファイル末尾の **最終更新** 行を更新
5. 完了したら何を更新したか 1〜3 行で報告
```

---

## やらないこと

- `wiki/` 内にサブフォルダを作らない
- 同じ決定内容を複数のドキュメントに書かない — 1 つの仕様は 1 つのドキュメントで管理
- `home.md` を更新せずに新しいドキュメントを追加しない
- 古い情報を残さない — ドキュメントを削除したら `home.md` のリンクも削除
- メインセッションで直接ファイル書き込みしない — バックグラウンドのサブエージェントに委譲
