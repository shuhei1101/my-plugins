# `needs-user-review` を付けるか判定する基準

Issue / PR に `needs-user-review` を付けるかは AI が自動判断する。
「ユーザー確認なしで実装/マージしてもまず安全」な変更には付けない。
それ以外は付ける（疑わしきは付ける側に倒す）。

`needs-ai-review` は必ず付く（AI レビューは常に通す）ので、この判定は不要。

## 付けない（ユーザー判断不要）

- リファクタリング（表面の動作は変わらない変更、type: refactor）
- 命名規則変更（変数名・関数名のスタイル統一など）
- 例外ハンドル変更（裸 `except:` の握り潰し改善、ログ追加など）
- ロガー使用箇所の追加・整理（`print` → `logger` 置換等）
- ラベル・テキスト・コメントなどの簡易的な見た目変更
- dead code（未使用 import / 未呼び出し関数 / コメントアウト残骸）の除去
- 分散ロジックの共通化（既存の重複コードを単純に関数化）
- タイムアウト追加（既存処理に妥当な timeout 値を入れる）
- タイムゾーン挙動の修正（明示的な UTC / JST 指定追加）
- typo / lint warning の修正
- ドキュメントの誤字脱字修正

## 付ける（ユーザー判断必要）

- 新規機能追加
- 仕様変更（既存の挙動が変わる）
- 公開 API の変更（シグネチャ・レスポンス形式・ステータスコード等）
- データ移行・スキーマ変更
- セキュリティに関わる変更（認証・認可・入力検証・シークレット扱い）
- パフォーマンス特性に影響する変更（キャッシュ追加 / クエリ最適化 / リトライ）
- 外部サービス連携の追加・変更
- 設定ファイル・環境変数の追加・既定値変更
- 依存ライブラリの追加・メジャー更新
- 対応案が複数ある変更（A/B/C のうちどれを採るかユーザー判断が要る）
- 影響範囲が広い変更（複数モジュールに横断する）

## 迷ったとき

「これを 100 件まとめて自動マージされたとして、ユーザーが後悔する可能性があるか?」を自問する。
1 件でも後悔しそうなら `needs-user-review` を付ける。

## 適用先

| スキル / エージェント | この判定の使い方 |
|---|---|
| `code-scanner` | Issue 起票時に `needs-user-review` を付けるか判断 |
| `issue-reviewer` | Issue レビュー時に既存ラベルを見直し、必要なら `needs-user-review` を追加 |
| `pr-implementer` | PR を Ready 化するときに `needs-user-review` を付けるか判断（実装内容で再判定） |
