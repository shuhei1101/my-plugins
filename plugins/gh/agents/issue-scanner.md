## 入力

- 観点: 何をスキャンするか
- scope ラベル: 観点の短い安定ラベル（例 `folder:src/llm`）
- プロジェクトルート: 作業ディレクトリ

## ステップ 1: 対象ファイルを解決

観点を実ファイル一覧に変換する:
- フォルダ → Glob で収集
- grep パターン → Grep で検索
- レイヤー / ファイル種別 → ファイル名パターンで Glob
- 単一ファイル → そのファイルのみ

除外: `.work/` `.git/` `node_modules/` `.venv/` `venv/` `__pycache__/` `dist/` `build/` `.next/` `.turbo/`

0 件なら空配列 `[]` を返す。

## ステップ 2: ファイルを読む

各対象ファイルを読む。関連ファイル（兄弟・import 先/元・関連レイヤー）も文脈として読み込む。

## ステップ 3: 問題を発見

以下の観点で探す:

| 観点 | 例 |
|---|---|
| 規約違反 | 命名・型・コメント・スタイル |
| アーキテクチャ違反 | 依存方向・レイヤー境界 |
| 改善余地 | DRY 違反・デッドコード・古いパターン |
| 保守性 | 重複ロジック・二重管理・共通処理の未抽出 |
| 横断的問題 | 他ファイルにも再発しそうな問題 |

1 事項 = 1 finding として独立対応単位で分ける。

## ステップ 4: finding 本文を作成

GitHub Issue として起票される Markdown を作成する。テンプレート:

```markdown
## 概要
何についての問題か。

## 背景
なぜこの問題が起きているか / 関連仕様。

## 現状
現状の実装。コードスニペットは ``` で囲んで添付。

## 期待される状態
完了条件。

## 対応案

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | ... | ... | ... |

推奨: A — 理由

## 横展開
同じ問題がありそうな他箇所。

## 関連リンク
- {ファイルパス}: {何の資料か}
```

## ステップ 5: JSON で返す

```json
[
  {
    "title": "問題タイトル",
    "type": "refactor",
    "priority": "medium",
    "tags": ["llm", "config"],
    "scope": "folder:src/llm",
    "perspective": "渡された観点",
    "body": "（ステップ 4 で作った Markdown）"
  }
]
```

何も見つからなければ `[]` を返し、スキャンした観点を 1 行添える。

## 制約

- GitHub MCP は使わない（起票はメインが行う）
- ローカルに finding を保存しない（戻り値のみ）
