## 入力

| 引数 | 内容 |
|---|---|
| Issue 番号 | 例: 42 |
| Issue タイトル | |
| Issue 本文 | ユーザー記入の問題説明 |
| 既存コメント全文 | 過去の議論 |

## ステップ 1: コードベースを読む

Issue が言及している領域・関連ファイルを Read で実際に確認する。Read 時に PreToolUse フックがファイル系ルールを自動注入する — 提案はそのルールに整合させる。

| 確認内容 |
|---|
| Issue が指す現状の実装位置 |
| 既存の似た機能・抽象化 |
| 想定される影響範囲（呼び出し元・テスト） |

## ステップ 2: コメント本文を作成

以下構造の Markdown を作る:

```markdown
## 実装方針案

<!-- 案が複数あれば表形式で比較 -->

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | ... | ... | ... |
| B | ... | ... | ... |

**推奨: A** — 理由を 1〜2 行

## 確認したい質問

### QA-1: {タイトル}

**背景**: {なぜ判断が必要か}

A) ... / B) ...

**推奨**: A — 理由

### QA-2: ...

## 分割提案（必要なときのみ）

| No | スコープ | 内容 |
|---|---|---|
| 1 | router 層 | ... |
| 2 | DB スキーマ | ... |

## 影響範囲

| No | ファイル / 領域 | 影響 |
|---|---|---|
| 1 | `{path}` | {何が変わるか} |
```

質問が無く方針が確定している場合は「## 確認したい質問」セクションごと省略する。分割不要なら「## 分割提案」も省略。

## ステップ 3: 戻り値

```json
{
  "issue_number": 42,
  "comment_body": "（ステップ 2 の Markdown）",
  "suggested_labels": ["ready-for-go"],
  "status": "ok"
}
```

`suggested_labels` の候補:

| ラベル | 条件 |
|---|---|
| `needs-clarification` | QA を含む |
| `ready-for-go` | QA なし・方針確定 |
| `split-needed` | 分割提案あり |

## 制約

- GitHub への投稿はしない（メインが行う）
- 推奨案は必ず明示（「後で決める」「TBD」禁止）
- 既存コメントで議論済みの論点は蒸し返さない
