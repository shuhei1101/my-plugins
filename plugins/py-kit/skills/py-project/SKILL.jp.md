# py-kit:py-project — Python プロジェクト（新規 or 既存）

本格 Python プロジェクトを扱う。新規ならゼロからレイヤー構造で生成し、
既存なら py-kit 規約に照らしてレビュー・拡張・修正する。

## 作業内容

### ステップ1: 規約を読み込む

まずインデックスファイルを読み込む：

```
{plugin_root}/references/_index.md
```

スキルファイルの2階層上がプラグインルート（例: `Base directory: .../skills/py-project` → プラグインルートは `.../{plugin-name}/`）。

続いて以下を読む：
- `{plugin_root}/references/python-core.md` — 常に必要
- `{plugin_root}/references/python-architecture.md` — プロジェクト作業では常に必要
- `{plugin_root}/references/python-testing.md` — 新規プロジェクトまたはテスト関連タスク
- `{plugin_root}/references/python-fastapi.md` — FastAPI を使う場合
- `{plugin_root}/references/python-llm.md` — LLM API を呼ぶ場合

→ ステップ2へ

#### 処理内容

ユーザーが新規プロジェクトを作りたいのか、既存プロジェクトへの作業をしたいのかを判定する：

| シグナル | モード |
|---|---|

判断が難しい場合はユーザーに確認する。

## 新規プロジェクト（ステップ3〜8）

### ステップ3: 要件収集

1. プロジェクト名・パッケージ名（`snake_case`）を確認する。
2. プロジェクトの目的と呼び出し元を確認する。
3. 主要ユースケースを3〜5個列挙する（動詞：「注文を処理する」「レポートを生成する」など）。
4. 外部依存（DB・API・ファイルシステム・メッセージキュー）を特定する。
5. インターフェース種別（CLI / FastAPI / tkinter GUI / バックグラウンドワーカー）を確認する。
6. 環境変数の要件を確認する。

→ ステップ4へ

---

### ステップ4: レイヤー設計

1. コードをどのレイヤーに分けるかを決める（フォルダ名は自由）。
2. 外部サービスに触れるコードを識別し、境界レイヤーに分離する。
3. ビジネスロジック層で各外部境界の `Protocol` インターフェースを定義する。
4. 境界レイヤーで具体実装クラスを計画する。
5. 全具体クラスをどこで組み立てるか（コンポジションルート）を確認する。
6. コード生成前にレイヤー計画をユーザーに提示して確認を得る。

→ ステップ5へ

---

### ステップ5: プロジェクト雛形を生成する

1. レイヤー計画に基づいてディレクトリ構造を作成する（`python-architecture.md`のプロジェクトフォルダ構成参照）。
2. `pyproject.toml` を作成する（Python `>= 3.11`、依存は `~=` でピン留め）。
3. `.gitignore` を作成する（`.env`・`__pycache__/`・`*.pyc`・`venv/`・`.venv/`・`log/`・`cache/` を含む）。
4. `.env.sample` を作成する（全環境変数キーとプレースホルダー値を記載）。
5. Windows の場合：`setup/setup_venv.bat`（ASCII のみ）と `activate.bat` を作成する。Linux/macOS はスキップ。
6. 空フォルダ（`log/`・`input/`・`output/`・`cache/`）に `.gitkeep` を追加する。
7. 計画した全モジュールのスタブファイルを作成する。
8. `python-testing.md` のロガー仕様に従って `logger.py` を作成する。
9. `constants.py` には `PROJECT_ROOT` と `LOG_DIR` のみ記載する（マジックナンバー・文字列は禁止）。

→ ステップ6へ

---

### ステップ6: 依存性注入の配線

1. 全外部境界インターフェースの `Protocol` 定義を作成する。
2. 全具体実装をインスタンス化・注入するコンポジションルートを作成する。
3. 上位ビジネスロジック層が外部ライブラリの具体クラスを直接インポートしていないことを確認する。
4. `python-architecture.md` の記述に従い、Strategy / Factory / Decorator パターンを適用する。

→ ステップ7へ

---

### ステップ7: リンクルールを作成する

雛形生成後、実装・ドキュメント・テストを同期させるルールを作成する。
各ルールについて `/claude-kit:rule-creator` スキルを使用する。

1. **クラス構造リンク** — Protocol と具体実装クラスをリンク
2. **設定 ↔ ソースリンク** — 設定ファイルとそれを読むソースファイルをリンク
3. **ソース ↔ テストリンク** — ソースファイルと対応テストファイルをリンク

→ ステップ8へ

---

### ステップ8: テスト雛形を作成する

1. `tests/conftest.py` を作成する（共有 pytest フィクスチャ）。
2. `tests/mocks/mock_env.py` を作成する（環境変数モックヘルパー）。
3. `tests/mocks/mock_externals.py` を作成する（外部 API / DB クライアントのスタブ）。
4. 各ユースケースに対応する `tests/{feature}/test_{feature}.py` スタブを作成する。
5. テストは外部 I/O 境界のみモック — 個別メソッドのユニットテストは書かない。

→ 完了（新規プロジェクトフロー終了）

---

## 既存プロジェクト（ステップ9〜13）

### ステップ9: プロジェクト構造を把握する

1. トップレベルのディレクトリ一覧を読む。
2. レイヤー構造を特定する（DDD を使っているか・どんなレイヤーがあるか）。
3. `pyproject.toml` を読む（依存関係とパッケージ設定を把握）。
4. メインエントリーポイントと既存テストを特定する。
5. `.claude/rules/` ファイルの有無を確認する。

→ ステップ10へ

---

### ステップ10: 品質チェック

1. `python-core.md` の命名規則に照らして確認する。
2. 型ヒントの網羅率を確認する。
3. SOLID 違反を確認する（`python-architecture.md` 参照）。
4. レイヤー分離を確認する。
5. ハードコード値を確認する。
6. 重複ロジックを確認する。
7. システム境界での Pydantic 使用状況を確認する。
8. レビューのみの依頼ならここで報告して終了。

→ 実装が必要な場合はステップ11へ

---

### ステップ11: 変更を実装する

1. タスク（機能追加・リファクタ・バグ修正）を実施する。
2. 参照ドキュメントの全規約に従う。
3. 新規・変更コードに型ヒントを全箇所付ける。
4. タスク要件を超えた抽象化を加えない。
5. コンストラクタで依存性を注入する — クラスボディ内で具体クラスをインスタンス化しない。
6. `print()` / ロガー出力は英語のみ。

→ ステップ12へ

---

### ステップ12: ルールチェック

1. タスク中に変更したものの種別を確認する。
2. 変更種別ごとに対応するルールを適用する。
3. `.claude/rules/` が存在しない場合は `/claude-kit:rule-creator` でルールを作成する。

→ ステップ13へ

---

### ステップ13: テストを更新する

1. 変更したソースファイルに対応するテストファイルを特定する。
2. 変更した動作のテストを更新・作成する。
3. テストは外部 I/O 境界のみモック — 個別メソッドのユニットテストは書かない。
4. `pytest` を実行してテストが通ることを確認する。

→ 完了（既存プロジェクトフロー終了）
