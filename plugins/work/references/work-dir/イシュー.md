# Issue File Format & Index Schema (`.work/issues/`)

Structure for issue files and their indexes under `.work/issues/`. Auto-injected when you create
or edit a file under `.work/issues/`. `issue-scan` / `issue-create` author issue
files from the template below; `merge` and `issue-tool.py` close them.
Japanese mirror: `イシュー.jp.md`

---

## Issue file — `.work/issues/ISSUE-{N}.md`

`{N}` is zero-padded to 3 digits (e.g. `ISSUE-007`). Create with this structure.

```markdown
# {ISSUE-N}: {タイトル}

**作成日**: {YYYY-MM-DD}

## 概要
1–3 sentence summary of what the problem is.

## 背景
Why this issue is needed. Related specifications, requirements, technical background.

## 現状
Current implementation status.

## 問題点
Details of the discovered problem.

### 発生手順

1. {ステップ1}
2. {ステップ2}
3. {ステップ3}

## 原因

Why this problem occurred. Describe the decision error, lack of understanding, or spec deficiency
at the root.

## 期待される状態
What needs to be true for this issue to be considered resolved.

## 修正案

List specific fix approaches to achieve the expected state.
If there are multiple options, list them all and write **推奨: 案X** at the end.

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | {内容} | {メリット} | {デメリット} |

**推奨: 案A**

### 再発防止

Trace back to the root cause and list measures to prevent recurrence. Common angles:

- Fix the source document (plugin definition, specification, etc.)
- Apply a fix in the parent class / base class / shared module
- Add constraints to `.rules` files to prevent missed fixes

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | {内容} | {メリット} | {デメリット} |

## 横展開

List locations beyond the current fix scope that may have the same problem. Common angles:

- Other subclasses inheriting the same parent class
- Similar functions / classes in other domains or modules

| No | 対象 | 内容 |
|---|---|---|
| 1 | {対象} | {横展開内容} |

## 関連ドキュメント

| No | ドキュメント | 備考 |
|---|---|---|
| 1 | [{タイトル}]({リンク}) | {備考} |

```

## `_index.yaml` — active issue index

Git-ignored (listed in `.work/issues/.gitignore`). Maintained by `issue-scan` / `issue-create`.
This index carries the metadata (type / priority / tags / scan scope) that is intentionally kept
out of the issue file body.

```yaml
# Managed by issue-scan / issue-create. Git-ignored (do not commit).
last_id: 0
issues: []
```

### Issue entry

```yaml
- id: ISSUE-007
  title: "{title}"
  created: {YYYY-MM-DD}
  type: {type}          # refactor / rule-violation / ui / backend
  scan_scope:
    - "{scope}"         # scan_scope: [] if none
  priority: {priority}  # high / medium / low
  tags: [{tags}]
```

---

## `_index.archive.yaml` — closed-issue / scan record

Committed to git. `merge` and `issue-tool.py close` append here.

```yaml
# Managed by issue-scan / issue-create / merge. Committed to git.
closed_issues: []
scan_records: []
```

---

## Conventions

- Issue IDs are sequential and zero-padded to 3 digits (`ISSUE-001`, `ISSUE-002`, …); `last_id`
  in `_index.yaml` tracks the highest assigned number.
- `_index.yaml` is git-ignored — never commit it.
- A branch's `## 関連イシュー` table lists the issues it resolves; `merge` closes them automatically.
- Do not hand-edit closed-issue records — let `merge` / `issue-tool.py` manage `_index.archive.yaml`.
