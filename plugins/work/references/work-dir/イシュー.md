# Issue File Format & Index Schema (`.work/issues/`)

Structure for issue files and their indexes under `.work/issues/`. Auto-injected when you create
or edit a file under `.work/issues/`. `issue-scan` / `issue-create` author issue files from the
template below; `issue-review` fills the review fields; `work:start` records the branch link;
`merge` / `issue-resolve` / `issue-tool.py` close them.
Japanese mirror: `イシュー.jp.md`

---

## Issue file — `.work/issues/ISSUE-{N}.md`

`{N}` is zero-padded to 3 digits (e.g. `ISSUE-007`). The file **opens with a YAML frontmatter block**
(nothing may precede the opening `---`), followed by the body. Create with this structure.

```markdown
---
decision: pending      # pending（unreviewed） / accept（対応する） / reject（対応しない）
status: not_started    # not_started / in_progress（closed は closed/ へ移動して表現）
branches: []           # このイシューに対応するブランチ名の配列（複数可）
---

# {ISSUE-N}: {タイトル}

**作成日**: {YYYY-MM-DD}

## 概要
1–3 sentence summary of what the problem is.

## 背景
Why this issue is needed. Related specifications, requirements, technical background.

## 現状
Current implementation status.

## 問題点
Details of the discovered problem.

### 発生手順

1. {ステップ1}
2. {ステップ2}
3. {ステップ3}

## 原因

Why this problem occurred. Describe the decision error, lack of understanding, or spec deficiency
at the root.

## 期待される状態
What needs to be true for this issue to be considered resolved.

List specific fix approaches to achieve the expected state.
```

## Frontmatter fields & issue lifecycle

The three frontmatter fields are the **source of truth** for an issue's review/work state. The
`_index.yaml` `status` field mirrors `status` for cross-session awareness (the index is the live
signal; the frontmatter is the durable record).

| Field | Values | Who sets it |
|---|---|---|
| `decision` | `pending` / `accept` / `reject` | Created as `pending` by `issue-create` / `issue-scan`; set to `accept` / `reject` by the user during `work:issue-review` |
| `status` | `not_started` / `in_progress` | Created as `not_started`; set to `in_progress` by `work:start` when a branch is created for this issue (also mirrored to `_index.yaml` via `issue-tool.py set-status`) |
| `branches` | list of branch names | Appended by `work:start` when a branch is created for this issue |

Lifecycle:

1. **Create** (`issue-create` / `issue-scan`) → `decision: pending`, `status: not_started`, `branches: []`. QA raised if there are open questions.
2. **Review** (`work:issue-review`) → user sets `decision` (accept/reject), answers `## QA`, optionally writes `## 対応メモ`.
3. **Resolve** (`work:issue-resolve`, looped):
   - `accept` + `not_started` → dispatch a `work:issue-resolver` subagent → `work:start` (sets `status: in_progress`, appends branch) → implement → final (merge-waiting) commit.
   - `accept` + `in_progress` → skip (already being worked on, possibly in another session).
   - `reject` → close as `wontfix` on the shared `chore/rejected-issues` branch (moved to `closed/`).
   - `pending` → skip (not yet reviewed).
4. **Close** → `merge` (resolution `resolved`) or the reject path (resolution `wontfix`) moves the file to `closed/` and records it in `_index.archive.yaml`.

## `_index.yaml` — active issue index

Git-ignored (listed in `.work/issues/.gitignore`). Maintained by `issue-scan` / `issue-create` /
`issue-tool.py`. Carries metadata kept out of the issue body (type / priority / tags / scan scope)
plus the `status` mirror.

```yaml
# Managed by issue-scan / issue-create / issue-tool.py. Git-ignored (do not commit).
last_id: 0
issues: []
```

### Issue entry

```yaml
- id: ISSUE-007
  title: "{title}"
  created: {YYYY-MM-DD}
  type: {type}          # refactor / rule-violation / ui / backend
  scan_scope:
    - "{scope}"         # scan_scope: [] if none
  priority: {priority}  # high / medium / low
  tags: [{tags}]
  status: not_started   # not_started / in_progress — mirrors the frontmatter (set via issue-tool.py set-status)
```

---

## `_index.archive.yaml` — closed-issue / scan record

Committed to git. `merge` / `issue-resolve` / `issue-tool.py close` append here.

```yaml
# Managed by issue-scan / issue-create / merge. Committed to git.
closed_issues: []
scan_records: []
```

## Conventions

- Issue IDs are sequential and zero-padded to 3 digits (`ISSUE-001`, `ISSUE-002`, …); `last_id`
  in `_index.yaml` tracks the highest assigned number.
- `_index.yaml` is git-ignored — never commit it.
- The frontmatter `status` is the durable record; mirror it to `_index.yaml` with
  `issue-tool.py set-status` so other sessions can see in-progress issues.
- A branch's `## 関連イシュー` table lists the issues it resolves; `merge` closes them automatically.
- Do not hand-edit closed-issue records — let `merge` / `issue-tool.py` manage `_index.archive.yaml`.
