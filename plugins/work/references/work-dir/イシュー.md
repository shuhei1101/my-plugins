# Issue File Format & Index Schema (`.work/issues/`)

Structure for issue files and their indexes under `.work/issues/`. Auto-injected when you create
or edit a file under `.work/issues/`. `issue-scan` / `issue-create` author issue files from the
template below; `issue-review` fills the "ユーザー回答欄" (user answer section); `work:start` records
the branch link in `_index.yaml`; `merge` / `issue-resolve` / `issue-tool.py` close them.
Japanese mirror: `イシュー.jp.md`

---

## Issue file — `.work/issues/ISSUE-{N}.md`

`{N}` is zero-padded to 3 digits (e.g. `ISSUE-007`). The file has **no frontmatter** (do not write a
YAML block). It is split into two parts, top and bottom.

- **Top half (AI-authored)**: from `# ISSUE-N` down to just before `# ユーザー回答欄`. Written by
  `issue-create` / `issue-scanner`.
- **Bottom half (user answer section)**: from `# ユーザー回答欄` onward. The human answers it during
  `work:issue-review`. The AI prepares only the headings and **回答候補** (answer candidates), leaving
  each `**回答**:` blank.

Create with this structure.

```markdown
# {ISSUE-N}: {タイトル}

**作成日**: {YYYY-MM-DD}

<!-- Everything above "# ユーザー回答欄" is the AI-authored half -->

## 概要
What this issue is about.

## 背景
Why this issue is needed. Related specifications, requirements, technical background.

## 現状
Current implementation status.

### 再現手順
(Bug only. Delete this heading for new work.)

1. {ステップ1}
2. {ステップ2}
3. {ステップ3}

## 原因
(Bug only.) Why this problem occurred — the decision error, lack of understanding, or spec
deficiency at the root. Delete this heading when there is no cause (e.g. new work).

## 期待される状態
What needs to be true for this issue to be considered complete.

## 対応案

Specific approaches to achieve the expected state. A single bullet is fine if there is one option.
If there are multiple options, list them in the table below and write **推奨: 案X** at the end.
**When you list multiple options, you MUST add a "## QA" entry below asking which option to take.**

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | {内容} | {メリット} | {デメリット} |
| B | {内容} | {メリット} | {デメリット} |

**推奨: 案A**

### 再発防止
(Bug.) Trace back to the root cause and list measures to prevent recurrence. Common angles:

- Fix the source document (plugin definition, specification, etc.)
- Apply a fix in the parent class / base class / shared module
- Add constraints to `.rules` files to prevent missed fixes

## 横展開

List locations beyond the current scope that may have the same problem. Common angles:

- Other subclasses inheriting the same parent class
- Similar functions / classes in other domains or modules

| No | 対象 | 内容 |
|---|---|---|
| 1 | {対象} | {横展開内容} |

|---|---|---|
```

## Lifecycle

An issue's review/work state is expressed by **`## 意思`** in the user answer section (whether to
take it on) and **`status`** in `_index.yaml` (work progress). There is no frontmatter.

| State | Location | Who sets it |
|---|---|---|
| 意思 (take it on?) | body `## 意思` `**回答**:` (free text, e.g. 対応する / 対応しない / 様子見; blank = unreviewed) | Created blank by `issue-create` / `issue-scan`; filled by the user in `work:issue-review` |
| QA answers | body `## QA` each entry's `**回答**:` | Filled by the user in `work:issue-review` |
| Free-form instruction | body `## 自由記述` `**回答**:` | Filled by the user in `work:issue-review` |
| `status` | `_index.yaml` (`not_started` / `in_progress`) | Created `not_started`; set to `in_progress` by `work:start` via `issue-tool.py set-status` when a branch is created |
| `branches` | `_index.yaml` (list of branch names) | Appended by `work:start` when a branch is created |

Lifecycle:

1. **Create** (`issue-create` / `issue-scan`) → fill the top (AI) half; in the bottom (user answer)
   half write only headings + answer candidates, leaving `**回答**:` blank. Register in `_index.yaml`
   with `status: not_started`, `branches: []`.
2. **Review** (`work:issue-review`) → the user answers `## 意思`, `## QA`, and `## 自由記述`.
3. **Resolve** (`work:issue-resolve`, looped):
   - `## 意思` is affirmative + `status: not_started` → dispatch a `work:issue-resolver` subagent →
     `work:start` (sets `status: in_progress`, appends `branches`) → implement → final (merge-waiting) commit.
   - affirmative + `in_progress` → skip (already being worked on, possibly another session).
   - negative ("対応しない") → close as `wontfix` on the shared `chore/rejected-issues` branch (moved to `closed/`).
   - blank (unanswered) → skip (not yet reviewed).
4. **Close** → `merge` (resolution `resolved`) or the reject path (resolution `wontfix`) moves the
   file to `closed/` and records it in `_index.archive.yaml`.

> The `## 意思` `**回答**:` is free human text. The AI reads "対応する/様子見" as affirmative and
> "対応しない" as negative; blank means unreviewed.

## `_index.yaml` — active issue index

Git-ignored (listed in `.work/issues/.gitignore`). Maintained by `issue-scan` / `issue-create` /
`issue-tool.py` / `work:start`. Carries metadata kept out of the issue body (type / priority / tags /
scan scope) plus the work state (`status` / `branches`).

```yaml
# Managed by issue-scan / issue-create / issue-tool.py. Git-ignored (do not commit).
last_id: 0
issues: []
```

### Issue entry

```yaml
- id: ISSUE-007
  title: "{title}"
  created: {YYYY-MM-DD}
  type: {type}          # refactor / rule-violation / ui / backend
  scan_scope:
    - "{scope}"         # scan_scope: [] if none
  priority: {priority}  # high / medium / low
  tags: [{tags}]
  status: not_started   # not_started / in_progress (set via issue-tool.py set-status)
  branches: []          # branch names addressing this issue (appended by work:start)
```

---

## `_index.archive.yaml` — closed-issue / scan record

Committed to git. `merge` / `issue-resolve` / `issue-tool.py close` append here.

```yaml
# Managed by issue-scan / issue-create / merge. Committed to git.
closed_issues: []
scan_records: []
```

---

## Conventions

- Issue IDs are sequential and zero-padded to 3 digits (`ISSUE-001`, `ISSUE-002`, …); `last_id`
  in `_index.yaml` tracks the highest assigned number.
- Issue files have **no frontmatter** — they start at `# ISSUE-N`.
- `_index.yaml` is git-ignored — never commit it.
- The work state (`status` / `branches`) lives in `_index.yaml`; update `status` with
  `issue-tool.py set-status` so other sessions can see in-progress issues.
- A branch's `## 関連イシュー` table lists the issues it resolves; `merge` closes them automatically.
- Do not hand-edit closed-issue records — let `merge` / `issue-tool.py` manage `_index.archive.yaml`.
