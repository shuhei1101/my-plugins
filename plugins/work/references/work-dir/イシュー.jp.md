# イシューファイル構成と索引スキーマ（`.work/issues/`）

`.work/issues/` 配下のイシューファイルと索引の構成。`.work/issues/` 配下のファイルを作成・編集
するときに自動注入される。`issue-scan` / `issue-create` が下のテンプレートからイシューファイルを
作成し、`issue-review` が「ユーザー回答欄」を絞り込み、`work:start` がブランチ連携を `_index.yaml` に
記録し、`merge` / `issue-resolve` / `issue-tool.py` がクローズする。
英語原文: `イシュー.md`

---

## イシューファイル — `.work/issues/ISSUE-{N}.md`

`{N}` は 3 桁ゼロ埋め（例: `ISSUE-007`）。**フロントマターは持たない**（YAML ブロックを書かない）。
ファイルは上から次の順で 2 つのパートに分かれる。

1. **ユーザー回答欄**: タイトル・作成日のすぐ下、ファイルの**上部**に置く。下までスクロールせずとも
   回答済みか一目で分かるようにするため。`## 意思` と `## QA` を持つ。AI が雛形（見出し、QA の
   タイトル・選択肢・推奨、そして**全候補を並べた** `**回答**:` 行）を用意し、ユーザーは各 `**回答**:`
   行で**不要な候補を消して 1 つだけ残す**（または `{回答を入力}` を埋める）。ユーザーが触るのは
   `**回答**:` 行だけ。
2. **イシュー本文（AI 記入欄）**: 回答欄の後の `---` 以降すべて（概要 / 背景 / 現状 / 対応案 /
   横展開 等）。`issue-create` / `issue-scanner` が全記入し、ユーザーは通常編集しない。

以下の構成で作成する。

```markdown
# {ISSUE-N}: {タイトル}

**作成日**: {YYYY-MM-DD}

# ユーザー回答欄

> 回答方法: 各 `**回答**:` 行で不要な選択肢を消し、1 つだけ残す（`{回答を入力}` は自由記入）。
> この欄だけ見れば回答済みか分かる。AI は選択肢・推奨と、候補を並べた `**回答**:` 行まで用意する。

## 意思

このイシューに対応するか。

**回答**: 対応する / 対応しない

## QA

着手前に決めるべき判断。各 QA は **番号・タイトル・選択肢・推奨** を必ず持つ。対応案が複数ある場合は
「どの案で進めるか」を必ず QA-1 に置く。**判断が不要なら、この「## QA」見出しごと削除する。**

### QA-1: {タイトル}

A) {選択肢 A の要点} / B) {選択肢 B の要点}

**推奨**: A — {理由を 1 行}

**回答**: A / B

### QA-2: {タイトル}

**背景**: {なぜ判断が要るか}

**推奨**: {推奨する値 or なし（要判断）}

**回答**: {回答を入力}

---

<!-- ここから下は AI 記入欄（イシュー本文）。ユーザーは通常編集しない -->

## 概要
何についてのイシューか。

## 背景
なぜこのイシューが必要か。関連仕様・要件・技術的背景。

## 現状
現在の実装状況。

### 再現手順
（バグの場合のみ。新規対応なら見出しごと削除）

1. {ステップ1}
2. {ステップ2}
3. {ステップ3}

## 原因
（バグの場合のみ）なぜこの問題が起きたか。根本にある判断ミス・理解不足・仕様欠陥。
新規対応など原因が無い場合は見出しごと削除。

## 期待される状態
このイシューが完了したと言えるために満たすべき状態。

## 対応案

期待される状態を達成する具体的な対応方針。案が 1 つなら箇条書き 1 つでよい。
複数案を出す場合は下表に列挙し、末尾に **推奨: 案X** を記載。
**複数案を出した場合は、必ず上の回答欄に `### QA-N` を立て、選択肢を `A) … / B) …` の形で要約し
推奨を添えて「どの案で進めるか」を問う。**

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | {内容} | {メリット} | {デメリット} |
| B | {内容} | {メリット} | {デメリット} |

**推奨: 案A**

### 再発防止
（バグの場合）根本原因まで遡り、再発を防ぐ施策を列挙。よくある観点：

- 元ドキュメント（プラグイン定義・仕様書等）を修正
- 親クラス／基底クラス／共通モジュールで修正
- 修正漏れ防止のため `.rules` に制約を追加

## 横展開

現在の対応スコープを超えて同じ問題がありそうな箇所を列挙。よくある観点：

- 同じ親クラスを継承する他のサブクラス
- 他ドメイン／モジュールの類似関数・クラス

| No | 対象 | 内容 |
|---|---|---|
| 1 | {対象} | {横展開内容} |

## 関連ドキュメント

| No | ドキュメント | 備考 |
|---|---|---|
| 1 | [{タイトル}]({リンク}) | {備考} |
```

## ライフサイクル

イシューのレビュー／作業状態は、**「ユーザー回答欄」の `## 意思`**（対応するか）と
**`_index.yaml` の `status`**（着手状況）で表す。フロントマターは持たない。

| 状態 | 置き場 | 設定者 |
|---|---|---|
| 意思（対応するか） | 回答欄 `## 意思` の `**回答**:`（全候補を事前記入。例: 対応する / 対応しない。ユーザーが 1 つに絞る。候補が全部残っている=未レビュー） | `issue-create` / `issue-scan` が全候補で作成。ユーザーが `work:issue-review` で絞り込み |
| QA 回答 | 回答欄 `## QA` 各エントリの `**回答**:`（全候補を事前記入。ユーザーが 1 つに絞る） | `issue-create` / `issue-scan` が事前記入。ユーザーが `work:issue-review` で絞り込み |
| `status` | `_index.yaml`（`not_started` / `in_progress`） | `not_started` で作成。ブランチ作成時に `work:start` が `issue-tool.py set-status` で `in_progress` に |
| `branches` | `_index.yaml`（ブランチ名の配列） | ブランチ作成時に `work:start` が追記 |

ライフサイクル：

1. **作成**（`issue-create` / `issue-scan`）→ ファイル全体を記入: イシュー本文と、回答欄の雛形
   （`## 意思` / `## QA` の見出し・タイトル・選択肢・推奨、`**回答**:` 行に全候補を事前記入）。
   `_index.yaml` に `status: not_started`、`branches: []` で登録。
2. **レビュー**（`work:issue-review`）→ ユーザーが `## 意思` と各 `## QA` の `**回答**:` 行を
   1 つに絞る（または `{回答を入力}` を埋める）。
3. **対応**（`work:issue-resolve`、ループ）：
   - `## 意思` が「対応する」系 + `status: not_started` → `work:issue-resolver` サブエージェントを起動
     → `work:start`（`status: in_progress` 設定・`branches` 追記）→ 実装 → 最終（マージ待ち）コミット。
   - 「対応する」系 + `in_progress` → スキップ（既に対応中。別セッションの可能性）。
   - 「対応しない」系 → 共有ブランチ `chore/rejected-issues` 上で `wontfix` クローズ（`closed/` へ移動）。
   - 未絞り込み（候補が全部残っている）→ スキップ（未レビュー）。
4. **クローズ** → `merge`（resolution `resolved`）または reject 経路（resolution `wontfix`）がファイルを
   `closed/` へ移動し、`_index.archive.yaml` に記録。

> `## 意思` の `**回答**:` は AI が解釈する。「対応する」を肯定、「対応しない」を否定とみなす。
> 候補が複数残ったまま（1 つに絞られていない）なら未レビュー扱い。

## `_index.yaml` — アクティブイシュー索引

Git 管理外（`.work/issues/.gitignore` に記載）。`issue-scan` / `issue-create` / `issue-tool.py` /
`work:start` が管理。イシュー本文に書かないメタ情報（type / priority / tags / scan scope）と、
作業状態（`status` / `branches`）を持つ。

```yaml
# Managed by issue-scan / issue-create / issue-tool.py. Git-ignored (do not commit).
last_id: 0
issues: []
```

### イシューエントリ

```yaml
- id: ISSUE-007
  title: "{title}"
  created: {YYYY-MM-DD}
  type: {type}          # refactor / rule-violation / ui / backend
  scan_scope:
    - "{scope}"         # 無ければ scan_scope: []
  priority: {priority}  # high / medium / low
  tags: [{tags}]
  status: not_started   # not_started / in_progress（issue-tool.py set-status で設定）
  branches: []          # このイシューに対応するブランチ名の配列（work:start が追記）
```

---

## `_index.archive.yaml` — クローズ済みイシュー／スキャン記録

Git 管理対象。`merge` / `issue-resolve` / `issue-tool.py close` が追記する。

```yaml
# Managed by issue-scan / issue-create / merge. Committed to git.
closed_issues: []
scan_records: []
```

---

## 規約

- イシュー ID は連番で 3 桁ゼロ埋め（`ISSUE-001`, `ISSUE-002`, …）。`_index.yaml` の `last_id` が
  最大採番値を追跡する。
- イシューファイルは**フロントマターを持たない** — `# ISSUE-N` から始まる。
- `_index.yaml` は git 管理外 — 絶対にコミットしない。
- 作業状態（`status` / `branches`）は `_index.yaml` が正。`issue-tool.py set-status` で `status` を
  更新し、他セッションが進行中イシューを把握できるようにする。
- ブランチの `## 関連イシュー` テーブルが解決するイシューを列挙し、`merge` が自動クローズする。
- クローズ済み記録は手編集しない — `merge` / `issue-tool.py` に `_index.archive.yaml` を管理させる。
