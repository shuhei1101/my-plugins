# イシューファイル構成と索引スキーマ（`.work/issues/`）

`.work/issues/` 配下のイシューファイルと索引の構成。`.work/issues/` 配下のファイルを作成・編集
するときに自動注入される。`issue-scan` / `issue-create` が下のテンプレートからイシューファイルを
作成し、`issue-review` がレビュー欄を埋め、`work:start` がブランチ連携を記録し、
`merge` / `issue-resolve` / `issue-tool.py` がクローズする。
英語原文: `イシュー.md`

---

## イシューファイル — `.work/issues/ISSUE-{N}.md`

`{N}` は 3 桁ゼロ埋め（例: `ISSUE-007`）。ファイルは **YAML フロントマターで始まり**（開始の `---`
より前には何も書かない）、本文が続く。以下の構成で作成する。

```markdown
---
decision: pending      # pending（未レビュー） / accept（対応する） / reject（対応しない）
status: not_started    # not_started / in_progress（closed は closed/ へ移動して表現）
branches: []           # このイシューに対応するブランチ名の配列（複数可）
instruction: ""        # ユーザーが自由に書く対応指示（任意。例: "公開APIのみ直す"。複数行は YAML の | を使う）
---

# {ISSUE-N}: {タイトル}

**作成日**: {YYYY-MM-DD}

## 概要
問題が何かを 1〜3 文で要約。

## 背景
なぜこのイシューが必要か。関連仕様・要件・技術的背景。

## 現状
現在の実装状況。

## 問題点
発見された問題の詳細。

### 発生手順

1. {ステップ1}
2. {ステップ2}
3. {ステップ3}

## 原因

なぜこの問題が起きたか。根本にある判断ミス・理解不足・仕様欠陥を記述。

## 期待される状態
このイシューが解決したと言えるために満たすべき状態。

## 修正案

期待される状態を達成する具体的な修正方針を列挙。複数案ある場合は全て挙げ、末尾に **推奨: 案X** を記載。

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | {内容} | {メリット} | {デメリット} |

**推奨: 案A**

### 再発防止

根本原因まで遡り、再発を防ぐ施策を列挙。よくある観点：

- 元ドキュメント（プラグイン定義・仕様書等）を修正
- 親クラス／基底クラス／共通モジュールで修正
- 修正漏れ防止のため `.rules` に制約を追加

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | {内容} | {メリット} | {デメリット} |

## QA

このイシューに着手する前に決着させるべき未解決事項。作成・スキャン時に提起する（例: 「どの修正案か」、
設計上の選択）。**ユーザーが `work:issue-review` で回答する。** 回答後は `状態` を 解決 にし、決定内容を
`## 修正案`（採用案）や該当セクションへ反映する。**未解決事項が無ければこの見出しごと削除する。**

### QA-001: {タイトル}

**背景**: {なぜ判断が要るか}

| # | 案 | 内容 |
|---|---|---|
| 1 | A | {案 A} |
| 2 | B | {案 B} |

**回答**: {レビューで記入。採用案 + 理由。未回答なら「未回答」}

**状態**: 未解決

## 横展開

現在の修正スコープを超えて同じ問題がありそうな箇所を列挙。よくある観点：

- 同じ親クラスを継承する他のサブクラス
- 他ドメイン／モジュールの類似関数・クラス

| No | 対象 | 内容 |
|---|---|---|
| 1 | {対象} | {横展開内容} |

## 関連ドキュメント

| No | ドキュメント | 備考 |
|---|---|---|
| 1 | [{タイトル}]({リンク}) | {備考} |

```

> ユーザーの自由記述の対応指示は**フロントマターの `instruction` キー**に入れる（`work:issue-review`
> 時に記入）— 例: `instruction: "公開APIのみ直す"`。本文セクションは設けない。

---

## フロントマターのフィールドとイシューのライフサイクル

フロントマターのフィールドがイシューのレビュー／作業状態の**正（source of truth）**。
`_index.yaml` の `status` フィールドはセッション横断の把握のために `status` をミラーする
（索引がライブな信号、フロントマターが永続的な記録）。

| フィールド | 値 | 設定者 |
|---|---|---|
| `decision` | `pending` / `accept` / `reject` | `issue-create` / `issue-scan` が `pending` で作成。ユーザーが `work:issue-review` で `accept` / `reject` に設定 |
| `status` | `not_started` / `in_progress` | `not_started` で作成。このイシュー用のブランチ作成時に `work:start` が `in_progress` に設定（`issue-tool.py set-status` で `_index.yaml` にもミラー） |
| `branches` | ブランチ名の配列 | このイシュー用のブランチ作成時に `work:start` が追記 |
| `instruction` | 自由テキスト（既定 `""`） | ユーザーの自由記述の対応指示（例: "公開APIのみ直す"）。`work:issue-review` 時に記入。複数行は YAML の `|` |

ライフサイクル：

1. **作成**（`issue-create` / `issue-scan`）→ `decision: pending`、`status: not_started`、`branches: []`、`instruction: ""`。未解決事項があれば QA を提起。
2. **レビュー**（`work:issue-review`）→ ユーザーが `decision`（accept/reject）を設定し、`## QA` に回答、任意で `instruction` フロントマターキーを記入。
3. **対応**（`work:issue-resolve`、ループ）：
   - `accept` + `not_started` → `work:issue-resolver` サブエージェントを起動 → `work:start`（`status: in_progress` 設定・ブランチ追記）→ 実装 → 最終（マージ待ち）コミット。
   - `accept` + `in_progress` → スキップ（既に対応中。別セッションの可能性）。
   - `reject` → 共有ブランチ `chore/rejected-issues` 上で `wontfix` クローズ（`closed/` へ移動）。
   - `pending` → スキップ（未レビュー）。
4. **クローズ** → `merge`（resolution `resolved`）または reject 経路（resolution `wontfix`）がファイルを `closed/` へ移動し、`_index.archive.yaml` に記録。

## `_index.yaml` — アクティブイシュー索引

Git 管理外（`.work/issues/.gitignore` に記載）。`issue-scan` / `issue-create` / `issue-tool.py` が
管理。イシュー本文に書かないメタ情報（type / priority / tags / scan scope）と `status` ミラーを持つ。

```yaml
# Managed by issue-scan / issue-create / issue-tool.py. Git-ignored (do not commit).
last_id: 0
issues: []
```

### イシューエントリ

```yaml
- id: ISSUE-007
  title: "{title}"
  created: {YYYY-MM-DD}
  type: {type}          # refactor / rule-violation / ui / backend
  scan_scope:
    - "{scope}"         # 無ければ scan_scope: []
  priority: {priority}  # high / medium / low
  tags: [{tags}]
  status: not_started   # not_started / in_progress — フロントマターをミラー（issue-tool.py set-status で設定）
```

---

## `_index.archive.yaml` — クローズ済みイシュー／スキャン記録

Git 管理対象。`merge` / `issue-resolve` / `issue-tool.py close` が追記する。

```yaml
# Managed by issue-scan / issue-create / merge. Committed to git.
closed_issues: []
scan_records: []
```

---

## 規約

- イシュー ID は連番で 3 桁ゼロ埋め（`ISSUE-001`, `ISSUE-002`, …）。`_index.yaml` の `last_id` が
  最大採番値を追跡する。
- `_index.yaml` は git 管理外 — 絶対にコミットしない。
- フロントマターの `status` が永続的な記録。`issue-tool.py set-status` で `_index.yaml` にミラーし、
  他セッションが進行中イシューを把握できるようにする。
- ブランチの `## 関連イシュー` テーブルが解決するイシューを列挙し、`merge` が自動クローズする。
- クローズ済み記録は手編集しない — `merge` / `issue-tool.py` に `_index.archive.yaml` を管理させる。
