# .work/ Directory Guide

Reference for editing files under `.work/` — directory structure, file roles, and commit conventions.
Japanese mirror: `references/work-dot-work-dir.jp.md`

---

## Directory Structure

| Path | Purpose |
|---|---|
| `tasks/index.yaml` | Branch index (`completed: false` = in progress). `last_id` tracks the next internal numeric ID (used for archive cross-reference; not embedded in branch names) |
| `tasks/index.archive.yaml` | Archived (`completed: true`) branch entries. Auto-generated by `index-tool.py archive` on merge |
| `tasks/{YYMMDD}_{title}/{YYMMDD}-{日本語タイトル}.md` | One Markdown file per branch — TODO + QA + variations all in a single document |
| `notes/{topic-name}.md` | Snapshot **spec sheet** — records the *current* spec/structure of one subject (not auto-loaded by Claude) |

### tasks/

`tasks/index.yaml` is the single source of truth for branch status. In-progress branches have `completed: false`; merged ones have `completed: true`. The `last_id` field tracks the highest internal numeric ID assigned so far (used for archive cross-reference; **not** embedded in branch names, worktree paths, or filenames). On each merge, `index-tool.py archive` moves completed entries to `index.archive.yaml`, keeping `index.yaml` small. Always read index.yaml at the start of a session to identify the active branch.

One folder per task (`{YYMMDD}_{title}/`). Inside the folder, **one Markdown file per branch** — the filename is `{YYMMDD}-{日本語タイトル}.md`, where the Japanese title is the H1 of the branch document (e.g. `260531-ブランチ文書ファイル名変更.md`).

The branch document is the single source of truth for what a branch does. Create it before starting implementation and keep it current. It contains the following sections:

- `## 概要` — purpose / background (includes `### 実施条件`)
- `## 作業内容` — task checklist (mark each completed row's `完了` column as `済`; all rows must be `済` before merging)
- `## 変更内容` — list of every implementation file added or modified (excluding tests)
- `## テスト` — test files added or modified alongside the implementation
- `## QA` — unresolved questions scoped to this branch (resolve before merging; reflect decisions in the relevant note / document)
- `## 参考ドキュメント` — links to related notes
- `## 関連イシュー` — `.work/issues/` entries this branch resolves (auto-closed by merge)
- `## 関連ブランチ` — predecessor / successor / sibling branches
- `## 次ブランチ候補` — follow-up branches to reserve via `/work:branch-reserve`

### notes/

**Role**: A **snapshot spec sheet** for the project. Each note records what one subject (a plugin, skill, hook, convention, or design) *currently is* — its present specification and structure. **Not auto-loaded by Claude** — notes are read on demand and linked from branch documents.

**Write the current state only.** A note describes how things are *now*. Do not put history, background, or rationale ("why it ended up this way") in the body. When something changes, **overwrite** the stale text — delete it cleanly rather than appending. The only record of change is each note's `## 変更履歴` table at the bottom.

- **What to write + the fixed note template** → see `notes-content-rules.md`
- **File naming + `_index.md` rules** → see `notes-naming-rules.md`

**`_index.md`**: the catalog of all notes under `.work/notes/`, organized by category. **Always update it in the same commit** when you create, rename, or delete a note. Read `_index.md` to find an existing note before creating a new one (no duplication — one subject, one note).

## Conventions

- Mark completed rows in the `## 作業内容` table with `済` in the `完了` column
- Keep each note a current-state spec sheet; record change only in the note's `## 変更履歴` table
- Append unresolved questions to the branch document's `## QA` section
- Confirm all rows in the task table are `済` before merging
- **Commit `.work/` folder changes separately from implementation code** — `.work/`-only changes (branch document updates, notes, etc.) may be bundled together in a single commit
