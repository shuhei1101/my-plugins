# Incidents Authoring Guide

Inclusion bar and file format for recording entries in the recurrence-prevention log (incidents).
This reference is auto-injected when you edit an incidents file.
Japanese mirror: `references/conversation/インシデント.jp.md`

> Related: for project-specific terminology, see `グロッサリー.md`.

---

## What an incident is

A log that records a **concrete process mistake that actually happened this session** so it does not
recur. "Mistake" here means an **error of operation or judgment** — NOT a **code defect (bug)**.
A bug is done once the code is fixed; it carries no recurrence-prevention lesson. It has a two-layer
structure:

- **Index**: `.claude/rules/incidents.md` — a list of one-line summaries. An **always-loaded rule**.
- **Detail**: `.claude/references/incidents/{slug}.md` (+ `.jp.md` mirror) — the body, read on demand only.

---

## Inclusion bar — record an entry only if ALL of these hold

- A real failure **actually occurred this session**: a command/operation failed and the correct
  approach is now known; a file was accidentally deleted or overwritten; a task planned in the
  original TODO was silently dropped by AI and the user had to re-request it; **AI misread the
  user's intent and the user had to correct the implementation** (examples below).
- The lesson is **generalizable** to future sessions (not specific to this one branch's code).
- The prevention is **not already captured** elsewhere (see the dedup check below).
- **The root cause lies on Claude Code's side**, not the user's side (see "Do NOT record" for the
  distinction).

When in doubt, do **not** record it. Quality over quantity.

### Intent-mismatch incidents — what to record

The most common recordable incident in this plugin's workflow: the user submitted a request, Claude
built a branch and implemented it, and only afterward the user discovered the result diverged from
their actual intent — **due to a judgment error on Claude Code's part**.

Examples that qualify:

- User said "refactor X" and Claude silently deleted X entirely instead of restructuring it.
- User asked for "a small change" and Claude overhauled the whole feature.
- Claude inferred a scope that was much broader (or narrower) than what the user meant, and the
  user had to say "that's not what I meant — I only wanted Y."
- Claude deleted a file thinking it was no longer needed; the user asked "why was this deleted?" —
  and the deletion was wrong.
- Claude preserved an old behavior that the user had already described as unwanted, because Claude
  treated it as safe default rather than reading the instruction.

What all these share: **the user's intent was reasonably discernible**, but Claude made a
misjudgment — wrong scope, wrong assumption, wrong default.

## Do NOT record (common mis-registrations)

> **The most frequent mistake is logging a code bug fix as an incident.**
> Example: a "bug-fix branch" fixes a bug → the bug gets registered as an incident. This is wrong.
> An incident records a **process mistake made during the session**, not a **code defect**.
> A bug is done once fixed (no recurrence-prevention lesson), and logging these explodes the entry count.

- **The code bug itself / its fix** (e.g. the bug a bug-fix branch resolved). Once fixed it is done —
  not an incident. "Which bug, fixed how" belongs in the branch document / commit message, not here.
- **"That's already a rule / CLAUDE.md convention."**
  If the correct behavior is (or should be) enforced by an existing rule, CLAUDE.md, or hook, it is
  not an incident. If a rule *should* exist, **create the rule** instead of logging an incident.
- The PR/branch work content itself (what feature was implemented, what code was changed).
- Tasks the user newly added as scope expansion.
- General best-practices already documented anywhere in the project or in well-known tooling docs.
- A one-off slip with no generalizable prevention.
- **The user's own request was unclear or wrong.** If the user's phrasing was ambiguous, incomplete,
  or simply mistaken, and Claude followed the literal wording, the fault lies with the request — not
  with Claude's judgment. Do not log it as a Claude Code incident. Only record cases where the
  user's intent was reasonably clear from context and Claude still misread it.

## Dedup check before recording (mandatory)

Before keeping an entry, verify:

1. Whether an existing rule, CLAUDE.md convention, hook, or incident already enforces / records the lesson.
2. If so → **discard**.
3. If a rule *should* exist but doesn't → convert it to a **rule candidate** instead of an incident.

## File format

### Index (`.claude/rules/incidents.md` — always loaded)

One incident = one summary line that points to the detail file. Keep it concise.

```markdown
# Incidents

- **{slug}**: {one-line summary — what happened and what was learned}. Detail: `.claude/references/incidents/{slug}.md`
```

### Detail (`.claude/references/incidents/{slug}.md` + `.jp.md`)

```markdown
# {Title}

## Situation
{What you were trying to do and what happened}

## Cause
{Why it happened}

## Prevention / Lesson
{What to do next time — the generalized recurrence-prevention measure}
```

- `{slug}` is a short kebab-case identifier (e.g. `master-direct-edit-causes-merge-conflict`).
- Keep the index entry to **one line** (it is always loaded); put the body in the detail file.
- Create the file / folder if it does not exist.
