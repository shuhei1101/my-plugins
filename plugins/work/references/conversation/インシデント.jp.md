# インシデント記述ガイド

再発防止ログ（incidents）にエントリを記録する際の採用基準とファイル形式。
このリファレンスは incidents ファイルを編集するときに自動注入される。
英語ミラー: `references/conversation/インシデント.md`

> 関連: プロジェクト固有用語の登録は `用語集.md` を参照。

---

## インシデントとは

**このセッションで実際に起きた、作業プロセス上の具体的なミス**を記録し、再発を防ぐためのログ。
ここで言うミスとは「**操作・判断の誤り**」であって、「**コードの不具合（バグ）**」ではない。
バグはコードを直せばそれで完了であり、再発防止の教訓にはならない。二層構造を持つ:

- **インデックス**: `.claude/rules/incidents.md` — 1行サマリの一覧。**常時ロードされるルール**。
- **詳細**: `.claude/references/incidents/{slug}.md`（+ `.jp.md` ミラー）— 必要時のみ読まれる本文。

---

## 採用基準 — 以下の全条件を満たす場合のみ記録する

- このセッションで**実際に失敗が起きた**: コマンド/操作が失敗して正しいやり方が今分かった、
  ファイルを誤って削除/上書きした、当初の TODO で計画されていたタスクを AI が黙って落として
  ユーザーが再依頼した、**AI がユーザーの意図を読み誤って実装し、ユーザーが後から訂正した**（下の例参照）。
- その教訓が将来のセッションに**一般化できる**（このブランチのコード固有でない）。
- 防止策が他所で**まだ捕捉されていない**（下の重複チェック参照）。
- **原因が Claude Code 側にある**（ユーザー側にない）こと（「記録しないもの」の判別基準を参照）。

迷ったら**記録しない**。量より質。

### 意図齟齬インシデント — 記録すべき具体例

このプラグインのワークフローで最も多く発生しうるインシデント：ユーザーが依頼を出し、Claude が
ブランチを切って実装した後になって、**Claude Code 側の判断ミス**によって結果がユーザーの実際の
意図とずれていたことが判明するケース。

記録すべき例:

- ユーザーが「X をリファクタして」と言ったのに、Claude が X をまるごと削除してしまった。
- ユーザーが「小さな変更」と言ったのに、Claude が機能全体を作り直してしまった。
- Claude がスコープを大幅に広く（または狭く）解釈し、ユーザーが「そういう意図じゃなかった、Y だけにしてほしかった」と訂正した。
- Claude がファイルを「もう不要」と判断して削除したが、ユーザーが「なんでこれ削除したの?」と気づいた — かつその削除が誤りだった。
- Claude が古い挙動をデフォルトとして保持したが、ユーザーはすでに「それは不要」と伝えていた。

共通点: **ユーザーの意図はコンテキストから十分に読み取れた**のに、Claude が判断を誤った — スコープ、前提、デフォルト値などの読み違い。

## 記録しないもの（よくある誤登録）

> **最頻出の誤りは「コードのバグ修正をインシデントに書いてしまう」こと。**
> 例: 「バグ対応ブランチ」でバグを直した → そのバグを incident に登録してしまう。これは誤り。
> incident は「コードの不具合」ではなく「セッション中の作業プロセスのミス」を記録するもの。
> バグは直せば終わりで再発防止の教訓ではないし、これを書き始めるとエントリ数が爆発する。

- **コードのバグそのもの・その修正内容**（バグ対応ブランチで直したバグなど）。直したら完了であり
  incident ではない。「何のバグをどう直したか」はタスクドキュメント / コミットメッセージに残るもので、
  incident に書くものではない。
- **「それは既にルール / CLAUDE.md の規約だ」**
  正しい挙動が既存ルール・CLAUDE.md・フックで強制されている（またはされるべき）なら、それは
  incident ではない。ルールが*存在すべき*なら、incident を記録するのではなく**ルールを作る**。
- PR / ブランチの作業内容そのもの（どの機能を実装し、どのコードを変えたか）。
- ユーザーがスコープ拡張として新規追加したタスク。
- プロジェクト内やよく知られたツールのドキュメントに既出の一般的ベストプラクティス。
- 一般化できる防止策のない、一度きりのうっかりミス。
- **ユーザー自身の依頼が不明確または誤りだったケース。** ユーザーの表現が曖昧・不完全・誤りで
  あり、Claude がその文字通りに従った場合は、責任はユーザー側の依頼にある。Claude Code の
  インシデントとして記録しない。記録するのは「ユーザーの意図がコンテキストから十分に読み取れた
  のに Claude が読み誤った」ケースのみ。

## 記録前の重複チェック（必須）

エントリを残す前に確認する:

1. 既存のルール・CLAUDE.md 規約・フック・既存 incident が、その教訓を既に強制 / 記録していないか。
2. していれば → **破棄**。
3. ルールが*あるべきなのに*ない場合は、incident ではなく**ルール候補**に変換する。

## ファイル形式

### インデックス（`.claude/rules/incidents.md` — 常時ロード）

1 インシデント = 1 行サマリ。詳細ファイルへ誘導する。簡潔に保つ。

```markdown
# Incidents

- **{slug}**: {1 行サマリ — 何が起きて何を学んだか}。詳細: `.claude/references/incidents/{slug}.md`
```

### 詳細（`.claude/references/incidents/{slug}.md` + `.jp.md`）

```markdown
# {タイトル}

## 状況
{何をしようとして、何が起きたか}

## 原因
{なぜ起きたか}

## 対策 / 教訓
{次回どうするか — 一般化された再発防止策}
```

- `{slug}` はケバブケースの短い識別子（例: `master-direct-edit-causes-merge-conflict`）。
- インデックスは常時ロードのため**1 行**に抑え、本文は詳細ファイル側に書く。
- ファイル / フォルダが無ければ新規作成する。
