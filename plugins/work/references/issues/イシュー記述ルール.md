# Issue File Authoring Rules

How to write an issue file under `.work/issues/`. This guide is auto-injected when you read, write,
or edit a `.work/issues/ISSUE-*.md` file, so follow it directly — there is no separate save skill.
Japanese mirror: `references/issues/イシュー記述ルール.jp.md`

---

## What an issue is

One issue = one independently actionable problem found in the codebase or reported by the user.
Each issue is a single Markdown file. Open issues live at `.work/issues/ISSUE-{N}.md`; closed issues
are moved to `.work/issues/closed/ISSUE-{N}.md` (the `merge` skill does this).

---

## File naming and numbering

- File name: `ISSUE-{N}.md` where `{N}` is a zero-padded 3-digit number (e.g. `ISSUE-007.md`).
- The authoritative counter is `last_id` in `.work/issues/_index.yaml`.
- To allocate a new ID: read `last_id`, increment by 1, use that as `{N}`.
- **Parallel allocation (issue-scan)**: when many issues are created at once, the orchestrator hands
  each writer a reserved ID block, so issue numbers may be non-contiguous. That is expected — IDs
  only need to be unique and monotonically increasing, not gapless.

---

## File format

Write the file with this structure. Omit any line or section that does not apply:

```markdown
# ISSUE-{N}: {title}

**Type**: {refactor | rule-violation | ui | backend}
**Priority**: {high | medium | low}
**Created**: {YYYY-MM-DD}
**Tags**: [{comma-separated tags}]
**Scan scope**: {file path or perspective}   ← omit if not applicable

## Problem

{Concrete description of what is wrong and why, citing file:line where possible.}

## User's words

{Verbatim quote of the user's report.}   ← include only when the user reported it; omit otherwise

## Horizontal expansion

{Where the same pattern likely appears elsewhere in the codebase.}   ← omit if none

## Suggested fix

{Direction for the fix.}   ← omit if unknown
```

- `Type`: `refactor` (cleanup/restructure), `rule-violation` (breaks a convention/reference),
  `ui` (front-end/visual), `backend` (server/data/logic).
- `Priority`: an estimate — the user can revise it later by editing the file or `_index.yaml`.
- `Created`: today's date, `YYYY-MM-DD`.

---

## Updating the index

After writing the issue file, append an entry to `_index.yaml`'s `issues` list and bump `last_id`:

```yaml
- id: ISSUE-{N}
  title: "{title}"
  created: {YYYY-MM-DD}
  type: {type}
  scan_scope:
    - "{scope}"        # use scan_scope: [] if no scope applies
  priority: {priority}
  tags: [{tags}]
```

- `_index.yaml` (open issues, git-ignored) is the live list. Keep `last_id` ≥ every issue number used.
- `_index.archive.yaml` (closed issues + scan records, committed) is **not** edited here — it is
  managed by the `merge` skill (on close) and by `issue-scan` (scan records).

---

## Closing

Do not hand-edit closures. The `merge` skill closes issues listed in a branch document's
`## 関連イシュー` table: it moves the file to `closed/`, removes the `_index.yaml` entry, and appends
to `_index.archive.yaml`. To drop an issue without a fix, close it with `resolution: wontfix`.
