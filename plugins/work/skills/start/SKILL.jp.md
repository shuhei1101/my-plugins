# SKILL.jp.md — work:start スキル（日本語ミラー）

# work-kit:work-start — 新しい PR を始める

先にワークツリーを作成し、その中に PR ごとの単一タスクドキュメントを作成する。
これによりタスクドキュメントがメインリポジトリに作成されることを防ぐ。

---

## 作業内容

### ステップ1: 次の PR 番号を決定する

#### 条件

- 常に — 最初に実行

#### 処理

1. ユーザーが既に PR 番号またはブランチ名を指定していればその値を使う
2. そうでなければ次のコマンドを実行し、出力された番号を使う:

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/index-tool.py next-id .work/tasks/index.yaml
```

→ ステップ2 へ

#### 出力

- 次の PR 番号が確定している

---

### ステップ2: リクエストの詳細を収集する

#### 条件

- ステップ1 完了

#### 処理

1. 以下を決定する:
   - **タイトル**: フォルダ名に使う短い kebab-case ラベル
   - **タイプ**: `feat` / `fix` / `refactor` / `docs` / `chore` / `test`
   - **TODO リスト**: この PR で何をするか（チェックリストになる）
   - **ノート**: `.work/notes/` に関連ノートがあるか? なければ作るか?
   - **不明点**: 不確定・未決定の事項

→ ステップ3 へ

#### 出力

- タイトル・タイプ・TODO・ノート情報・不明点が確定している

---

### ステップ3: index.yaml にエントリを追加する（メインリポジトリ）

#### 条件

- ステップ2 完了

#### 処理

1. 次のコマンドで新規 PR エントリを追加する:

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/index-tool.py add .work/tasks/index.yaml \
  --id {N} \
  --title "PR{N} — {title}" \
  --type {type} \
  --summary "{summary}" \
  --task "{YYMMDD}_{title}"
```

→ ステップ4 へ

#### 出力

- メインリポジトリの `.work/tasks/index.yaml` に新規 PR エントリと `last_id` が更新されている

#### 補足

- `index.yaml` は `.work/tasks/.gitignore` で除外されているので master コミット不要
- 日付は 6 桁の `YYMMDD`（例: `260530`）。8 桁の `YYYYMMDD` ではない

---

### ステップ4: ワークツリーとブランチを作成する（有効な場合）

#### 条件

- ステップ3 完了

#### 処理

1. ワークツリー利用が有効かを確認する。**デフォルトで有効**であり、環境変数
   `WORK_USE_WORKTREE` を falsy 値（`false` / `0` / `no` / `off`）に設定したときのみ無効になる:

   ```bash
   v="${WORK_USE_WORKTREE:-true}"; case "${v,,}" in false|0|no|off) echo disabled;; *) echo enabled;; esac
   ```

2. **有効の場合**: `/work:worktree-create` を PR 番号・ブランチ付きで呼び出す:

   > `/work:worktree-create PR{N} {type}/{title}`

3. **無効の場合**: ワークツリー作成をスキップしてユーザーに通知する:

   > ⚠️ `WORK_USE_WORKTREE` が無効のため、ワークツリーの作成をスキップします。  
   > `.work/` フォルダ管理のみで作業を続けます。  
   > ワークツリーを使用したい場合は `settings.json` の `env` から `WORK_USE_WORKTREE` を外すか `true` に設定してください。

→ ステップ5 へ

#### 出力

- （有効）ワークツリーが `../repo-wt-PR{N}` に作成され、ブランチ `PR{N}/{type}/{title}` が存在する
- （無効）ワークツリーなし。`.work/` フォルダ管理のみで作業継続

#### 補足

##### 禁止事項

- 直接 master/main にコミットしてはならない

---

### ステップ5: タスクフォルダを判断する（自律判断）

#### 条件

- ステップ4 完了

#### 処理

1. ワークツリー内の `.work/tasks/` 配下の全フォルダ名を読む
2. 各フォルダ名（`YYMMDD_title` 形式）と今回の PR の内容を照合し、以下の基準で判断する:
   - **既存フォルダに追加**: 同じ目的・機能領域のフォルダが既にあり、この PR がその一部として収まる場合
     - 例: 機能を複数 PR に分割している場合、フォローアップ修正、関連リファクタなど
   - **新規フォルダ作成**: 関連の深い既存フォルダがない、または `.work/tasks/` が空の場合
3. 次のステップに渡す引数を確定する:
   - 既存フォルダに追加 → `--task-dir {folder_name}` を使う
   - 新規作成 → `--date {YYMMDD} --title {title}` を使う

→ ステップ6 へ

#### 出力

- タスクフォルダの戦略（新規・既存）と使用する引数が確定している

#### 補足

- ユーザーに尋ねない — 内容に基づいて自律判断する
- 迷ったら新規フォルダを作成（あとから統合可能）
- 旧来のフォルダは 8 桁 `YYYYMMDD` プレフィックスの可能性あり — そのまま放置し、新規フォルダのみ `YYMMDD` を使う

---

### ステップ6: PR ドキュメントを作成する（ワークツリー内）

#### 条件

- ステップ5 完了

#### 処理

ステップ5 の選択に応じて以下のいずれかを実行する。`--branch` 引数はフルブランチ名（`PR{N}/{type}/{title}`）で、スクリプトがスラッシュをハイフンに置換してファイル名を生成する
（例: `PR168/refactor/refactor-task-doc-structure` → `PR168-refactor-refactor-task-doc-structure.md`）:

**新規タスクフォルダの場合:**

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/setup-task.py \
  ../$(basename $(pwd))-wt-PR{N} \
  --pr {N} \
  --branch PR{N}/{type}/{title} \
  --title {title} \
  --date {YYMMDD} \
  --plugin-root ${CLAUDE_PLUGIN_ROOT}
```

**既存タスクフォルダに追加の場合:**

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/setup-task.py \
  ../$(basename $(pwd))-wt-PR{N} \
  --pr {N} \
  --branch PR{N}/{type}/{title} \
  --task-dir {existing_folder_name} \
  --title {title} \
  --plugin-root ${CLAUDE_PLUGIN_ROOT}
```

→ ステップ7 へ

#### 出力

- `../repo-wt-PR{N}/.work/tasks/{task_folder}/PR{N}-{type}-{title}.md` が作成されている

---

### ステップ7: PR ドキュメントに作業計画を記入する（ワークツリー内）

#### 条件

- ステップ6 完了

#### 処理

ワークツリー内の `PR{N}-{type}-{title}.md` を開き、テンプレートのひな形を実際の計画に置き換える。
このドキュメント 1 つにこの PR の全セクション（TODO・変更内容・テスト・QA・参考）が入る。

**`## 概要`** — 目的 / 背景を書き、`### 実施条件` サブセクションも埋める:

- `### 実施条件`: この PR を開始できる条件。`即時実施可`、または `「{他PR名}」が完了してから`。
  トリガー PR の `## 次PR候補` 行の `実施条件` カラムをそのまま反映する。

**`## 作業内容`** — タスクチェックリスト。以下の行は必須で省略・スキップ禁止:

| 完了 | 作業内容 | 対象ファイル |
|---|---|---|
| - | 不明点を `## QA`（このドキュメント内）に記録する | - |
| - | `.work/notes/` のノートを更新する | - |
| - | （実装タスクをここに記述する） | - |
| - | ルール・CLAUDE.md を整備する | - |

**`## 変更内容`** — この PR が追加・編集した実装ファイル（テスト除く）。実装が始まったら埋める。
コミットに積まれる全ファイルを列挙:

| ファイル名 | 新規/編集 | 内容 | 補足 |

**`## テスト`** — 実装に伴って追加・編集したテストファイル。
テスト変更がない場合はプレースホルダ行のまま残す。

**`## QA`** — ステップ2 の不明点を QA-XXX として記録する（下のステップ9 で追記する）。

**`## 参考ドキュメント`** — 関連ノート / 仕様へのリンク（ステップ8 のノートをここに追記する）。

**`## 関連イシュー`** — この PR が解決する `.work/issues/ISSUE-{N}` を列挙
（表形式: `| ID | 概要 | resolution |`）。`resolution` は `resolved` または `wontfix`。
**関連イシューがない場合**: `## 関連イシュー` 見出しと表ごと削除する。

**`## 関連PR`** — 直接関連する PR（先行・分割兄弟・後続）を列挙
（表形式: `| PR番号 | 概要 |`）。なければプレースホルダ行のまま。

**`## 次PR候補`** — このセッションで言及された後続 PR を列挙
（カラム: タイトル / 概要 / 実施条件）:
- 依存がなければ `即時実施可`（または `-`）
- 同じ表内の他候補に依存していれば `「{他候補タイトル}」が完了したら`

→ ステップ8 へ

---

### ステップ8: ノートドキュメントを保守する（ワークツリー内）

#### 条件

- ステップ7 完了

#### 処理

1. ワークツリー内の `.work/notes/` に関連ノートがあるか確認する
2. ある場合 → この PR の関連セクションを更新する
3. ない場合 → `${CLAUDE_PLUGIN_ROOT}/templates/note.md` から新規作成する
4. PR ドキュメントの `## 参考ドキュメント` セクションにノートへのリンクを追記する

→ ステップ9 へ

---

### ステップ9: 不明点を `## QA` セクションに記録する（ワークツリー内）

#### 条件

- ステップ8 完了

#### 処理

1. ステップ2 で確認した不明点を PR ドキュメントの `## QA` セクションに QA-XXX として追記する
2. 不明点がなければスキップ

→ ステップ10 へ

---

### ステップ10: 作成物をコミットし、ユーザーに報告し、実装を開始する

#### 処理

1. ワークツリー内で作成したファイルを全てコミットする（ブランチ: `PR{N}/{type}/{title}`）
2. 作成内容を報告: ブランチ名・ワークツリーパス・PR ドキュメントパス・ノートパス
3. 実装を開始する:
   - **QA エントリがある場合** → ユーザーに確認してから着手する
   - **QA エントリがない場合** → そのまま実装に進む

#### 補足

##### 禁止事項

- 作成したワークツリー（`PR{N}/{type}/{title}` ブランチ）以外にコミットしてはならない

##### コミット粒度

- ユーザーが理解しやすい意味単位でコミットする
- コミットを細かく分けすぎない
- 計画ドキュメント（PR ドキュメント・ノート等）と実装コードを同じコミットに混ぜない

##### コミットメッセージの言語

- このスキルが生成する全コミットメッセージは **日本語** で書く
- subject と body の両方が日本語（`Co-Authored-By:` などのメタデータ行は英語のまま可）
- Conventional commit プレフィックス（`feat:` `fix:` `chore:` 等）は英語のままで可
- 例: `chore: PR{N} のタスクドキュメントを作成 #PR{N}`
