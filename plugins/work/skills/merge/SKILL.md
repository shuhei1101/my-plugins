# merge — ブランチを親ブランチにマージ

## タスク

### ステップ 1: マージ対象ブランチを特定

会話文脈で特定できなければユーザーに聞く。

### ステップ 2: マージ先ブランチをワークツリーに取り込む

コンフリクトが master 上に流れ込まないように、先に親ブランチを現在のブランチへ取り込む。

```bash
git -C {WORKTREE_PATH} fetch origin <PARENT_BRANCH>
git -C {WORKTREE_PATH} merge origin/<PARENT_BRANCH>
```

#### コンフリクト時の取り扱い（AI 自身で文脈判断して解消）

両側の変更意図を読み、より「意味の強い」方を採用または両立させる。ユーザーへ聞くのは最後の手段。並列で複数ブランチを進めている関係で両側に正当な理由があるため「相手側採用」「自分側採用」の機械的決め打ちはしない。

##### 判断の基本

`Read` / `git show :2:<file>`（自分側）/ `git show :3:<file>`（相手側）/ `git log --all --oneline -- <file>` で両側の意図を取り、次の観点で比較する:

| 比較観点 | 「意味が強い」と判断する例 |
|---|---|
| 変更の目的 | 機能追加・バグ修正・セキュリティ修正・ハードコード削除 などの構造的変更 |
| 変更の範囲 | ロジック本体・公開 API・型定義 など影響の広い箇所 |
| 変更の最新性 | より新しいコミットメッセージで明確な理由が示されているもの |
| 弱い側 | コメント整形・ログ文言調整・改行追加・無意味なリネーム などの装飾的変更 |

##### XY コード別の進め方

`git status -s` の左 2 文字で初動を決める。最終判断は常に両側内容の比較から。

| コード | 意味 | 初動 |
|---|---|---|
| `UU` | 両側で変更 | 両側 diff を読み、意味の強い変更を残しつつ両立できる部分は両立。手動編集後 `git add` |
| `AA` | 両側で追加 | 両側を統合して `git add`。片方が雛形だけならもう片方を採用 |
| `DD` | 両側で削除 | `git rm <file>` |
| `DU` | 自分側で削除 / 相手側で変更 | 削除理由が強い → `git rm`、相手側の方が強い → `git checkout --theirs -- <file>` → `git add` |
| `UD` | 自分側で変更 / 相手側で削除 | 同様に両側意図を比較し、`git rm` か `git checkout --ours -- <file>` |

##### 解消後

1. `git status` で残りなしを確認
2. `git diff --stat HEAD` で削除件数が多すぎないか確認（master 側の追加ファイルを巻き込んでいないか）
3. `git commit`

##### 禁止事項

| No | 禁止 |
|---|---|
| 1 | `-X ours` / `-X theirs` / `--strategy-option=ours/theirs` 等の **一括自動解消** |
| 2 | ファイル指定なしの `git checkout --ours` / `git checkout --theirs` |
| 3 | サブエージェントを起動してコンフリクト解消を委譲（自分のコンテキストで判断する） |

##### 最終手段

判断不能ファイルだけ残し、`git status -s` の全行と両側 diff（`git diff :2:<file> :3:<file>`）を添えてユーザーに報告。

### ステップ 3: 親ブランチへマージ

1. メインリポジトリで親ブランチに切り替える
2. `--no-ff` でマージ:

```bash
git merge --no-ff -m "{type}: {title}" {BRANCH_NAME}
```

### ステップ 4: ワークツリーとブランチを削除

`worktree_remove` MCP ツール（work-tools サーバー）を実行:

- branch: `{BRANCH_NAME}`
- ワークツリー・ブランチ・セッショントークンが削除される
