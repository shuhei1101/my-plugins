# work:issue-scan — コードベーススキャン

毎回 1 ファイルをランダムに選んで Read し、`*-kit` プラグインの reference auto-injection
フックが返してくる reference と比較して、発見した問題を `/work:issue-save` 経由で
`.work/issues/` に記録するスキル。

---

## 概要

**前提条件**:
- `.work/issues/` が存在すること（なければ `/work:setup` を実行）
- `*-kit` 形式のプラグイン（dev-kit など、`PreToolUse(Read)` フックを持つもの）が
  1つ以上インストールされていること

**動作方針**:
- 各 `*-kit` プラグインの `PreToolUse(Read)` フックがファイル種別に応じて reference を
  自動注入してくれるため、本スキルは「対象ファイルを 1 つ選んで Read する」だけでよい
- フックは `_injection_rules.yaml` を参照して該当 reference を判断するので、
  本スキル側で pattern マッチや YAML パースを実装する必要はない
- フックの session+file-hash トークンにより、同一ファイルは 1 セッション 1 回しか注入されない

---

## 作業内容

### ステップ1: スキャン履歴を読む

#### 条件

- 常に — 最初に実行する

#### 処理内容

1. `.work/issues/` が存在するか確認する
   - 存在しない場合 → `/work:setup` を促して停止
2. `_index.archive.yaml` を読み込む（なければ空として扱う）
   - `scan_records` のエントリ（過去にスキャンしたファイル一覧）を把握する
   - `closed_issues` の `resolution: wontfix` の ID を把握する（結果から除外する）

→ ステップ2へ進む

#### 出力

- スキャン済みファイルパスの集合
- wontfix イシュー ID の集合

---

### ステップ2: スキャン対象ファイルをランダムに 1 つ選ぶ

#### 条件

- 常に — ステップ1の後に実行する

#### 処理内容

1. プロジェクトのソースファイルを列挙する
   - `find` や glob で `**/*.py`, `**/*.ts`, `**/*.tsx`, `**/*.html`, `**/*.js` などを対象に
   - `.work/`・`.git/`・`node_modules/`・`.venv/`・`venv/`・`__pycache__/`・`dist/`・`build/`・
     `.next/`・`.turbo/` などは除外する
2. `_index.archive.yaml` の `scan_records[].scope` に既に登場しているファイルを除外する
3. 残ったファイルからランダムに 1 つ選ぶ
4. 残候補が 0 件のとき: ユーザーに「すべてスキャン済みです。再スキャンしますか？」と確認し、
   Yes なら除外を解いて選び直し、No なら停止する

→ ステップ3へ進む

#### 出力

- 選ばれたファイルパス（例: `src/myapp/features/chat/service.py`）

---

### ステップ3: ファイルと関連ファイルを Read して reference を取得する

#### 条件

- 常に — ステップ2の後に実行する

#### 処理内容

1. ステップ2で選んだファイルを Read する（スキャンの主対象）
2. `*-kit` プラグインの `PreToolUse(Read)` フックが該当する場合、
   `decision: block` の reason に reference 本文が注入されてくる
   - 注入された内容にはこのファイルに適用される必須 / 任意 reference の本文が含まれる
3. **関連ファイルも追加で Read して文脈を取り込む**:
   - 同フォルダの兄弟ファイル（例: 主対象が `features/chat/service.py` なら `types.py`, `route.py`, `query.py`）
   - 主対象が依存する側 / 主対象を呼び出している側のファイル（imports を辿る）
   - 主対象がレイヤー横断の問題に該当しそうなら関連レイヤー（例: LLM フォルダ全体）
   - 関連ファイルの選定は判断に必要な範囲に絞る（広げすぎない）
   - 関連ファイル自体はスキャンの主対象ではないので `scan_records.scope` には記録しない
4. 注入がなければ「このファイルに該当する `*-kit` reference は無い」と扱い、
   ステップ6へ進む（スキャン記録だけ書く）

→ 注入あり → ステップ4へ進む / 注入なし → ステップ6へ進む

#### 出力

- 選ばれたファイルの本文
- 関連ファイルの本文（文脈用）
- フックが注入した reference 本文（無い場合もある）

---

### ステップ4: ファイルを reference と比較してイシューを発見する

#### 条件

- ステップ3で reference が注入されたときのみ実行する

#### 処理内容

1. 注入された各 reference と選ばれたファイル（および必要に応じてステップ3で読んだ関連ファイル）を照合し、以下を探す:
   - 規約違反（命名・型・コメント・スタイル）
   - アーキテクチャ違反（依存方向・レイヤー境界）
   - 改善余地（DRY 違反・冗長コード・古い書き方など、reference に記載された規約に基づくもの）
2. 関連ファイルは判断材料として使うが、イシュー本体は主対象ファイルに対して立てる
   （関連ファイルにも問題がある場合は同じイシュー内で言及するか、別スキャン回に回す）
3. `wontfix` で既にクローズされているイシューと同じ内容は除外する
4. 独立して対処可能な単位ごとに整理する

→ ステップ5へ進む

#### 出力

- 発見した問題の一覧（タイトル / タイプ / 優先度 / 該当箇所 / 修正案）

---

### ステップ5: イシューを保存する

#### 条件

- ステップ4で問題が見つかったときのみ実行する

#### 処理内容

1. 発見した各問題について `/work:issue-save` を呼び出す:
   - タイトル / タイプ / 優先度 / タグ / スコープ（= 選ばれたファイルパス）/ 問題の説明 / 修正案
   - issue-save が返す ISSUE ID を収集する

→ ステップ6へ進む

#### 出力

- 作成したイシュー ID のリスト

---

### ステップ6: スキャン記録を更新する

#### 条件

- 常に — 問題が見つからなくても必ず実行する

#### 処理内容

1. `_index.archive.yaml` の `scan_records` に以下を追記する:
   ```yaml
   scan_records:
     - date: {YYYY-MM-DD}
       skill: issue-scan
       scope: "{選ばれたファイルパス}"
       issues_found: [{ISSUE-N}, ...]   # 0 件なら空リスト
   ```
2. `_index.archive.yaml` が存在しなければ `closed_issues: []` と `scan_records: []` で新規作成する

→ ステップ7へ進む

---

### ステップ7: 結果をレポートする

#### 条件

- 常に — 最後に実行する

#### 処理内容

1. 以下をユーザーに報告する:
   - スキャンしたファイルパス
   - reference が注入されたかどうか（注入されなかった場合は対応する `*-kit` が無い）
   - 作成したイシュー数とその一覧（ID / タイトル / 優先度）
   - 問題が 0 件の場合はその旨
2. 修正予定なしの場合は `_index.archive.yaml` の `resolution: wontfix` で閉じられる旨を伝える

#### 補足

- このスキルでは `git commit` を行わない — ユーザーが確認した後にコミットする
- フックの注入によって context が膨らむが、`*-kit` 側の session+file-hash トークンが
  同一ファイルへの再注入を防ぐ
