# .work/ — work-kit タスク管理ディレクトリ

work-kit プラグインが管理するタスク・PR ライフサイクルの作業場所。
Claude はここのファイルを読み書きして作業状態を追跡する。

---

## ディレクトリ構成

| パス | 役割 |
|---|---|
| `tasks/{YYYYMMDD}_{title}/PR{N}/TODO.md` | PR の作業チェックリストと仕様参照 |
| `specs/{機能名}.md` | 機能仕様書（タスクをまたいで参照） |
| `QA.md` | 未解決事項・設計上の疑問点 |

### tasks/

タスクごとにフォルダ（`{YYYYMMDD}_{title}/`）を切り、その中に PR フォルダ（`PR{N}/`）を置く。
1 タスクに複数の PR が紐づく場合がある。

`TODO.md` は「この PR が何をするか」の唯一の正本。実装開始前に作成し、作業を通じて常に最新に保つ。
完了したタスクは `- [x]` にチェックし、マージ前に全項目が `- [x]` であることを確認する。
スコープが変わった場合は実装より先に `TODO.md` を更新する（実態とドキュメントのズレは禁止）。

### specs/

フラット構造（**サブフォルダ禁止**）。1 事実 1 ドキュメント原則に従い、同じ内容を複数ファイルに書かない。
重複する内容はリンクで解決する。

仕様書を編集するとき、実装が記録された挙動を変えるなら必ず更新する。
未決定事項が出たらその場で `QA.md` に記録し、仕様書本文に `TBD`・`要検討` を残したまま放置しない。

### QA.md

設計・実装上の未解決事項を QA-XXX 連番で管理する。

未決定事項が出たらその場で追記する。必ず推奨方式（自分が推す案と理由）を書く。「後で決める」だけの逃げは禁止。
ユーザーが決定したら内容を仕様書・ドキュメントに反映し、QA エントリをこのファイルから削除する。

---

## 規約

- 作業開始時は必ず該当 PR の `TODO.md` を読んで作業範囲を確認する
- 完了したタスクは `- [x]` にチェックする
- 仕様変更は `specs/` の該当ドキュメントにも反映する
- 疑問点・未確定事項は `QA.md` に追記する
- マージ前に `## TODO` が全て `- [x]` であることを確認する

---

## work-kit スキル

| スキル | 用途 |
|---|---|
| `/work-kit:setup` | `.work/` を初期化する（初回のみ） |
| `/work-kit:work-start` | 新規タスク・PR・TODO.md を作成する |
| `/work-kit:merge` | TODO 確認・マージ・クリーンアップを実行する |
