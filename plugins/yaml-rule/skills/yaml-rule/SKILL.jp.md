# YAML ファイル管理ルール

このルールは、アセットカタログとプロジェクト設定に使うすべてのYAMLファイルに適用されます。

## 基本原則

物理ファイル（アセット・メディア等）はどのようなフォルダ構成に置いてもよい。プログラムやAIはファイルパスをハードコードせず、**必ずYAML経由でファイルを参照する**。

## YAMLファイルの種類

### index.yaml — アセットカタログ

- カテゴリに属するアセットやファイルを一覧管理する
- プロジェクト初期に1回作成し、ファイルの追加・削除時のみ更新する
- 環境によって値が変わらない（すべての開発者・環境で共通）
- 「何が存在するか」を記述するマニフェスト

### settings.yaml — 環境設定

- `index.yaml` に登録されたアイテムのID別設定値を記述する
- 環境ごとに値が異なる（開発者・デプロイ環境によって変わる）
- `.env` ファイルのようなもの：各環境に専用のコピーが存在する
- **`settings.yaml` はリポジトリにコミットしない。** 代わりに `settings.yaml.sample` をコミットし、各開発者が自分の `settings.yaml` を作成する

### settings.yaml.sample

- `settings.yaml` のテンプレートとしてリポジトリにコミットする
- すべてのキーをプレースホルダー値または初期値で記述する
- 開発者はこのファイルを `settings.yaml` にコピーして自分の値を入力する

## 規約は YAML の外で文書化する

管理ルール・変更履歴・各フィールドの説明を YAML の冒頭コメントブロックに書かないこと。YAML はデータ。記述は最小に保つ。

これらの規約は `.claude/rules/<name>.md` に書く。`paths:` frontmatter で対象 YAML を指定すれば、Claude が該当 YAML を読み込んだときにルールが自動でコンテキストに入るので、「このファイルを開いた人が背景を把握できる」という目的は達成しつつ、データファイルを膨らませない。`.claude/rules/` の運用ルールは `claude-rule` skill を参照。

YAML 冒頭に「詳しくは `.claude/rules/assets-bgm.md` を参照」のような短いポインタコメントを置くのはOK。ただし、ルールの内容自体を YAML 内に複製してはいけない。

## ファイル構成パターン

```
{機能名}/
├── index.yaml           # アセットカタログ（コミット対象・環境共通）
├── settings.yaml        # ローカル設定（gitignored・開発者ごと）
└── settings.yaml.sample # テンプレート（コミット対象）
```

`.gitignore` に追加する：

```
settings.yaml
```

## 各ファイルの更新タイミング

| イベント | index.yaml | settings.yaml.sample | settings.yaml |
|---------|------------|----------------------|---------------|
| 新しいアセット追加 | エントリ追加 | キーをプレースホルダーで追加 | キーをローカル値で追加 |
| アセット削除 | 非アクティブ化または削除 | キーを削除 | キーを削除 |
| 新しい設定項目追加 | — | キーとコメントを追加 | キーをローカル値で追加 |
| 構造変更 | 更新 | 更新 | 手動で更新 |

## UI から書き換えられる YAML はメインリポジトリの実体を参照する

リポジトリで git worktree を使っている場合、**UI / API から実行時に書き換える YAML**（`settings.yaml`、ランタイム保存用の `*.yaml` など）はワークツリー内の自分のコピーではなく、**メインリポジトリ側の実体を参照** すること。

### なぜ必要か

ワークツリーごとに別コピーを持つと:

1. ワークツリー A で UI から設定を保存
2. ワークツリー側 YAML が更新されるが、メインリポジトリ側は変更なし
3. ワークツリーを削除したり別ブランチへ切り替えたタイミングで、保存内容が**消失**
4. ユーザーが UI で書き込んだ設定が全部飛ぶ — 一番まずい結末

### 実現方法（どちらかを採用）

**A. ファイルシステムレベル（symlink / junction）**

ワークツリーセットアップ時に `<worktree>/path/to/settings.yaml` を `<main-repo>/path/to/settings.yaml` へリンクする。アプリは通常パスで読み書きし、リンクが透過的にメインへ向ける。symlink 不可の環境ではコピーへフォールバックする。

**B. アプリレベル（runtime path 解決）**

アプリ内で `main_repo_root()` のような helper を用意し、ワークツリーから呼び出してもメインリポジトリのパスを返すようにする。検出は `git rev-parse --git-common-dir` を使う:

- メインワークツリーでは `.git` (相対パス) が返る
- linked worktree では絶対パスでメインの `.git` ディレクトリが返る

アプリコード側で runtime-editable YAML のパスを必ず `main_repo_root() / "path/to/file.yaml"` のように組み立てる。

### 適用対象

| YAML | 対象? | 理由 |
|---|---|---|
| `settings.yaml` | ✅ 対象 | UI / 設定画面から書き換える |
| `mock_notes.yaml`, `runtime_state.yaml` 等のランタイム保存用 | ✅ 対象 | アプリが API 経由で書き込む |
| `index.yaml` | ❌ 対象外 | 手で編集するカタログ。ワークツリーごとにコピーがあって通常 git マージで衝突解決すれば OK |
| `settings.yaml.sample` | ❌ 対象外 | テンプレートでコミット対象 |

### 採用方針の記録

新しい runtime-editable YAML を導入したら、対応する `.claude/rules/<name>.md` に下記を明記:

- 解決方法 (A: symlink / B: runtime helper のどちらか)
- 正本ファイルがどこに住むか (`<main-repo>/data/...` 等)
- gitignore の有無

これで他の開発者やセッションが構造を理解できる。
