# workspace:impl-review — インタラクティブ実装レビュー

現在の作業ブランチのコミット履歴を分析し、実装内容を `AskUserQuestion` ツールで選択肢形式として **最大 4 件ずつのバッチ** にまとめて提示する。ユーザーは 1 バッチ内の全項目を一括で「OK / 次へ」「もっと詳しく」「問題あり」から選べる。スマホや SSH 接続など、コードの差分を直接確認しづらい環境で確認往復回数を最小化する設計。

---

## 概要

スキルは最初に内部で「大枠リスト」（変更エリアの一覧）を作成し、これを **最大 4 件ずつのバッチ** に分割して提示する（リスト全体のプレビューはユーザーに見せない）。1 つのバッチでは `AskUserQuestion` を 1 回だけ呼び、複数アイテムを一括で回答してもらう。バッチ内で「もっと詳しく」が選ばれた項目は、そのバッチ終了後にひとつずつ深掘りループへ入る。深掘りが終わったら次のバッチへ進む。

---

## 作業内容

### ステップ 1: 対象ブランチを特定する

#### 条件

- 常に最初に実行

#### 処理内容

1. 現在の会話セッションで作業中のブランチがある場合、そのブランチを最優先で使用する
2. 引数にブランチ名（または部分一致語）が明示されていれば（例: `refactor/rename-pr-to-branch`、レガシー形式の `PR139` も可）、それを使って対応するブランチを探す:
   ```bash
   git branch --list "*{引数}*"
   ```
3. 上記どちらも該当しない場合は現在のブランチを使用する
4. ベースブランチを確認する（デフォルト: `master`）

→ ステップ 2 へ

#### 出力

- 対象ブランチとベースブランチが確定している

---

### ステップ 2: コミットと差分を分析する

#### 条件

- ステップ 1 完了

#### 処理内容

1. コミット履歴を取得する:
   ```bash
   git log {base}..{branch} --oneline
   ```
2. 変更ファイルのサマリーを取得する:
   ```bash
   git diff {base}..{branch} --stat
   ```
3. ベースからのコミットが 0 件の場合 → 「実装コミットがありません」と報告して終了

→ ステップ 3 へ

#### 出力

- コミット一覧と変更ファイルのサマリー

---

### ステップ 3: 大枠リストを内部で作成する

#### 条件

- ステップ 2 完了

#### 処理内容

1. コミットメッセージと変更ファイルを自律的に分析する
2. 関連する変更をグループ化して「変更エリア」（2〜8 件が目安）を作る:
   - 各アイテムは、ファイルタイプではなく目的・機能単位でまとめる（例: 「新スキル qa-review の追加」「plugin.json バージョン更新」）
3. 各エリアについて以下を用意する:
   - 1 行のタイトル（`question` の見出しに使う）
   - 何が変わりなぜそうしたかの 2〜3 文の説明
   - 主な関連ファイル

→ ステップ 4 へ（ユーザーへのプレビュー提示はしない）

#### 出力

- 2〜8 件の変更エリアからなる大枠リスト（内部保持）

#### 補足

- 見せる観点は AI が都度判断する（固定テンプレートなし）
- バックエンド変更: API 変更点・副作用・データモデルへの影響を中心に
- フロントエンド変更: 影響する画面・ユーザーから見える動作の変化を中心に
- 設定・インフラ変更: 有効化/無効化されたものとその影響範囲を中心に
- 変更の大きさに合わせて粒度を調整（1 ファイルの修正なら 1 件、複数機能ブランチなら 6〜8 件）

---

### ステップ 4: バッチ式インタラクティブレビュー

#### 条件

- ステップ 3 完了

#### 処理内容

大枠リストを **最大 4 件ずつのバッチに分割** して提示する。`AskUserQuestion` は 1 回の呼び出しに最大 4 件の questions を渡せるため、確認往復回数を最小化できる（例: 5 件なら 4+1、8 件なら 4+4）。

各バッチについて、以下を実行する:

1. `AskUserQuestion` を **1 回だけ** 呼び出し、そのバッチの全アイテムを `questions` 配列にまとめて渡す。各 question は次のとおり:
   - **question**: そのアイテムの 2〜3 文の説明
   - **header**: アイテム番号と短縮タイトル（12 文字以内）。例: `1/8 qa-review`
   - **options**:
     - `OK / 次へ` — 理解した
     - `もっと詳しく` — このエリアをさらに詳しく説明してほしい
     - `問題あり` — このエリアに懸念がある。フラグを立てる
   - **multiSelect**: false

2. バッチの回答が一括で返ってきたら、各アイテムについて以下を集計する:
   - `OK / 次へ` → 何もしない
   - `もっと詳しく` → そのバッチ終了後に深掘りキューへ入れる
   - `問題あり` → フラグ付きで記録する

3. バッチ内で `もっと詳しく` が選ばれたアイテムがあれば、それぞれについて順番に深掘りループを回す（深掘りはバッチ化できない・1 アイテムずつ）:
   - そのエリアの詳細情報を提示する（具体的なコード変更・採用理由・リスク等）
   - `AskUserQuestion` を呼び出す:
     - **question**: 「さらに深掘りしますか？」
     - **options**: `OK / 終わり` / `別の角度から説明して` / `問題あり`
   - ユーザーが `OK / 終わり` または `問題あり` を選ぶまで続ける

4. 現在のバッチの深掘りがすべて終わったら、次のバッチへ進む

→ ステップ 5 へ

#### 補足

##### なぜバッチ化するか

旧方式は 1 アイテムにつき 1 回の `AskUserQuestion` 呼び出しだったため、8 アイテムあると確認往復が 8 回発生していた。スマホや SSH では特に負担が大きい。`AskUserQuestion` は 1 回に最大 4 件まで questions を受け取れるので、8 アイテムなら 4+4 の 2 回の往復で済む（深掘り分は別途加算）。

##### バッチサイズの選び方

- 大枠リスト総数 ≦ 4 → 1 バッチで全件
- 5〜8 → 4 + 残り、または偶数等分
- 9 以上 → 4 件ずつ均等に分割
- 1 バッチを 4 件未満にする運用上の理由はない（深掘りは別ループなので 4 件全件を1度に投げて問題ない）

---

### ステップ 5: 完了レポートを出力する

#### 条件

- 全アイテムのレビューが完了（ステップ 4 完了）

#### 処理内容

1. 集計を出力する:
   - レビューしたアイテムの総数
   - フラグが立ったアイテム（あれば）とそのタイトル
2. フラグ付きアイテムがある場合 → 次のアクションを提案する（修正・QA 追記等）
3. フラグなしの場合 → 「すべての実装内容を確認しました。」

→ 完了
