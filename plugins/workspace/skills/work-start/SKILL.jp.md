# workspace:work-start — ブランチを新規作成

先にワークツリーを作成し、その中に1ブランチあたり1つのタスクドキュメントを作成する。
これによりタスクドキュメントがメインリポジトリに作成されることを防ぐ。

> **ブランチ名規則**: ブランチは `{type}/{title}` の形式を使用します（`PR{N}/` プレフィックスなし）。
> ワークツリーはブランチを反映して `{repo}-wt-{type}-{title}` となります。
> タスクドキュメントのファイル名はブランチ名からスラッシュをハイフンに置換したものです
> （`feat/foo-bar` → `feat-foo-bar.md`）。内部の数値IDは引き続き `index.yaml`
> で追跡されます（コミット、アーカイブメタデータでの相互参照用）が、
> ブランチ名、ワークツリーパス、またはタスクドキュメントのファイル名には現れません。

---

## Tasks

### Step 1: ブランチ名を決定する

#### 条件

- 常に — 最初に実行

#### 処理

1. リクエストされた作業からブランチサフィックスを決定する：
   - **Type**: `feat` / `fix` / `refactor` / `docs` / `chore` / `test`
   - **Title**: 短い kebab-case ラベル（作業の説明）
2. 完全なブランチ名は `{type}/{title}` です（例：`refactor/rename-pr-to-branch`）。
3. `index.yaml` ブックキーピング用の内部IDを予約します（アーカイブおよびコミット
   相互参照で使用されます — ブランチ名自体には現れません）：

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/index-tool.py next-id .work/tasks/index.yaml
```

→ Step 2 へ進む

#### 出力

- ブランチ名 `{type}/{title}` が決定されている
- 内部ID `{N}` が予約されている

---

### Step 2: リクエストの詳細を収集する

#### 条件

- Step 1 完了

#### 処理

1. 以下を決定する：
   - **TODO リスト**: このブランチで何をするか（チェックリストになる）
   - **Note**: `.work/notes/` に関連ノートが存在するか？ それとも作成が必要か？
   - **未解決の質問**: 不確定・未決定の事項があるか

→ Step 3 へ進む

#### 出力

- TODO リスト、ノート情報、未解決の質問が確認されている

---

### Step 3: index.yaml にエントリを追加する（メインリポジトリ）

#### 条件

- Step 2 完了

#### 処理

1. 次のコマンドで新規ブランチエントリを追加する：

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/index-tool.py add .work/tasks/index.yaml \
  --id {N} \
  --title "{type}/{title}" \
  --type {type} \
  --summary "{summary}" \
  --task "{YYMMDD}_{title}"
```

→ Step 4 へ進む

#### 出力

- `.work/tasks/index.yaml` が新規ブランチエントリと `last_id` で更新されている（メインリポジトリ）

#### 補足

- `index.yaml` は `.work/tasks/.gitignore` で除外されているため、master へのコミット不要
- 6桁の `YYMMDD`（例：`260530`）を使用します。8桁の `YYYYMMDD` 形式ではありません
- `--id {N}` は Step 1 で予約した内部の数値ID です。このIDはYAML行に記録されますが、
  ブランチ / ワークツリー / ファイル名には埋め込まれません
- `--title` はブランチ名を行タイトルとして記録します（`PR{N}` プレフィックスなし）

---

### Step 4: ワークツリーとブランチを作成する（有効な場合）

#### 条件

- Step 3 完了

#### 処理

1. ワークツリー使用が有効かを確認します。**デフォルトで有効**です。無効にするには、
   `WORKSPACE_USE_WORKTREE` 環境変数を falsy 値（`false` / `0` / `no` / `off`）に設定します：

   ```bash
   v="${WORKSPACE_USE_WORKTREE:-true}"; case "${v,,}" in false|0|no|off) echo disabled;; *) echo enabled;; esac
   ```

2. **有効の場合**: `/workspace:work-add` をブランチ名で呼び出します：

   > `/workspace:work-add {type}/{title}`

3. **無効の場合**: ワークツリー作成をスキップしてユーザーに通知します：

   > ⚠️ `WORKSPACE_USE_WORKTREE` が無効のため、ワークツリーの作成をスキップします。  
   > `.work/` フォルダ管理のみで作業を続けます。  
   > ワークツリーを使用したい場合は `settings.json` の `env` から `WORKSPACE_USE_WORKTREE` を外すか `true` に設定してください。

→ Step 5 へ進む

#### 出力

- （有効）ワークツリーが `../{repo}-wt-{type}-{title}` に作成され、ブランチ `{type}/{title}` が存在する
- （無効）ワークツリーなし。`.work/` フォルダ管理のみで作業継続

#### 補足

##### 禁止事項

- 直接 master/main にコミットしてはならない

---

### Step 5: タスクフォルダを判断する（自律判断）

#### 条件

- Step 4 完了

#### 処理

1. ワークツリー内の `.work/tasks/` 配下のすべてのフォルダ名を読む
2. 各フォルダ名（`YYMMDD_title` 形式）と現在のブランチの目的を比較して決定する：
   - **既存フォルダに追加**: 既存フォルダが同じ目的または機能領域をカバーしており、
     このブランチが自然にその一部として適合する場合
     - 例：機能を複数のブランチに分割、フォローアップ修正、関連リファクタリング
   - **新規フォルダ作成**: 関連性の深い既存フォルダがない場合、または `.work/tasks/` が空の場合
3. 次のステップに渡す引数を確定する：
   - 既存フォルダに追加 → `--task-dir {folder_name}` を使用
   - 新規作成 → `--date {YYMMDD} --title {title}` を使用

→ Step 6 へ進む

#### 出力

- タスクフォルダの戦略（新規または既存）と使用する引数が確定している

#### 補足

- ユーザーに尋ねない — 内容に基づいて自律的に決定する
- 迷った場合は新規フォルダを作成します（フォルダは後から統合可能）
- レガシーフォルダは 8桁の `YYYYMMDD` プレフィックスを使用している可能性があります —
  そのまま保持し、新規フォルダのみ `YYMMDD` を使用します

---

### Step 6: ブランチドキュメントを作成する（ワークツリー内）

#### 条件

- Step 5 完了

#### 処理

Step 5 の選択に応じて、以下のいずれかを実行します。`--branch` 引数はブランチ名（`{type}/{title}`）です。
スクリプトがスラッシュをハイフンに置換してファイル名を生成します
（例：`refactor/rename-pr-to-branch` → `refactor-rename-pr-to-branch.md`）：

**新規タスクフォルダの場合：**

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/setup-task.py \
  ../$(basename $(pwd))-wt-{type}-{title} \
  --id {N} \
  --branch {type}/{title} \
  --title {title} \
  --date {YYMMDD} \
  --plugin-root ${CLAUDE_PLUGIN_ROOT}
```

**既存タスクフォルダに追加する場合：**

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/setup-task.py \
  ../$(basename $(pwd))-wt-{type}-{title} \
  --id {N} \
  --branch {type}/{title} \
  --task-dir {existing_folder_name} \
  --title {title} \
  --plugin-root ${CLAUDE_PLUGIN_ROOT}
```

→ Step 7 へ進む

#### 出力

- `../{repo}-wt-{type}-{title}/.work/tasks/{task_folder}/{type}-{title}.md` が作成されている

---

### Step 7: ブランチドキュメントに作業計画を記入する（ワークツリー内）

#### 条件

- Step 6 完了

#### 処理

ワークツリー内に作成された `{type}-{title}.md` を開き、テンプレートのプレースホルダ内容を
実際の計画に置き換えます。このドキュメントには、このブランチのすべてのセクション —
TODO、バリエーション、QA、参考資料 — が1つのファイルに含まれます。

**`## 概要`** — 目標 / 背景を記載し、`### 実施条件` サブセクションも入力します：

- `### 実施条件`: このブランチをいつ開始できるか。`即時実施可`、または `「{他ブランチ名}」が完了してから`。
  トリガーブランチの `## 次ブランチ候補` 行の `実施条件` カラムを反映します。

**`## 作業内容`** — タスクチェックリスト。以下の行は必須であり、削除またはスキップしてはいけません：

| 完了 | 作業内容 | 対象ファイル |
|---|---|---|
| - | 未解決の質問を `## QA`（このドキュメント）に記録する | - |
| - | `.work/notes/` のノートドキュメントを更新する | - |
| - | （実装タスク：ブランチ固有の作業に置き換える） | - |
| - | ルール / CLAUDE.md を更新する | - |

**`## 変更内容`** — このブランチが追加または変更する実装ファイル（テスト除く）。実装開始時に入力します —
コミットに含まれるすべてのファイルをリストします：

| ファイル名 | 新規/編集 | 内容 | 補足 |

**`## テスト`** — 実装に伴って追加または変更されたテストファイル。このブランチにテスト変更がない場合は、
プレースホルダ行のまま保持します。そうでない場合は各テストファイルをリストします。

**`## QA`** — Step 2 の未解決の質問をここに QA-XXX エントリとして記録します
（Step 9 以下で追加）。

**`## 参考ドキュメント`** — 関連ノート / 仕様へのリンク（Step 8 のノートはここに追加）。

**`## 関連イシュー`** — このブランチが解決する `.work/issues/ISSUE-{N}` エントリをリストします
（テーブル形式：`| ID | 概要 | resolution |`）。`resolution` は `resolved` または `wontfix` です。
**関連イシューがない場合**: `## 関連イシュー` 見出しとテーブル全体を削除します。

**`## 関連ブランチ`** — このブランチと直接関連するブランチ（先行、分割兄弟、
後続）をリストします（テーブル形式：`| ブランチ | 概要 |`）。ない場合はプレースホルダ行のまま保持します。

**`## 次ブランチ候補`** — このセッション中に言及された後続ブランチをリストします
（カラム：title / summary / 実施条件）：
- 候補に依存がない場合は `即時実施可`（または `-`）
- 候補が同じテーブル内の別の候補に依存する場合は `「{他候補title}」が完了したら`

→ Step 8 へ進む

---

### Step 8: ノートドキュメントを保守する（ワークツリー内）

#### 条件

- Step 7 完了

#### 処理

1. ワークツリー内の `.work/notes/` で関連ノートを確認します
2. 見つかった場合 → このブランチの関連セクションを更新します
3. 見つからない場合 → `${CLAUDE_PLUGIN_ROOT}/templates/note.md` のテンプレートから新規作成します
4. ブランチドキュメントの `## 参考ドキュメント` セクションにノートへのリンクを追加します

→ Step 9 へ進む

---

### Step 9: 未解決の質問を `## QA` セクションに記録する（ワークツリー内）

#### 条件

- Step 8 完了

#### 処理

1. Step 2 の未解決の質問をブランチドキュメントの `## QA` セクションに QA-XXX エントリとして追加します
2. 未解決の質問がない場合はスキップします

→ Step 10 へ進む

---

### Step 10: 作成内容をコミットし、ユーザーに報告し、実装を開始する

#### 処理

1. ワークツリー内に作成したすべてのファイルをコミットします（ブランチ：`{type}/{title}`）
2. 作成内容をユーザーに報告します：ブランチ名、ワークツリーパス、ブランチドキュメントパス、ノートパス
3. 実装を開始します：
   - **QA エントリが存在する場合** → 実装開始前にユーザーに確認を求めます
   - **QA エントリがない場合** → すぐに実装に進みます

#### 補足

##### 禁止事項

- 作成されたワークツリー（`{type}/{title}` ブランチ）以外のどこにもコミットしてはならない

##### コミット粒度

- ユーザーが理解しやすい意味のある単位でコミットします
- コミットを細かく分けすぎません
- 計画ドキュメント（ブランチドキュメント、ノートなど）と実装コードを同じコミットに混ぜません

##### コミットメッセージの言語

- このスキルが生成するすべてのコミットメッセージは **日本語** で書かれます
- subject と body の両方が日本語（`Co-Authored-By:` などのメタデータ行は英語のままで可）
- Conventional commit プレフィックス（`feat:` `fix:` `chore:` など）は英語のままで可
- 例：`chore: {type}/{title} のブランチドキュメントを作成`
