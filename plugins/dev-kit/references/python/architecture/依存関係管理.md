# Dependency Direction Rules

---

## One-way dependencies

```
features / server
        ↓
   integrations / runtime
        ↓
      shared
```

- `shared/` **depends on nothing** (the bottom layer)
- `integrations/` / `runtime/` depend only on `shared/`
- `features/` / `server/` depend on `integrations/` / `runtime/` / `shared/`
- **Cross-references within the same layer (features ↔ features, integrations ↔ integrations) are basically prohibited**

---

## Violation examples

```python
# ❌ shared が features に依存
# {pkg}/shared/logger.py
from {pkg}.features.chat.types import ChatMessage   # NG

# ❌ integrations が features に依存
# {pkg}/integrations/llm/openai_client.py
from {pkg}.features.chat.service import generate_response   # NG

# ❌ feature が他の feature に直接依存
# {pkg}/features/chat/service.py
from {pkg}.features.users.service import find_user   # NG（features 同士の相互参照）
```

## When a same-layer reference becomes necessary

### Pattern 1: Lift into shared as a commonality

`features/chat/` and `features/auto_tweet/` need the same "message formatting logic":

```python
# 共通化して shared に置く
# {pkg}/shared/text.py
def strip_control_chars(s: str) -> str: ...
def truncate(s: str, max_len: int) -> str: ...

# 両 feature から shared を参照
# {pkg}/features/chat/service.py
from {pkg}.shared.text import strip_control_chars

# {pkg}/features/auto_tweet/service.py
from {pkg}.shared.text import truncate
```

### Pattern 2: DIP (dependency inversion) via function-type aliases

"Chat needs User, but a User → Chat dependency also seems to be emerging." Use **function types** to create an abstraction boundary and invert the dependency:

```python
# ❌ Bad: 直接依存
# {pkg}/features/chat/service.py
from {pkg}.features.users.service import find_user_by_id   # NG（features 同士）

async def generate_response(user_id: UserId, msg: str) -> str:
    user = find_user_by_id(user_id)
    ...
```

```python
# ✅ Good: 関数の型で受ける（DIP）
# {pkg}/features/chat/types.py
from {pkg}.shared.types import UserId

type FindUserForChat = Callable[[UserId], UserMinimal | None]

@dataclass(frozen=True, slots=True, kw_only=True)
class UserMinimal:
    id: UserId
    name: str

# {pkg}/features/chat/service.py
from .types import FindUserForChat

async def generate_response(
    user_id: UserId,
    msg: str,
    *,
    find_user: FindUserForChat,
) -> str:
    user = find_user(user_id)
    ...

# {pkg}/main.py で配線
from {pkg}.features.users.service import find_user_by_id as raw_find_user

def _adapt_user_for_chat(id: UserId) -> UserMinimal | None:
    u = raw_find_user(id, find=...)
    return UserMinimal(id=u.id, name=u.name) if u else None

wired_chat = partial(generate_response, find_user=_adapt_user_for_chat)
```

Key points:
- `features/chat/` knows only about `UserMinimal` (a Chat-perspective DTO)
- It does not know the full `User` from `features/users/`
- Wiring (the adapter) is done in `main.py`
- This is **DIP via function-type aliases**, not "DIP via class inheritance"

Place the abstraction-boundary type in the **source feature's `types.py`** or in `shared/types.py`.

### Pattern 3: server orchestrates multiple features

Place the responsibility of composing multiple features in `server/`:

```python
# {pkg}/server/routes/chat.py
from fastapi import APIRouter
from {pkg}.features.users.service import find_user_by_id
from {pkg}.features.chat.service import generate_response

router = APIRouter()

@router.post("/chat")
async def post_chat(body: ChatRequest, ...) -> ChatResponse:
    # 複数 feature を server レイヤで組み合わせる（features 同士は知らない）
    user = find_user_by_id(body.user_id, find=...)
    text = await generate_response(body.text, chat=...)
    return ChatResponse(user_name=user.name, text=text)
```

## Dependency direction check

Violations are detectable just by inspecting the `import` statements at the top of files:

```bash
# features から features への import がないか
grep -rn "from {pkg}.features\." src/{pkg}/features/

# shared が外を import してないか
grep -rn "from {pkg}\." src/{pkg}/shared/ | grep -v "from {pkg}.shared\."

# integrations が features を import してないか
grep -rn "from {pkg}.features\." src/{pkg}/integrations/
```

You can integrate this into CI (consider ruff's `tidy-imports` plugin, etc.).

---

## Exception: type-only imports

When you want to reference a type without creating a runtime dependency, use `TYPE_CHECKING`:

```python
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from {pkg}.features.users.types import User   # 型としてだけ使う
```

This is not a "runtime dependency," so it can be treated as a lenient violation of the dependency-direction rule
(but the priority is still **a design that does not reference at all** in the first place).

---

## Summary

- `shared` depends on nothing (bottom layer)
- `integrations` / `runtime` depend only on `shared`
- `features` / `server` depend only on lower layers
- Same-layer cross-references are prohibited — lift into `shared` or use DIP via function-type aliases
- The responsibility of combining multiple features goes into `server/`
