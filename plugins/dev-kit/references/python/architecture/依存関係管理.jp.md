# 依存方向のルール

> このファイルは `依存パッケージ管理.md` の日本語ミラーです。

---

## 一方向の依存

```
features / server
        ↓
   integrations / runtime
        ↓
      shared
```

- `shared/` は **誰にも依存しない**（最下層）
- `integrations/` / `runtime/` は `shared/` のみに依存
- `features/` / `server/` は `integrations/` / `runtime/` / `shared/` に依存
- **同層内（features 同士、integrations 同士）の相互参照は基本禁止**

---

## 違反例

```python
# ❌ shared が features に依存
# {pkg}/shared/logger.py
from {pkg}.features.chat.types import ChatMessage   # NG

# ❌ integrations が features に依存
# {pkg}/integrations/llm/openai_client.py
from {pkg}.features.chat.service import generate_response   # NG

# ❌ feature が他の feature に直接依存
# {pkg}/features/chat/service.py
from {pkg}.features.users.service import find_user   # NG（features 同士の相互参照）
```

## 同層内の参照が必要になった場合

### パターン 1: shared に共通化して引き上げる

`features/chat/` と `features/auto_tweet/` が同じ「メッセージ整形ロジック」を使いたい:

```python
# 共通化して shared に置く
# {pkg}/shared/text.py
def strip_control_chars(s: str) -> str: ...
def truncate(s: str, max_len: int) -> str: ...

# 両 feature から shared を参照
# {pkg}/features/chat/service.py
from {pkg}.shared.text import strip_control_chars

# {pkg}/features/auto_tweet/service.py
from {pkg}.shared.text import truncate
```

### パターン 2: 関数の型エイリアスで DIP（依存性逆転）

「Chat が User を必要とするが、User → Chat の依存も生まれそう」というケース。
**関数の型** で抽象境界を作って依存を逆転する:

```python
# ❌ Bad: 直接依存
# {pkg}/features/chat/service.py
from {pkg}.features.users.service import find_user_by_id   # NG（features 同士）

async def generate_response(user_id: UserId, msg: str) -> str:
    user = find_user_by_id(user_id)
    ...
```

```python
# ✅ Good: 関数の型で受ける（DIP）
# {pkg}/features/chat/types.py
from {pkg}.shared.types import UserId

type FindUserForChat = Callable[[UserId], UserMinimal | None]

@dataclass(frozen=True, slots=True, kw_only=True)
class UserMinimal:
    id: UserId
    name: str

# {pkg}/features/chat/service.py
from .types import FindUserForChat

async def generate_response(
    user_id: UserId,
    msg: str,
    *,
    find_user: FindUserForChat,
) -> str:
    user = find_user(user_id)
    ...

# {pkg}/main.py で配線
from {pkg}.features.users.service import find_user_by_id as raw_find_user

def _adapt_user_for_chat(id: UserId) -> UserMinimal | None:
    u = raw_find_user(id, find=...)
    return UserMinimal(id=u.id, name=u.name) if u else None

wired_chat = partial(generate_response, find_user=_adapt_user_for_chat)
```

ポイント:
- `features/chat/` は `UserMinimal` だけを知っている（Chat 視点の DTO）
- `features/users/` の `User` 全体を知らない
- 配線（adapter）は `main.py` で行う
- 「クラス継承による DIP」ではなく **関数の型エイリアスで DIP**

抽象境界の型は **抽出元 feature の `types.py`** または `shared/types.py` に置く。

### パターン 3: server が複数 feature をオーケストレーション

複数 feature を組み合わせる責務は `server/` 側に置く:

```python
# {pkg}/server/routes/chat.py
from fastapi import APIRouter
from {pkg}.features.users.service import find_user_by_id
from {pkg}.features.chat.service import generate_response

router = APIRouter()

@router.post("/chat")
async def post_chat(body: ChatRequest, ...) -> ChatResponse:
    # 複数 feature を server レイヤで組み合わせる（features 同士は知らない）
    user = find_user_by_id(body.user_id, find=...)
    text = await generate_response(body.text, chat=...)
    return ChatResponse(user_name=user.name, text=text)
```

## 依存方向チェック

ファイル先頭の `import` 文を見るだけで違反を検出できる:

```bash
# features から features への import がないか
grep -rn "from {pkg}.features\." src/{pkg}/features/

# shared が外を import してないか
grep -rn "from {pkg}\." src/{pkg}/shared/ | grep -v "from {pkg}.shared\."

# integrations が features を import してないか
grep -rn "from {pkg}.features\." src/{pkg}/integrations/
```

CI に組み込んでもよい（ruff の `tidy-imports` プラグイン等も検討）。

## 例外: 型のみインポート

実行時依存を作らずに型だけ参照したい場合は `TYPE_CHECKING` を使う:

```python
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from {pkg}.features.users.types import User   # 型としてだけ使う
```

これは「実行時依存」ではないので、依存方向ルールの違反としては緩く扱える
（ただし基本は **そもそも参照しない設計**を優先）。

---

## まとめ

- `shared` は誰にも依存しない（最下層）
- `integrations` / `runtime` は `shared` のみ
- `features` / `server` は下層のみに依存
- 同層内相互参照は禁止 — `shared` への引き上げ or 関数の型エイリアスで DIP
- 複数 feature の組み合わせ責務は `server/` に置く
