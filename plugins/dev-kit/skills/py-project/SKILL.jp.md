# dev-kit:py-project — Python プロジェクト（新規 or 既存）

本格 Python プロジェクトを扱う。新規ならゼロからレイヤー構造で生成し、
既存なら dev-kit 規約に照らしてレビュー・拡張・修正する。

---

## 作業内容

### ステップ1: 規約を読み込む

共通 Python 規約をすべて読み込む：

```
{plugin_root}/references/python.md
```

プラグインルートはこのスキルファイルの2階層上（例：`Base directory: .../skills/py-project` → プラグインルートは `.../{plugin-name}/`）。

タスクの内容によって全セクションを使用する。

→ ステップ2へ

---

### ステップ2: モード判定（新規 / 既存）

#### 処理内容

新規プロジェクト作成か既存プロジェクト対応かを判定する：

| シグナル | モード |
|---|---|
| 「新規」「create a new project」「土台から作りたい」、まだプロジェクトファイルがない | **新規** — ステップ3へ |
| 「このコード見て」「機能追加」「リファクタ」「レビュー」、既にプロジェクトが存在する | **既存** — ステップ9へ |

不明な場合はユーザーに確認する。判定後、分岐：

- **新規プロジェクト** → ステップ3へ進む（新規プロジェクトの要件ヒアリング）
- **既存プロジェクト** → ステップ9へスキップ（既存プロジェクト構造把握）

---

## 新規プロジェクトの流れ（ステップ3〜8）

### ステップ3: 要件ヒアリング

#### 処理内容

1. プロジェクト名とパッケージ名（`snake_case`）を確認。
2. プロジェクトを説明する：どんな問題を解決するか？誰が呼び出すか？
3. 主要ユースケースを列挙（3〜5個の動詞：「注文を処理する」「レポートを生成する」など）。
4. 外部依存を特定：データベース・API・ファイルシステム・メッセージキュー。
5. インターフェース種別を確認：CLI / FastAPI / tkinter GUI / バックグラウンドワーカー。
6. 環境変数の要件を確認。

→ ステップ4へ

---

### ステップ4: レイヤー設計

#### 処理内容

1. コードをどのレイヤーに分けるかを決定する（フォルダ名は自由 — プロジェクトに合う形で）。
2. 外部サービスに触れるコードを特定し、境界レイヤーに分離する計画を立てる。
3. ビジネスロジック層で外部境界ごとの `Protocol` インターフェースを定義する。
4. 境界レイヤーの具象実装を計画する（DB クライアント・HTTP アダプター・ファイルアダプター等）。
5. コンポジションルートの配置を確定：全具象クラスをどこで組み合わせるか？
6. コード生成前にユーザーへレイヤー計画を提示して確認を得る。

→ ステップ5へ

#### 出力

- レイヤー計画確認済み：ビジネスロジック・外部境界・それらの Protocol インターフェース

---

### ステップ5: プロジェクトスキャフォールド生成

#### 処理内容

1. レイヤー計画に基づいてディレクトリ構造を作成（参考：規約の「プロジェクトフォルダ構成」）。
2. Python `>= 3.11`・依存ライブラリは `~=` で指定した `pyproject.toml` を作成。
3. `.gitignore` を作成（`.env`・`__pycache__/`・`*.pyc`・`venv/`・`.venv/`・`log/`・`cache/` を含む）。
4. `.env.sample` を作成（全環境変数キーをプレースホルダーで記述）。
5. Windows の場合のみ：`setup/setup_venv.bat`（ASCII のみ）と `activate.bat` を作成。Linux / macOS はスキップ。
6. 空フォルダ（`log/` など）に `.gitkeep` を置く。
7. 計画した全モジュールのスタブファイルを作成（正しいインポートと型スタブのみ）。
8. ロガー仕様に従って `logger.py` を作成。
9. `PROJECT_ROOT` と `LOG_DIR` のみを定義した `constants.py` を作成 — マジックナンバーや文字列は書かない。

→ ステップ6へ

#### 補足

##### 禁止事項

- `.bat` ファイルを `bat/` サブフォルダに置かない — プロジェクトルート直下のみ（Windows のみ）
- 空フォルダに `README.md` を置かない — `.gitkeep` のみ使用
- クラス本体内で具象クラスをインスタンス化しない — コンストラクタ経由でインジェクト
- 設定値・URL・ポート・パス・認証情報をソースコードにハードコードしない

---

### ステップ6: 依存性注入の配線

#### 処理内容

1. 全外部境界インターフェースの `Protocol` 定義を作成。
2. コンポジションルート（`main.py` or `container.py`）で全具象実装をインスタンス化してインジェクト。
3. 確認：高レベルのビジネスロジッククラスが外部ライブラリの具象クラスを直接インポートしていないこと。
4. 規約に従って Strategy / Factory / Decorator パターンを適切に適用。

→ ステップ7へ

#### 出力

- 全依存はコンポジションルートから流れる。ビジネスロジック層は Protocol のみインポートする。

---

### ステップ7: 連携ルールを作成する

スキャフォールド生成後、実装・ドキュメント・テストを同期させるためのルールを作成する。
各ルールの作成には `/claude-kit:rule-creator` スキルを使用する。

#### 作成するルール

1. **クラス構造連携** — Protocol と具象実装クラスをリンクする。
   トリガー：継承ツリーまたは Protocol 実装クラスのいずれかが変更されたとき。
   チェック：階層全体への波及確認（シグネチャ・LSP・兄弟クラスへの影響）。

2. **設定 ↔ ソース連携** — 設定ファイル（`.yaml`・`.toml`・`.env`・`.json`）と、それを読み込むソースファイルをリンクする。
   トリガー：設定ファイルまたは設定読み込みソースが変更されたとき。
   チェック：追加・変更・削除されたキーが両側に反映されているか確認。

3. **ソース ↔ テスト連携** — ソースファイルとテストファイルをリンクする。
   トリガー：ソースファイルが変更されたとき。
   チェック：対応するテストファイルが更新されているか確認。

#### 処理内容

上記の各ルールに対して `/claude-kit:rule-creator` を実行し、以下を伝える：
- リンクするファイル（glob パターン）
- トリガー条件
- 実行するチェック内容

全ルール作成後にコミット：
```
git add .claude/rules/ .claude/rules-jp/ && git commit -m "chore: add dev-kit rules"
```

→ ステップ8へ

#### 出力

- `/claude-kit:rule-creator` 経由で3つのルールが `.claude/rules/` と `.claude/rules-jp/` に作成済み

---

### ステップ8: テスト雛形の作成

#### 処理内容

1. 共有 pytest フィクスチャを含む `tests/conftest.py` を作成。
2. 環境変数モッキングヘルパー `tests/mocks/mock_env.py` を作成。
3. 外部 API / DB クライアントのスタブ `tests/mocks/mock_externals.py` を作成。
4. 計画した各ユースケースに対応する `tests/{feature}/test_{feature}.py` スタブを作成。
5. テストは外部 I/O 境界のみモック — 個々のメソッドの単体テストは書かない。

→ 完了（新規プロジェクトの流れ終了）

---

## 既存プロジェクトの流れ（ステップ9〜13）

### ステップ9: プロジェクト構造を把握する

#### 処理内容

1. プロジェクトのトップレベルディレクトリ一覧を読む。
2. レイヤー構造を特定：DDD を採用しているか？どのレイヤーが存在するか？
3. `pyproject.toml` を読んで依存関係とパッケージ設定を把握する。
4. メインエントリーポイントと既存テストを特定する。
5. 既存の `.claude/rules/` ファイルを確認する。

→ ステップ10へ

---

### ステップ10: 品質チェック

#### 処理内容

1. 命名規則（モジュール・クラス・関数・変数）を規約と照合する。
2. 型ヒントのカバレッジを確認 — 欠けている箇所を報告する。
3. SOLID 違反を確認する：
   - SRP：変更理由が複数あるクラスはないか？
   - OCP：Strategy パターンに置き換えるべき if/elif チェーンはないか？
   - DIP：高レベルクラス内で具象クラスをインスタンス化していないか？
4. レイヤー分離を確認する：
   - ビジネスロジックが外部ライブラリを直接インポートしていないか？
   - 全外部サービス呼び出しは `Protocol` インターフェース経由か？
   - 具象クラスのインスタンス化がコンポジションルートに集約されているか？
5. ハードコードを確認する：
   - URL・ポート・ファイルパス・認証情報・しきい値がソースコードに埋め込まれていないか？
   - 設定値は `.env` / 設定ファイル経由で `config.py` や `constants.py` から読み込んでいるか？
6. 重複ロジックを確認する：
   - 複数箇所に似たようなロジックが繰り返されていないか？
   - 抽象クラス・基底クラス・共有関数にまとめられる箇所はないか？
7. システム境界での Pydantic 使用状況を確認する。
8. 調査結果を報告する。レビューのみの依頼ならここで終了してレポートを提示する。

→ 実装が必要な場合はステップ11へ

---

### ステップ11: 変更を実装する

#### 処理内容

1. タスクを実行する（機能追加・リファクタ・バグ修正）。
2. 参考資料の規約をすべて適用する。
3. 新規・変更コードに型ヒントを全箇所付ける。
4. タスクに必要な範囲を超えた抽象化は加えないが、新規モジュール追加時は拡張性を考慮した設計にする。
5. 依存性はコンストラクタ経由でインジェクトする — クラス本体内で具象クラスをインスタンス化しない。
6. `print()` / ロガー出力は英語のみ。

→ ステップ12へ

---

### ステップ12: ルール照合

#### 処理内容

1. 今回のタスクで以下が変更されたかを確認する：
   - 抽象クラス・Protocol・それらを実装する具象クラス
   - 設定ファイル（`.yaml`・`.toml`・`.env`・`.json`）
   - 設定ファイルを読み込むソースファイル
   - 対応するテストファイルが存在するソースファイル
2. 変更種別に応じてルールを適用する：
   - **クラス構造変更** → 継承ツリー / Protocol 実装クラスへの波及を確認
   - **設定変更** → 対応するソースファイルを確認（またはその逆）
   - **ソース変更** → 対応するテストファイルの更新が必要か確認
3. プロジェクトに `.claude/rules/` がなければ `/claude-kit:rule-creator` を使ってルールを今すぐ作成する（クラス構造連携 / 設定↔ソース連携 / ソース↔テスト連携）。

→ ステップ13へ

---

### ステップ13: テストを更新する

#### 処理内容

1. 変更したソースファイルに対応するテストファイルを特定する（ミラーパス：`src/foo/bar.py` → `tests/foo/test_bar.py`）。
2. 変更した動作に対するテストケースを更新または新規作成する。
3. テストは外部 I/O 境界（DB・API・ファイルシステム）のみモック — 個々のメソッドの単体テストは書かない。
4. `pytest` を実行してテストがパスすることを確認する。

→ 完了（既存プロジェクトの流れ終了）
