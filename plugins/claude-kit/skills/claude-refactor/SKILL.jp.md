# claude-refactor — Claude 設定全体の監査・整理

`.claude/` 配下の rules / skills / CLAUDE.md / hooks を横断的に監査し、
フォルダ構成の整備・重複/過密結合の解消・ファイルタイプ間の移管・JP/EN ミラーの整備を提案するスキル。

---

## 概要

Claude 設定はプロジェクトが育つにつれて自然に肥大化・複雑化する。
このスキルは以下をまとめて診断し、整理案をユーザーに提示する:

1. **rules** — フォルダ構成の整備、統合/分離の提案、ファイルタイプ移管の提案
2. **skills** — 類似スキルの提案
3. **CLAUDE.md** — 肥大化検出と `.claude/references/` への外出し提案
4. **hooks** — rules/CLAUDE.md のフック化候補の発見
5. **JP/EN ミラー** — 全スコープで対応ミラーファイルの欠如を検出

常に全スコープを対象とする。

### ステップ2: rules を分析する

#### 条件

- ステップ1 完了

#### 処理内容

以下の観点で各ルールを分析する。分析前に必ず以下のルール設計原則を把握しておくこと:

##### ルール設計の2種類

ルールには目的の異なる2種類がある。現行ルールがどちらの種類か、また正しい設計になっているかを判断する基準として使う:

**① リンクルール（ファイル連携型）**

関連するファイル群を束ねて「1つを編集したら他も確認する」という連携を強制するルール。

- `paths:` に連携させたいファイル群すべてを列挙する
- 例: 抽象クラス・インターフェース・子クラス・親クラスをまとめて1つのルールに
- 例: 設定ファイル・仕様書・テストケース・実装コードを紐づける
- **効果**: どれか1つを編集したとき、AIが全体像を把握した状態で作業できる

**② コンテキストルール（読み込みトリガー型）**

特定の作業エリアを触ったときに、必要な知識・仕様書・ガイドラインを自動ロードするルール。

- `paths:` に「このファイルを触ったとき読ませたいルールと紐づくファイル」を設定する
- 例: `config/` フォルダを触ったとき → 設定仕様書のルールが読み込まれる
- 例: `src/` 配下を触ったとき → コーディング規約ルールが読み込まれる

##### ユースケース思考で paths: を設計する

**「いつ読まれたいか」を起点に考える。**

`paths:` を設定するときは「このルールはどのタイミングで Claude に読まれるべきか」を先に決め、そこから逆算してパスを設定する:

1. **ユースケースを特定する** — このルールが役に立つのはどんな作業をしているとき？
2. **トリガーとなるファイル/フォルダを特定する** — その作業では必ずどのファイルを触るか？
3. **そのファイルを `paths:` に設定する** — 触るたびにルールが読み込まれる

**例1 — 仕様書フォルダのコンテキストルール**:
- ユースケース: 特定の設定ファイルを触るとき、対応する仕様書を読んでほしい
- トリガー: `config/` フォルダを編集するとき
- `paths:` に `config/**` を設定 → 設定ファイルを触るたびに仕様書ルールがロードされる

**例2 — 常時読み込みが必要なルール**:
- ユースケース: どんな作業中も必ず守ってほしいルール（コーディング規約など）
- トリガー: 任意のソースコードを触るとき
- `paths:` に `src/**` や `**/*.ts` など広いパターンを設定

**既存ルールの評価**: `paths:` パターンが「いつ読まれたいか」のユースケースと一致しているかを確認する。ずれている場合は修正を提案する。

##### 2-A: フォルダ構成の整備

1. `.claude/rules/` 直下にフラットな `.md` ファイルが多い場合、サブフォルダへの整理を提案する
2. 以下の基準でフォルダを決定する:

   **必須フォルダ**

   | フォルダ | 役割 | 何を入れるか |
   |---|---|---|
   | `core/` | プロジェクト全体の基礎ルール | コーディング規約・ワークフロー・環境設定・開発プロセス全般 |
   | `feature/` | 機能別ドメイン知識 | 機能単位の実装ルール・仕様・設計判断（1機能 = 1ファイル） |

   **任意フォルダ（コードベース依存）**

   | フォルダ | 追加する目安 |
   |---|---|
   | `ui/` | `components/`・`pages/`・`views/` などフロントエンドが存在する |
   | `api/` | バックエンド API のルールが多い / `routes/`・`handlers/` がある |
   | `infra/` | Docker・CI/CD・デプロイ系のルールが多い |

3. 各フォルダに `_overview.md` を生成することを伝える（テンプレートはステップ9に記載）

##### 2-B: 統合・分離の検出

ルールの過統合（密結合）と重複（統合不足）の両方を検出する:

**統合候補（重複の検出）**:
- 複数のルールで同じ `paths:` パターンや同じドメインを扱っているものを特定する
- 内容が大きく重複しているルールを「統合候補」としてマークする

**分離候補（過密結合の検出）**:
- 1つのルールの `paths:` が複数の無関係なドメインをカバーしている場合を特定する
  - 例: `src/models/` と `src/payments/` が同じルールに含まれている
  - この状態だと models を編集しただけで payments のルールも読み込まれ、コンテキストを無駄に消費する
- 「分離候補」としてマークし、ドメインごとに別ファイルへの分割を提案する

**判断基準**:
- `paths:` パターンが互いに無関係なディレクトリを含む → 分離
- `paths:` パターンが同一ドメインを重複カバーしている → 統合

##### 2-C: ファイルタイプの適切性チェック

各ルールについて §参考資料 / ファイルタイプ判断基準 の表で確認する

→ ステップ3へ進む

#### 出力

- フォルダ構成案
- 統合候補・分離候補一覧
- ファイルタイプ移管候補一覧

### ステップ4: CLAUDE.md を分析する

#### 条件

- ステップ3 完了

#### 処理内容

CLAUDE.md は毎回必ずロードされるため、内容は極力薄くする必要がある。

##### 4-A: 肥大化の検出

1. 200行超の CLAUDE.md を「肥大化」としてマークする
2. 行数が多くなくても、詳細な説明・ワークフロー・参考資料が含まれている場合は外出しを提案する

##### 4-B: 外出し先の提案

各セクションについて以下の優先順で外出し先を提案する:

| 内容の性質 | 外出し先の提案 |
|---|---|
| 特定ファイル編集時にのみ必要なクロスパスリンク | `.claude/rules/` — パスマッチで必要な時だけロード |
| 複数ステップのワークフロー・手順 | `.claude/skills/` — オンデマンド呼び出し |
| 特定ディレクトリにのみ関係する内容 | そのサブフォルダ内の `CLAUDE.md` |
| 状況によって読み込みたい参考資料・詳細説明 | `.claude/references/{topic}.md` — CLAUDE.md にはファイルパスだけ記載 |
| プロジェクト内に既にある仕様書・ドキュメント | そのファイルパスのみ CLAUDE.md に記載し、内容は書かない |

**`.claude/references/` について**:
CLAUDE.md に書きたいが毎回読む必要はない内容（詳細仕様・補足説明・参考資料）を置く場所。
CLAUDE.md には「詳細は `.claude/references/xxx.md` を参照」とファイルパスだけ書き、
Claude が必要なときに読み込む形にする。

→ ステップ5へ進む

#### 出力

- 肥大化している CLAUDE.md の一覧と行数
- セクション別の外出し提案（外出し先含む）

### ステップ5: hooks を分析する

#### 条件

- ステップ4 完了

#### 処理内容

##### 5-A: hooks 化の候補発見

rules / CLAUDE.md の内容をスキャンし、以下の性質を持つものを「hooks 化候補」としてマークする:

| 性質 | フックイベント候補 |
|---|---|
| 「プロンプト送信のたびに確認する」「毎回チェックする」 | `UserPromptSubmit` |
| 「Claude が止まるたびに〜する」「作業完了後に確認する」 | `Stop` |
| 「ツール実行前に確認する」 | `PreToolUse` |
| 「ファイル編集後に通知する」 | `PostToolUse` |

##### 5-B: 既存 hooks の冗長性チェック

1. 同じイベントに複数のフックが登録されている場合、統合を提案する
2. 使われていないフック定義があれば削除を提案する

→ ステップ6へ進む

#### 出力

- hooks 化候補（現在の場所 → 移管先フックイベント）
- 既存 hooks の冗長性レポート

### ステップ9: 実行する

#### 条件

- ステップ8 でユーザーの確認が取れた

#### 処理内容

**カテゴリごとに対応するクリエータースキルを先に呼び出してから作業する。**
クリエータースキルは作成/変換の判断基準・テンプレート・ミラー同期を内包しているため、直接ファイルを書かない。

| カテゴリ | 先に呼び出すスキル | その後の作業 |
|---|---|---|
| rule の新規作成・変換・統合・分離 | `/claude-kit:rule-creator` | スキルの指示に従って作成・移動・統合・分割 |
| rule のフォルダ整理 | （スキル不要） | `git mv` でファイルを移動し、各フォルダに `_overview.md` を生成する |
| skill の新規作成・変換 | `/claude-kit:skill-creator` | スキルの指示に従って作成・変換 |
| CLAUDE.md の作成・外出し後の更新 | `/claude-kit:claude-creator` | スキルの指示に従って作成・更新 |
| hook の作成 | `/claude-kit:hook-creator` | スキルの指示に従ってフックを作成し、元の rules/CLAUDE.md から内容を削除する |
| JP ミラーの作成 | 対応するクリエータースキル（上記） | 各クリエータースキルが JP ミラー作成手順を含んでいる |

**`_overview.md` テンプレート**（rules フォルダ整理時に使用）:

```markdown
# {フォルダ名} — {カテゴリの一行説明}

## このフォルダについて

{このカテゴリに含まれるルールの方針を1〜3文で}

## ファイル一覧

| ファイル | 内容 |
|---|---|
| `{file}.md` | {1行説明} |
```

→ ステップ10へ進む

#### 補足

##### 禁止事項

- `cp` でなく `git mv` を使うこと（git 履歴を保持するため）
- クリエータースキルを呼ばずに直接ファイルを書かないこと
- 参照元（他のスキル・ルールからの言及）を更新し忘れないこと

## 参考資料

### ファイルタイプ判断基準

複数ステップで参照する共通基準。

| 内容の性質 | 最適なファイルタイプ | 理由 |
|---|---|---|
| 複数の異なるフォルダをまたぐファイル同期リンク | **rule** | パスマッチで対象ファイル編集時にのみ自動ロード |
| 単一フォルダ内のファイル一覧・ローカル規約 | rule または サブフォルダ CLAUDE.md | 一覧性重視なら rule、co-location 重視なら CLAUDE.md |
| プロジェクト全体で常に必要な短いワークフロー・禁止事項 | **CLAUDE.md（ルート）** | セッション開始時に必ず読み込まれる |
| 複数ステップ・ユーザー確認・分岐があるワークフロー | **skill** | オンデマンド呼び出し、コンテキストを汚染しない |
| 「〜のたびに自動チェック/通知」という繰り返し処理 | **hook** | イベント発火で自動実行、Claude のコンテキストに注入 |
| 1〜2行のシンプルな指示・注意事項 | CLAUDE.md または rule | スキルにするほど複雑でない |
| 状況によって読み込みたい詳細説明・参考資料 | `.claude/references/` | CLAUDE.md にはパスだけ書き、必要時に読み込む |
