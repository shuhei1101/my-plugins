# Jinja2 テンプレートオーサリング — Markdown 出力

**Markdown を出力する** Jinja2 テンプレート（例: `hooks/templates/injection.md.j2`）の執筆ルール。
レンダリングバグのほとんどは、Jinja2 のホワイトスペース除去と Markdown のブロック要素間スペーシング
の相互作用から生じる。以下のパターンはこのリポジトリで実際にテンプレートを壊した事例なので、
習慣として身につけること。

英語正本: `references/jinja2/templates.md`

---

## 前提となる Jinja2 環境

以下の環境設定を前提とする:

```python
Environment(
    trim_blocks=True,       # {% %} 直後の最初の改行を除去
    lstrip_blocks=True,     # {% %} の前の行頭ホワイトスペースを除去
    undefined=StrictUndefined,
    autoescape=False,
)
```

これは `claude-kit` / `dev-kit` の注入フックで使われている設定。同じフック基盤向けに
テンプレートを書くなら、この設定を継承するのでこのルールが適用される。

`trim_blocks` が以下のバグのほぼすべての原因。設定を変えるならルールも変わる。

---

## ルール 1 — `{% %}` ブロックタグは直後の改行を 1 つ食う

`trim_blocks=True` のもとでは、`{% ... %}` タグの **直後の** 改行が剥がされる。
つまり `{% endif %}` のあとに 1 行空けて書いても、出力には **空行が 0 行** になる。

### アンチパターン

```jinja
{% if note %}
> {{ note }}
{% endif %}
## 次の見出し
```

レンダリング結果:

```markdown
> note text
## 次の見出し
```

blockquote と `##` 見出しが隣接行で衝突する。ほとんどの Markdown レンダラーは見出しとしてはパース
してくれるが、視覚スペーシングが壊れ、レンダラーによっては両者が結合されてしまう。

### 修正 — 空行をブロックの **内側** に置く

```jinja
{% if note %}
> {{ note }}

{% endif %}
## 次の見出し
```

空行はブロック内のコンテンツの一部なので、生き残る。`trim_blocks` が `{% endif %}` 直後の改行を
食ったあとも、blockquote と見出しの間にちょうど 1 行の空行が残る — これが Markdown が必要とする形。

**経験則**: Markdown のブロック要素（見出し、リスト、blockquote、コードフェンス、テーブル）の周りに
空行が必要なら、その空行は `{% endif %}` / `{% endfor %}` の **外側** ではなく、囲んでいる
Jinja2 ブロックの **内側** に置くこと。

---

## ルール 2 — 連続するブロックタグはあいだの改行を **全部** 消す

`{% endfor %}{% endif %}{% if other %}`（1 タグ 1 行で並ぶ）の連鎖は `trim_blocks` を通って
途中の空行がすべて消える。次に来る可視文字が `---` だと、それは **直前のコンテンツの最後の行** に
バインドされ、setext スタイルのレベル 2 見出しになってしまう。

### アンチパターン

```jinja
{% if required %}
{% for ref in required %}
- {{ ref.name }}
{% endfor %}
{% endif %}
{% if optional %}
---

## Optional references
```

レンダリング結果:

```markdown
- last_ref_name
---

## Optional references
```

`last_ref_name\n---` は Markdown の **setext 見出し**（dash がその前の行に下線を引く形式）になる。
リストの最後の bullet が黙って見出しに化け、`---` セパレータは出力から消える。

### 修正 — 先頭の空行を optional ブロックの **内側** に入れる

```jinja
{% if required %}
{% for ref in required %}
- {{ ref.name }}
{% endfor %}
{% endif %}
{% if optional %}

---

## Optional references
```

`{% if optional %}` ブロックの先頭の空行は `trim_blocks` を生き延びるので、出力は
`空行 + ---` となり、Markdown は setext 見出しの下線ではなく `<hr>` として認識する。

**経験則**: `{% endif %}{% if X %}` の直後に `---` が続くなら、`---` の前の空行は
内側の `{% if X %}` ブロックの内側に置くこと。

---

## ルール 3 — 見出し末尾の `}}` は Handlebars 系パーサーを混乱させる

次のような行

```jinja
## {{ ref.path }} — {{ ref.description }}
```

は綺麗な Markdown にレンダリングされるが、見出し末尾の生の `}}` は **下流ツール**
（Handlebars / Mustache / Jinja2 系記法を使う IDE プレビュー、チャットクライアント、ドキュメントジェネレータ）
が誤読することがある。そういうツールはマッチする `{{` を探してバッファの残りを噛み続け、
後続コンテンツが黙って消える。

### 修正 — 行末を `<!-- -->` で閉じる

```jinja
## {{ ref.path }} — {{ ref.description }}<!-- -->
```

HTML コメントはレンダリングされた Markdown では不可視だが、`}}` とそのあとに続く literal text を
分断するので、Handlebars 系パーサーはコメントでスキャンを止める。

**Jinja2 式（`}}`）で行が終わる見出し・段落すべてに適用する**。
`}}` のあとに literal text が続く行（例: `{{ name }} — description`）は、literal text が
既にパース連鎖を切るので安全。

---

## 一般的なオーサリングガイダンス

1. **すべてのテンプレートを末尾改行 1 つで終わらせる**。最終改行がないファイルは、最後のブロックが
   レンダラーが続けて出すコンテンツと結合してしまう。
2. **`{%- ... -%}` よりも Markdown の通常の空行リズムを優先する**。先頭/末尾 dash 付きの変種は
   ホワイトスペース除去を細かく制御できるが、`trim_blocks` / `lstrip_blocks` との組み合わせが悪く、
   推論しづらいテンプレートを生む。標準フォーマットでは必要なスペーシングが達成できない稀な場合
   のためにとっておくこと。
3. **テンプレート構文だけでなくレンダリング結果をテストする**。構文として通るテンプレートでも、
   パース不能な Markdown を生むことがある。代表的なペイロードでレンダリングし、Markdown として
   表示確認する — できれば消費側と同じレンダラーで。
4. **Jinja2 制御タグは 1 行 1 タグに保つ**。`{% endif %}{% endfor %}` を 1 行に詰めると
   ルール 2 が見つけにくくなり、ホワイトスペースが予測不能になる。

## クイックチェックリスト

`.md.j2` テンプレートを編集するときは、以下を順に確認する:

- [ ] Markdown のブロック要素の前にある `{% endif %}` / `{% endfor %}` すべて — 必要な空行は
      ブロックの **内側** にあるか？
- [ ] `---` が続く `{% endif %}{% if X %}` の連鎖すべて — 空行は内側の `{% if X %}` の **内側** にあるか？
- [ ] `}}` で終わる見出し・段落すべて — `<!-- -->` で行末を閉じているか？
- [ ] ファイルの末尾はちょうど 1 つの改行で終わっているか？
- [ ] 代表的なペイロードでテンプレートをレンダリングし、出力を確認したか？
