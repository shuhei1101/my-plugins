# ルール設計ガイド

`.claude/rules/<name>.md` の設計・作成・評価に使う知識をまとめたドキュメント。

---

## 読み込みタイミング

`paths:` パターンに一致するファイルを Claude が**読み込んだとき**にロードされる。

- ✅ ファイルを読む → ロードされる
- ✅ ファイルを編集する（編集前に読むため） → ロードされる
- ❌ `mv` / `rm` 等のシェルコマンドのみ → ロードされない
- ❌ ファイルを参照せず別の作業をする → ロードされない

---

## ルールの2種類

ルールには目的の異なる2種類がある:

### ① リンクルール（ファイル連携型）

関連するファイル群を束ねて「1つを編集したら他も確認する」という連携を強制するルール。

- `paths:` に連携させたいファイル群すべてを列挙する
- 例: 抽象クラス・インターフェース・子クラス・親クラスをまとめて1つのルールに
- 例: 設定ファイル・仕様書・テストケース・実装コードを紐づける
- **効果**: どれか1つを編集したとき、Claude が全体像を把握した状態で作業できる

### ② コンテキストルール（読み込みトリガー型）

特定の作業エリアを触ったときに、必要な知識・仕様書・ガイドラインを自動ロードするルール。

- `paths:` に「このファイルを触ったとき読ませたいルールと紐づくファイル」を設定する
- 例: `config/` フォルダを触ったとき → 設定仕様書のルールが読み込まれる
- 例: `src/` 配下を触ったとき → コーディング規約ルールが読み込まれる

---

## ユースケース指向で `paths:` を設計する

**「いつ読まれたいか」を起点に考える。**

1. **ユースケースを特定する** — このルールが役に立つのはどんな作業をしているとき？
2. **トリガーとなるファイル/フォルダを特定する** — その作業では必ずどのファイルを触るか？
3. **そのファイルを `paths:` に設定する** — 触るたびにルールが読み込まれる

**例 — 設定仕様書のコンテキストルール**:
- ユースケース: 設定ファイルを触るとき、対応する仕様書を読んでほしい
- トリガー: `config/` フォルダを編集するとき
- `paths:` に `config/**` を設定 → 設定ファイルを触るたびに仕様書ルールがロードされる

**例 — 常時読み込みが必要なルール**:
- ユースケース: どんな作業中も守ってほしいルール（コーディング規約など）
- トリガー: 任意のソースコードを触るとき
- `paths:` に `src/**` や `**/*.ts` など広いパターンを設定

---

## 統合・分離の判断基準

- **統合**: 同じドメインを扱う重複ルールは統合してよい
- **分離**: 無関係なドメインを1つのルールにまとめてはいけない
  - `paths:` が無関係なフォルダを含む → 触れるたびに不要なコンテキストが読み込まれる
  - 1ドメイン = 1ルールファイルを原則とする

## フォルダ構成の基準

### 必須フォルダ

| フォルダ | 役割 | 何を入れるか |
|---|---|---|
| `core/` | プロジェクト全体の基礎ルール | コーディング規約・ワークフロー・環境設定・開発プロセス全般 |
| `feature/` | 機能別ドメイン知識 | 機能単位の実装ルール・仕様・設計判断（1機能 = 1ファイル） |

### 任意フォルダ（コードベース依存）

| フォルダ | 追加する目安 |
|---|---|
| `ui/` | `components/`・`pages/`・`views/` などフロントエンドが存在する |
| `api/` | バックエンド API のルールが多い / `routes/`・`handlers/` がある |
| `infra/` | Docker・CI/CD・デプロイ系のルールが多い |

---

## ルールファイルの必須セクション

| セクション | 内容 | 必須/推奨 |
|---|---|---|
| フロントマター `paths:` | ルールが発動する glob パターン | **必須** |
| `## Overview` | このルールが何を管理するかの説明 | 必須 |
| `## Related Files` | ファイルパスと役割の一覧 | 推奨 |
| `## When Editing` | 更新時に必ずチェックする項目 | 推奨 |
| `## Rule Maintenance` | ファイル追加・削除・リネーム時のルール更新手順 | 推奨 |

---

## 構造例

```markdown
---
paths:
  - "src/models/**/*.py"
  - "tests/test_models.py"
  - "docs/specs/models.md"
---

## Overview

models ドメインの実装・テスト・仕様書を束ねるルール。

## Related Files

| ファイルパス | 役割 |
|---|---|
| `src/models/**/*.py` | 実装 |
| `tests/test_models.py` | テスト |
| `docs/specs/models.md` | 仕様書 |

## When Editing

- [ ] 実装・テスト・仕様書の内容が一致しているか確認する
- [ ] 新しいファイルを追加した場合、このルールの `paths:` も更新したか

## Rule Maintenance

- **新規ファイルを追加した** → `paths:` と Related Files に追加する
- **ファイルを削除・リネームした** → `paths:` と Related Files から削除・更新する
```

---

## 単一フォルダ内容の置き場：rules vs サブフォルダ CLAUDE.md

| 優先したいこと | 選択 |
|---|---|
| **全ルールを一箇所で把握したい**（監査・一覧性重視） | `.claude/rules/<name>.md` |
| **コードに隣接してルールを置きたい**（co-location 重視） | サブフォルダ `CLAUDE.md` |

複数の異なるフォルダをまたぐリンクは常に `.claude/rules/` に書く。
